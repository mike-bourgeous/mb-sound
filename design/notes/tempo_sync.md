# Tempo sync

Detailed notes moved from CLAUDE.md (2026-10-10); CLAUDE.md keeps a summary and points here.  Update both when behavior changes.


`Sequence::Duration` (`lib/mb/sound/sequence/duration.rb`) is an exact musical length in whole notes (comparable, `+`/`-`, scaled by numbers, friendly `to_s` like "3 × n16"), accepted wherever lengths are (`on:`/`in:`/`at:`, `fade:`, `every`, `after`, `render(bars:)`, `.len`, `until`).  `1.beat.hz` is a Pitch whose frequency comes from a `Sequence::TempoNode` following the tempo, and `4.bars.lfo` a Tone from it.  Tones made from the pitch lock their phase to the timeline on jumps (start, seeks, resume) plus `with_phase`, top-down through two TempoNode ports that are inputs of each tone (`Tone#follow_timeline`; `jumps` is 1 on the first sample after a jump, `jump_phase` the timeline position in cycles there, shared frozen zeros otherwise), split and band-limited like resets; they freeze while the timeline is paused unless `.freewheel` (per TempoNode; `Tone#timeline` is the TempoNode).  `sig.delay(1.n8.dotted)` (or `sig.filter(3.n16.delay(...))`, `multitap(1.n8.d, ...)`) follows the tempo; `2.bars.lfo.square.at(3.n16..5.n16)` gives an alternating delay time (`Tone#musical_time?`).  Tempo-following nodes include `Sequence::TimelineNode` (shared with `MIDI::ClipSource`, found through the Notes nodes' streams), which `Session` finds in every graph (`timeline_nodes`).  `Tone#lfo` means full range plus no MIDI retrigger.  `render(bars:)` counts bars on the timeline, so tempo changes during a render are followed; `tail: true` adds the master effects tail after the limit.  See `bin/songs/tempo_song.rb`.

Meter map (2026-10-10, branch `arrange-form`; `arrangement.md`): `Transport#meters` (`Meter(pos, bar_length, bar)`), `#meter(bar_length, at:)` (on a bar line; later entries dropped), `#meter_at`, `#bar_at(pos)` (Rational bar position from 1), `#bar_position(bar)`, `#next_bar_line(pos, every = 1)`, `#bars_length(pos, bars)`, `#bar_length(pos = position)`; console `meter 7, 8` (alias `time_signature`).  Bar numbers count through the map (`bar(n)`, `at_bar`, `after`, `every`, `seek(n)`, `:bar`/N-bar alignments, `in: N`, stamps, `render(bars:)`, form sections given in plain bars, takes).  `bar_length=` sets one meter for the whole timeline.  `Numeric#bars` Durations stay whole notes at the current transport's bar length when created (`Sequence.current_transport`, below).

Build-time tempo (2026-10-15, branch `fixes-14`): conversions that read a tempo when a graph is built (Lengths and Durations to seconds or samples by default, `Numeric#bars`, `bounce`'s default `bpm:`, `render`'s default tempo, `Clip#bake`, `ghost_chords`' default span, `Sample#transport`) read `Sequence.current_transport`: the current Session context's transport (a `render` block, a scheduled block, a scene build), else the default `Sequence.transport`.  Before, they read the default transport, so a song's `bpm 72` in a render (which sets only the render's own transport) left them at 120: granular_song bounced its sources and read its spray's `density: 1.n16` at 120 BPM, and wind_chimes' section envelopes got their default hold (twice the time before the release, in seconds at build) at 120, which happened to equal the intended release at 60 BPM (the song now passes `hold:`; renders unchanged).  Inside a scheduled block, `bpm n` queues the change for the block's time; the rest of the block now reads it (`bpm` returns it; `current_transport` is a Transport at the pending tempo, kept in the context), so a bounce or a length built after it counts at the tempo it will play at.  Audit: every `bin/songs` script rendered on master-ai and the branch with a hook reporting default-transport reads under a render session at another tempo (314 sites before, only `TimelineNode#transport`'s fallback after, which Sessions replace on start); only granular_song (spray) and wind_chimes changed, both kept bit-identical to the Bench picks.  Spec: `spec/lib/mb/sound/sampler_spec.rb` ("bounces at the tempo...").

## Session time for clocks: run frames (time-automation; maintainer-approved 2026-10-18)

Clocks (`MB::Sound::Clock`, arrangement.md "Clocks") count **run frames**, not bars and not raw session frames.  A run frame is a frame the Session rendered while its timeline was moving (`Session::Clocks#run_frame`): it advances with every span the timeline advances, keeps going through seeks and scene drops (a seek jumps the timeline, not the run count), and pauses whenever the timeline pauses (a live session with nothing playing).  Ratio clocks follow the matching odometer: whole notes the timeline advanced, seeks not counted.

Why not raw frames since the session started: a live session keeps rendering (and counting frames) while it idles between commands, for however long the performer types, and a take replay doesn't reproduce those wall-clock gaps (its lines land on timeline positions).  Counting only frames where the timeline moved makes the live run and every replay agree on each clock's phase, exactly, at any buffer size.  Takes that start after the timeline already ran record the run frame and odometer (`run_frame:`, `odometer:` in the start state) and replays restore them.  Why not bars: a clock's whole point is to keep its own time through tempo changes, seeks, and relaunches (a bowl loop of 19.7 s comes back where it would have been).

## Tempo maps, ramps, and followed tempo (tempo-maps-1, 2026-10-28)

The Transport's tempo is a function of timeline position: `Sequence::TempoMap` (a frozen value) holds segments, each from a position on: a **step** (a constant BPM), a **ramp** (from a BPM to a BPM over a length in whole notes, shaped by a Curve; afterwards the target holds), or a **follow** (a source read as BPM: a Session knob name, a Knob, or a `MIDI::Param` such as `4.bars.lfo.at(150..180)`).  A map with one step at `-Infinity` is the old constant tempo, and every path is then unchanged (bit-identical renders).

How the Session integrates it (the clocks' approach, `Session::Clocks`): spans are split so that the tempo is constant inside each one.  While a ramp or a follow is in effect, a span ends at the next **tempo cell** boundary (every `TempoMap::CELL` = 800 run frames, the clocks' `Clock::CELL` grid) and at the frame where the position reaches the map's next breakpoint (a ramp's end, a later segment); the tempo for the span is the map's value at the span's first position, quantized to 1/1024 BPM (Rational positions keep bounded denominators).  So positions are exact Rationals, the tempo steps every 16.7 ms at 48 kHz during a ramp, and every buffer size and every take replay renders the same frames at the same tempos (run frames are restored by takes).  Everything that already reads the tempo per span (clip sources and their quiet reads, TempoNodes and tempo LFOs, tempo-synced delays, launch-point landings, `at_bar`, the meter map, `render(bars:)`, clocks' tempo points) follows the map with no changes of its own; estimates made ahead of time (scheduler lookahead, `seek 32.seconds`) read the current tempo.  `render(bars:)`'s end bar is found in the span holding it (`Session#process_buffer(count, until_pos:)`: the buffer ends on the first frame at or past the position, at that span's cell tempo), since omnibus16: renders estimated the frames to the end from the tempo at their last buffer's start, so a followed tempo LFO ended renders 1-2 frames apart at 367 and 800 frames (generative-g4's session fuzz seeds 52, 82, 127; session_fuzz_spec keeps them and a shrunk song).

Changes: `bpm 140, over: 4.bars` (and launch points, `curve:`, followed sources) is a journaled `:tempo` change (subject `:tempo`), a timeline change like seeks (it lands at the start of a span on its exact frame), undoable (restores the map as it was), exact in takes.  A ramp starts from the tempo in effect where it lands, so a new `bpm` mid-ramp replaces the ramp from the current tempo.  Plain `bpm 120` (no options) keeps its old immediate path (a constant tempo everywhere: it ends a ramp or a follow) so scripts calling it outside any Session still work.  Seeks collapse the map to the segment in effect (like the key map: a live ramp isn't replayed by jumping back) unless the map was assigned whole (`Transport#tempo_map=`, e.g. from a MIDI file), which seeks read as a function of position.

Ramp shape (decision, see the report): linear in BPM over musical position by default (a straight line on the bar ruler, as DAW tempo lanes draw it); `curve:` takes any Curve.  `over:` is bars (through the meter map), a Duration, or seconds (`over: 10.seconds`: the ramp's length in whole notes is solved from the curve so it lasts that long).

Implementation notes: `Session::TempoChanges` (`change_tempo_map`, `tempo_cell`).  The cell tempo is read at the cell's start, or where the map, its segment, or the timeline generation changed inside it, and again at the end of each moving span for the next frame and right after a :tempo change or its undo lands, so console lines typed between buffers and take replays at other buffer sizes (whose changes land inside spans) see the same tempo; ramps start, and seeks collapse, from the map's own tempo at the landing position (not the cell's).  A live map that stops moving (a finished ramp, a step) settles back to a constant map, so the constant-tempo path (no span splits) comes back.  Hz LFOs and other audio-rate nodes are refused by the param rule (`MIDI::Param::NotAParam`), pointing at a knob that follows them (`turn :tempo, follow: 0.1.hz.lfo.at(90..180); bpm :tempo`).  Tempo values compare (`Tempo#<=>`), so `90.bpm..180.bpm` ranges work for knobs.  Not yet: a take started mid-ramp records only the tempo then (the start state has no map), and `seek 32.seconds` / scheduler lookahead convert at the current tempo.  MIDI files: `Transport#tempo_map = TempoMap.steps([[whole_notes, bpm], ...])` is the hookup for midi-import-1's FileSource tempo-map reader (positions = ticks / (4 * ticks per quarter)).  Specs: `spec/lib/mb/sound/session/tempo_changes_spec.rb`; session fuzz has a tempo command.
