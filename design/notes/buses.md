# Buses, sends, and bus sidechains

<!-- summary -->
`bus(:verb) { |sig| sig.reverb(:hall, mix: 1) }` (`Session::Buses`, console `BusMethods`: `bus`, `buses`, `feed`, `routes`) makes a named bus, a master-like chain (`Master::Chain` machinery) with its own input, into the master or another bus (`to:`; loops refused).
Routing belongs to player names: `track(:keys, send: { verb: -12.db })`, `track(:kick, to: :drums)`, `bg ..., send:`; sends are post-fader or pre-fader (`send: { verb: [-12.db, :pre] }`: before the level, after fades, mute); `feed :keys, :verb, -6.db, over: 2` (`pre: true`) is an undoable `:send` change.
Readers (`GraphNode::BusTap`: `duck(:drums)`, `duck(:drums, only: :kick)`, `bus(:drums)`) work anywhere, hear tracks pre-fader (`key_level :kick, -6.db` sets how hard a track drives them); buses ring out and sleep on the 800-frame grid, so output is the same at any buffer size; `render(stems:)` stems sum to the pre-master mix.
<!-- /summary -->

## Quick reference

- `bus(:verb) { |sig| sig.reverb(:hall, mix: 1) }`, `buses`, `routes`; routing on players: `track(:keys, send: { verb: -12.db })`, `track(:kick, to: :drums)`, `feed :keys, :verb, -6.db, over: 2` (undoable).
- Pre-fader sends: `track(:lead, send: { verb: [-6.db, :pre] })`, `feed :lead, :verb, -6.db, pre: true` (`pre: false` back, level optional when switching); `level :lead, 0` then leaves only the reverb; mute still cuts it ("Pre-fader sends" below).
- Readers anywhere: `duck(:drums)`, `duck(:drums, only: :kick)`, `bus(:drums)`, pre-fader; `key_level :kick, -6.db` (knob `:"kick/key"`) is how hard a track drives its readers; `render(stems:)` stems sum to the pre-master mix.
- Resamplers in bus, master, and stem chains and in graphs reading a tap run `:min_phase` when given no `mode:` (latency 0, live and in renders: the same samples); given a mode they read ahead and the chain is `Chain#latency` frames late (`buses` shows it; PDC is a later project).  "Chains that read ahead" below.
- Spec `spec/lib/mb/sound/session/buses_spec.rb`; help `help :buses`.

Branch buses-1 (2026-10-13).  The maintainer queued "Buses, sends, bus sidechain" (persona consensus B; Kez Volta asked for `duck(:drums, only: :kick)`; earlier: longer delay and reverb tails should come through "future effect sends" rather than delay discovery).  The summary block above feeds the generated index (`design/notes/README.md`, `rake docs:index`).  Update it when behavior changes.

## API

```ruby
bus(:verb) { |sig| sig.reverb(:hall, mix: 1) }        # a named bus: its own effect chain, into the master
bus(:slap, to: :verb) { |sig| sig.delay(1.n8) }       # into another bus (no loops)
bus(:drums) { |sig| sig.compress(threshold: -18.db) } # the same kind of bus, used as a group
track(:keys, send: { verb: -12.db }) { |c| ... }      # sends (post-fader), per player name
track(:lead, send: { verb: [-6.db, :pre] }) { |c| ... } # a pre-fader send: `level :lead, 0` keeps feeding it
feed :lead, :verb, -6.db, pre: true                   # switch a send to pre-fader (pre: false: back)
track(:kick, to: :drums) { |k| tr808(k) }             # the track's main out goes into a bus
bg :pad, graph, send: { verb: -6.db, slap: :space }   # bg too; a knob name follows the knob
feed :keys, :verb, -6.db, over: 2, on: :bar           # change a send (journaled, undoable)
feed :keys, :verb, 0                                  # off
bass.duck(:drums)                                     # sidechain from a bus or a track
bass.duck(:drums, only: :kick)                        # one named node inside a track's graph
pad.compress(sidechain: bus(:drums))                  # bus(:name) reads a bus or track anywhere
master { |mix| mix.duck(:kick_bus) }                  # master chains read them too
mute :verb; solo :verb                                # buses are strip names
buses; routes                                         # listings
render('x.flac', stems: 'stems/') { ... }             # one stem per bus too
```

## Decisions (agent's, open to the maintainer's review)

- **One concept** (maintainer, 2026-10-18: "bus and send should be the same thing unlike in some DAWs"): a bus is a named chain; a player reaches it with a level (`send:`, `feed`) or with all of its sound (`to:`).  There are no aux, return, or group kinds: the routing tree, the buses pane, and the meters (`Snapshot#bus_levels`, `#send_levels`, terminal_ui.md "UI round 4") show one kind of bus with its sends and sources.

- **Names.** Buses share the Session namespace with tracks, groups, and knobs (`Names#claim(name, :bus)`), so a bus can't be named like a track; `:master` stays reserved.  `send` is `Object#send` (every object, used all over the library), so the console command is `feed` (aliases `send_level`, `fx_send`; maintainer 2026-10-13: keep `feed`, add `fx_send`); `send:` stays the keyword on `track`/`bg`.
- **The bus is a master-like chain with its own input.** A bus reuses `Session::Master`'s chain machinery (`Master::Chain`, `build_master`, spill/fade/cut handover): the block gets the bus input as a bundle (one parameter) or per channel, `bus :verb { ... }` again swaps the chain at a launch point with the old one spilling over (or `fade:`), and undo rebuilds the previous chain from its block (`:bus` changes, `BusState`).  Bus chains are installed as plans like players (`Plan.install`): the `MixSource` channels are boundaries, the chain behind them fuses.
- **Routing belongs to names**, like mute flags: a graph replacing `:keys` keeps its sends.  Each player has a main out (the master, or a bus with `to:`) and any number of sends.  Sends are post-fader: after the fade ramps, the level (`level :keys, -6.db`; arrangement.md "Track levels"), and mute/solo (contract K7's order: fade, gain, mute/solo, then routes), so a muted or faded track sends nothing, and a ringing-out track keeps sending its tail.  Armed monitors (`:"lead/live"`) use their track's routes.  Pre-fader sends (since prefader-sends-1) skip the level only (below).
- **Send levels** are linear gains (`-12.db` reads as its gain) or a knob (a name or `knob(:x)`) to follow.  Internally each send is an unregistered `GraphNode::Knob` advanced with the Session's knobs, so ramps land on exact frames at any buffer size, `over:` takes bars, Durations, or Lengths with any `curve:`, and undo restores the level the same way knob turns do.  Ramps are linear in gain, like every fade.  `feed` lands right away (with the knob glide) unless given a launch point.  Negative numbers raise (write `-6.db`).
- **Order.** Each span renders players and buses in dependency order: a player before the buses it feeds, a bus before the bus it feeds, any source before a graph that reads it (`bus(:x)`, `duck(:x)`).  Ranks come from the longest path; equal ranks keep the existing order, so sessions without buses or readers render exactly as before (the same summation order).  A cycle goes through `live_error` when it is made (`bus`, `track`, `bg`, a reader added) and is broken at render time (the reader gets silence) if one appears anyway.
- **Readers** (`GraphNode::BusTap`): `bus(:name)` is a bundle of the Session's channels; `bus(:name, only: :kick)` is mono.  They read the current span's signal of their source: a bus's output (before its mute), a player name's output (after its fades, before its level, mute, solo, and routing: pre-fader since session-2, below), or with `only:` a node inside the named track's graph (a drum `Voice` named like it, or a node given `.named(:kick)`), read through a spy as the track renders (before the track's fade and mute: it's the voice itself).  A bus chain's input (`GraphNode::MixSource`) serves consecutive pieces of the span's buffer to reads of fewer samples, so a Synth in a bus chain whose lanes wake inside a buffer (read in windows) works (Kez's K10, `"asked for 799 samples, but the mix buffer has 800"`; fused plans hid it from fuse-more-1, 3ee3c039, on, and plans off it failed until omnibus17; buses_spec, mix_source_spec, SessionFuzz step).  Spies attach to every graph as it starts under the read name (`Session#start_player` -> `Buses#start_player_spies`, idempotent) as well as to the graphs playing when the reader is bound: before omnibus17 a graph queued before its reader (a scene swapping the drums' kit on the bar as it starts the ducked bass) or brought back by undo/resume played unread, so `duck(:drums, only: :kick)` read silence after the swap (Munro's M3; `buses_spec.rb`, SessionFuzz step).  Exact at any buffer size (the source renders first in the same span).  A source that something reads keeps rendering while muted or not soloed, so soloing a ducked bass keeps it pumping (its muted kick's CPU stays spent while read; found by tunnel_vision_spec, which solos the Reese).  It does so from the frame a player's reader first starts (a bus or master chain: from its binding), and on from there, since readers stay bound: a reader is bound when its graph is added, which a scheduled block does ahead of its time on a buffer that depends on the buffer size, and before fix-bufsize-1107 that binding woke a held or muted source there, so its clip chased from another frame at 800 and 367 frames (SessionFuzz seed 611891; `Buses#bus_read_from`, buses_spec "wakes a held source").  A reader outside a Session reads silence.  Readers are plan boundaries for now.
- **Mute and solo** (maintainer, 2026-10-13: yes, solo-in-place, and sidechain sources keep feeding readers when muted). A muted bus sleeps (its senders' sends are dropped, their direct sound is untouched).  Solo is solo-in-place through the routing: a soloed track keeps the buses it feeds audible (so its reverb stays), and a soloed bus keeps the tracks feeding it audible (dry too: a track's sends and main out are one strip).  Tracks sending to the same bus that aren't soloed are silent as usual.
- **Tails and sleep.** A bus processes while anything is sent to it and rings out after its senders stop, sleep, or ring out, so delays and reverbs on buses finish on their own (no delay discovery).  It sleeps once its input and output have both stayed below `Master::TAIL_THRESHOLD` (-90 dB) for `TAIL_QUIET_SECONDS` (1 s), checked on the 800-frame session grid (`Synth::SKIP_GRID`), and wakes on the exact frame its input reaches the threshold, so output and CPU decisions are the same at any buffer size.  On waking, its chains' timeline nodes (clips, tweens, tempo LFOs) restart at the song position, from where the chain started (with the bus, not with its first signal), so a chain's `tween(..., loop: false)` plays what the same tween on a track from bar 1 plays there: before fix-bus-tween-1 (2026-11-08) a one-shot tween woken in its first step jumped to its end value (a Glide chase without a previous keyframe; curves.md).  Measured after the fix: one-shot, looping, and `align: :launch` tweens, `1.bar.lfo`, `1.beat.hz`, and `x.bars` LFOs in a chain fed from bar 2, off the bar, or after a gap it slept through match the track (equal, the `x.bars` LFO within 3e-8), at 800 and 367 frames, plans on and off.  No cap: a frozen reverb rings until muted.  `render` keeps rendering after the last player until buses and master chains are quiet (as before, at most `MAX_TAIL_SECONDS`).
- Bus chains for stem copies are built on the render thread inside `Session.with_context(session: self)`, so blocks that call console commands such as `knob(:x)` find the rendering Session (round 3 found `No knob :lift` from a stems render).
- **Stems** (maintainer, 2026-10-13: "Use final versions of stems through all non-mastering processing"): a track's stem is the track as heard before the master chain: its main out if that goes to the master, plus its own share of every bus it sends or plays into, rendered by its own copy of each bus it reaches (`Buses#stem_shadow`: a chain built from the bus's block, fed only by that track, following the bus's chain swaps and mute, routed through its own copies of downstream buses).  So stems sum to the pre-master mix (exactly for buses linear in their input, like delays, reverbs, and ducks by a sidechain; up to the nonlinearity of compressors and clippers on buses), and nothing counts twice.  `render(stems:, bus_stems: true)` also writes each bus's output ("<bus>.flac").  Costs a copy of each bus per sending track, in stems renders only.
- **The master gain** applies to the sum of players' main outs and bus outputs (pre-chain by default), as before.

## Pre-fader sends (prefader-sends-1, 2026-11-10)

The maintainer (2026-11-09): "Pre-fader sends are also very important", for playing audio into an effect without hearing the dry sound (a reverb lead-in, a sidechain feed); the .acd converter needs them (42 of his 431 ACID projects use send mode 2, pre-fader).
- **Values.** A send value is a level (a gain, a knob name, a node) or `[level, :pre]` (`[level, :post]` too): `track(:lead, send: { verb: [-6.db, :pre] })`, the same on `bg`, `Session#route`, genre roles (`Genre::Role`), and set documents.  `Buses.send_parts` is the one parser; other Arrays raise (a mode symbol gets a did-you-mean).  `feed :lead, :verb, -6.db, pre: true` (or a level of `[-6.db, :pre]`) switches a send to pre-fader, `pre: false` back, nil keeps the mode, and the level may be left out to switch only the mode (`feed :lead, :verb, pre: false`).  `routes` and `Session#route_definitions` list `[level, :pre]`; the buses pane prints "-12.0 pre" and "lead (pre-fader send)".
- **Tap point** (agent's choice, review): after the fades (fade-in, fade-out, crossfades), mute/solo, and CUE's MAIN share; before the track's level.  So a pre-fader send at `level :lead, 0` keeps sending, fades still apply, a muted or soloed-away track sends nothing (pre-fader, post-mute: the conservative choice; consoles differ, and "pre-mute" is a later option), and a cue player sends nothing (CUE stays dry).  Readers (`duck`, `bus(:x)`) tap earlier, before the mute (their key level instead).
- **Mechanism: one send row, two tap points.** A send is still a row of `Buses#send_rows`: the bus input, the send's level knob, the stem shadow, and now what the row hears the player through: the post-fader `ramp` (fade x level x mute/solo x MAIN, computed as before, so post-fader samples are bit for bit what they were) or the strip's pre-fader tap point (`Faders#pre_fader_levels`: fade x mute/solo x MAIN; computed only for routes with pre-fader sends).  `Buses#deliver_player`/`#deliver_fast` add every row with the same kernel (`Kernels.accumulate`).  The mode is a hidden 0..1 `GraphNode::Knob` per send (`Route#pre`, `:"lead>verb/pre"`, made only for sends that are or were pre-fader, advanced with the send levels), so a `feed ..., pre:` lands on its exact frame at any buffer size and glides over the declick time (the row blends the two tap points meanwhile, `Buses#send_factor`), like a level change.  Undo restores level and mode (`SendState`); the `:send` change's data has `pre:`.
- **Set documents**: GraphIO format 10 (`:prefader_sends`) writes `send: { verb: [-6.db, :pre] }`; older mb-sound refuses the format line instead of the value.
- Sound: nothing changes unless a send is made pre-fader (golden unchanged).  Specs: `buses_spec.rb` "pre-fader sends" (level 0, the same samples as a unity post-fader send with fades at 800/367/7-128-333-frame buffers, mute and solo, CUE, feed switching on the exact frame at any buffer size, ramps, journal/undo/redo, knob follows, stems, set documents, the buses pane), `genre_spec.rb` (roles); SessionFuzz draws a pre-fader feed to a `:wet` bus with the level pulled to 0, sometimes switched back or muted (drawn last: seeds keep their songs).

## Measurements

CPU per 800-frame stereo buffer (2026-10-13, Linux desktop, no YJIT, median of 600 after 60 warm-up buffers, two rounds agreeing within 5%; `/tmp/buses-1/bench.rb` in the branch report): 16 constant players 120 us; the same sending to one passthrough bus 209 us (~5.5 us per send: one multiply-add per channel); routed `to:` a passthrough bus 133 us; plus four asleep reverb buses nothing is sent to 101 us (asleep buses cost nothing, and the routed path's in-place adds are a little faster than the plain mix); 16 noise players each with their own `:hall` 1543 us vs sending to one `:hall` bus 544 us (the point of buses); a pad ducked by `duck(:drums, only: :kick)` 253 us vs the same pad ducked by a ghost kick 290 us (the reader replaces a second kick voice).  Worst case per send stays one vector multiply-add per channel per buffer; a bus costs its chain while awake and nothing asleep.

Plans: bus chains are planned regions (installed like players' graphs; their `MixSource` input is the region boundary); readers (`BusTap`) are boundaries for now, so a `duck(:drums)` fuses with its sidechain as a boundary input, as before.

Demo: `bin/songs/tunnel_vision.rb` (buses by default, `--no-buses` for Kez's original; round 2: the :hall return gain `-H` dB, after "Buses, way more hall (-30dBFS or more?)"; round 3: +18 dB by default, the maintainer's pick ("18 sounds right during the notes"), the return at about -35 dBFS RMS in the breakdown with the breakdown at the original's -9.1 LUFS; a `:lift` knob (`-U`; on by default since patches-5, the maintainer's pick, with the lifted return 6 dB down, so +12 dB, "With the lift I might take the wet mix down 6dB or so"; lift 0 is round 3's +18 dB return) blends in an upward compressor on the return that lifts the hall's decaying tail (+6..+12 dB in the outro's thin bars; the breakdown's sustained pad keeps it above the threshold); small hall sends from the drums, Reese, neuro, boom, and riser, with the hall input highpassed at 250 Hz so the kick's body stays out; the pullup riser that plays on after the others ring out is Kez's arrangement, identical in both versions): the pad and liquid pluck dry, sending to a `:hall` bus ducked by the kick and an `:echo` bus (the `:space` knob is its send), and the basses ducked by the drums' own kick voice.  Same loudness as the original (-7.5 LUFS); the drop nulls to -44 dB against the ghost-kick version.  Renders and bench set: `/app/tmp/listening/buses-1/`.

## Warm-ups and the first routed span (dropouts-2, 2026-10-28)

A new bus's chain is built again in a sandbox and played there before its change is queued (`Session::Warming`, arrangement.md "Warming changes before they land"): the landing buffer of a `:hall` bus went from 66 ms (63 ms of it YJIT compiling) to 6.5 ms with YJIT, for ~250 ms more at the prompt.  The first routed span no longer sets an instance variable on the Session (`@ui_bus_meter` is preset), which had made YJIT recompile every Session method there.  Per-span bookkeeping (send rows, chain and bus snapshots, reader keys, segment positions) reuses its Arrays (graph_nodes.md, Allocation on the render path).

## Shared nodes (fixes-13, 2026-10-14)

A bus chain may share nodes with players (`lfo = 3.hz.lfo; bg :a, lfo * 0.5; bus(:fx) { |sig| sig * (lfo * 0.5 + 1) }`), like master chains since fixes-12 (`master_effects.md`).  Bus chains run in segments of a span (split on the sleep grid), sleep while nothing is sent or while muted, and a chain may start in a later segment, so each part of the bookkeeping applies:
- Every non-bypass bus chain (stem copies' too) is a Session graph for `Strip#span_graphs` (`Buses#bus_chain_graphs`), so a muted player sharing a node only with a bus chain still reads its branch.
- `:bus` changes (a new bus or chain, an undo's restore) carry the chain's `ChainGraph`, and chains landed but not started are waiting graphs for `Strip#catch_up_waiting`: their shared branches skip to the Tees' leaders at the start of every span.
- `Buses#bus_read_shared` keeps `Chain#read_to` (the session frame a chain read its shared branches up to): before each segment the chains read the frames they missed (asleep before waking, or before starting in this span) on their shared branches only, and after the last segment the frames they slept through (falling asleep on the grid, a mute ramp's end, asleep all span), like a sleeping player's `read_while_asleep`.  The chains' own nodes still sleep.
- Stem copies (`#stem_shadow`) are made at the start of the span, before players render (`#prepare_stem_shadows`, for the same sends `#deliver_player` used to make them for), so their new branches start on the span's first frame.

Measured on master-ai b6b06139 (mono, 120 bpm, 128/801/7, 800, and 7-frame buffers): a chain queued 0.3 s ahead read the LFO 0.155-0.176 off, 1.5 s raised `BranchBufferOverflow`; a sleeping bus waking after 1.5 s, a muted bus unmuted, a muted sender sharing the LFO only with the bus, a replacement chain while the old one spilled over, and an undo back to an LFO chain all raised; a track's stem copy read the LFO a span ahead (0.039 off in a 0.25 stem).  After: within 1.2e-7 everywhere (`buses_spec` 'nodes shared with players', 9 examples, all failing before).  Cost: 16 players sending to one bus with four asleep reverb buses, 800-frame stereo buffers, 311/320 us vs master-ai 307/308 (alternating, within noise).

## Trigger tracks (duck-keys, 2026-10-18)

A trigger route (`route(name, trigger: true)`, made by `sidechain :pump, clip` or `track(..., trigger: true)`) is a player name whose sound goes only to its readers: no main out, sends, stems, CUE, or meters; `to:`/`send:`/`feed` raise.  Readers read it like any source (before its mute; it keeps rendering while read), and any trigger route turns on the routed render.  Its level is its fader, the Session knob `:"name/level"` like every track's (`Session::Faders`, arrangement.md "Track levels"; since omnibus17, before which trigger routes had their own 0..1 knob applied in `#deliver_trigger`): `level :pump, 0` turns it off, and the track's name stands for it where a knob is meant (`turn :pump, 0`, scenes `pump: 0`; the resolution rule in arrangement.md, "Names that stand for controls").  Template bus steps keyed by `:sidechain` (`[:duck, :sidechain, { amount: -6.db }]`, `Template#bus_chain`) read the template's sidechain, so dnb's :hall follows `sidechain :pump, :pump` (maintainer: "follow the pump").  `Session#trigger_tracks`, `#trigger_track?`, `#bus_readers_of` (source => reader names, for `sidechains`).  Details and measurements in dynamics.md ("Trigger tracks").

## Pre-fader readers and key levels (session-2, 2026-10-31)

The maintainer's decisions (2026-10-30, "Pre-fader"; 2026-10-31, "Pre-fader; separate duck level control" and "Add them"):
- **Readers hear players pre-fader**: `duck(:kick)`/`bus(:kick)` read a player after its fades and before its level (omnibus17 had moved the tap to fade times level, so pulling a kick's fader down weakened the duck), mute, and solo.  A trigger track keeps its level in the tap, since that is its only fader (`level :pump, 0` turns a pump off).  `only:` readers read the node itself, before the track's fade too, as before.
- **Key levels**: each player name has a key level, the Session knob `:"kick/key"` (`Session::Name::KEY`, a reserved leaf like `level`; a linear gain `0..4` like levels, made at unity when first set: `key_level :kick, -6.db`, `turn :"kick/key", 0.5`, scene and section values `"kick/key": 0`, all launch points and ramps), how hard the player drives every reader of its name, `only:` readers included.  It multiplies the readers' signal on exact frames (`Faders#reader_levels`: fade, a trigger's fader, key; `#key_fader_levels` in `Buses#bus_only_write`), independent of the fader and fade.  A session that never sets one makes no knob and renders as before.  Spelled as a track knob rather than a reader-side option (`duck(:kick, key: 0.5)`) so one turn moves every reader of the track, scenes and `learn` reach it, and set documents save it like levels; `duck`'s `amount:` stays the reader's depth.
- **Crossfading players add up**: `only:` spies add into the reader's signal (zeroed at each span's first use) instead of copying, so two same-named graphs playing at once (a crossfade's old and new kits) both key the reader.  A single player's reads never overlap, so its samples are unchanged (0 + x).
- Sound: no shipped song sets track levels or key levels, so none moves (golden and the genre pumps are unchanged).  Specs: `faders_spec.rb` (pre-fader, key levels on exact frames at any buffer size, `only:` key levels, crossfade sums, scene names); SessionFuzz draws a key level, a pulled fader, and a crossfaded kit for a ducked part's source.

## Chains that read ahead (fix-bus-resample-1, 2026-11-08)

Found by the Linux session converting one of his songs from .acd: a drum bus with `sig.resample(96000).filter(:lowpass, cutoff: tween(...), quality: tween(...)).resample(48000)` came out 66.6 ms late against the bass ("a gallop").  Measured on master-ai 026d2fe1 (a click at frame 24000 through `resample(96000).resample(48000)`): bus and master chains and a bus tap read through the pair played it 1600 frames late at 800-frame buffers and 734 at 367 (two buffers), and a click in the first buffer three times (at its frame, one buffer later, two buffers later); the same pair on a track or in a bare graph, 0 frames.  `resample(44100).resample(48000)` and a filter between moved it by a few frames only.
- Cause: libsamplerate reads ahead of its output (its sinc filter's half length: 145 input frames upsampling 48 to 96 kHz, 286 at 96 kHz downsampling, measured by `Resample.lookahead`), and its callback asked for a whole buffer each time it needed a few frames.  A track's sources can be pulled early, so the track isn't late.  A chain's `MixSource` handed every whole-buffer read the same span buffer again (a bus tap read zeros past the span), so each resampler's priming read repeated the first buffer and slipped the stream by a buffer.  A Tee whose branches diverged also read its source a whole request ahead.
- Fix: nodes that read ahead say how far (`#read_ahead`, frames at their source's rate, at any buffer size: `Resample` libsamplerate's lookahead + 18, the Ruby interpolators 2, `BufferAdapter` its block less one), `GraphNode::ReadAhead.frames` sums them along each path from a chain's outputs to its span-fed source (through rate changes; paths not reaching it don't count), and the source starts that many frames late: `MixSource#read_ahead` (a FIFO; set in `build_master`, so bus, master, and stem chains), `BusTap#read_ahead` (set in `bind_bus_taps` from the graph reading it).  A read past the written frames raises (a node reading ahead without saying so) instead of repeating a buffer.  `Resample`'s libsamplerate callback asks for what the read consumes plus the lookahead (at least 2 frames: the linear converter gave wrong samples fed one frame at a time, reading the frame before a one-frame block: an invalid read under memcheck from `Resample.lookahead`'s one-frame feeding, batch 22; since fix-batch22 `FastResample` copies each block after the previous block's last frame, so libsamplerate never holds a pointer into an upstream buffer and one-frame blocks are exact, `fast_resample_spec.rb` "blocks given to libsamplerate"), then 16 at a time; output is bit-identical to big-chunk reads at any read size (all four converters, ratios 2, 0.5, 2.8, 0.919).  Tees read only the frames a branch lacks.
- Latency (chains whose resamplers were given a libsamplerate or Ruby mode, live and in renders; offline renders of resamplers given no mode too until resample-render-minphase): a chain hears its input `Chain#latency` frames late (`buses` shows "315 frames late" for the best-sinc pair: 6.6 ms; measured: `resample(44100).resample(48000)` 351, the oversample region `resample(96000).lp4(9000).oversample(2).resample(48000)` 391, `:libsamplerate_fastest` pairs 67, libsamplerate linear and zoh pairs 27, Ruby-mode pairs 3; each libsamplerate resampler's 18-frame rounding margin is part of it), the same at any buffer size; a track playing the same graph isn't late.  Compensating it (PDC, live and renders) is a later project (maintainer, 2026-11-08); with PDC, renders could return to best sinc.
- Chains use `:min_phase`, live and in renders (the maintainer, 2026-11-08: "Use a minimum phase resampler for zero latency when live; FIFO fix now; PDC later for live and renders"; then, asked "Should renders also use :min_phase until PDC?" and "Is the mode name :min_phase OK?": "1 yes, 2 yes"; resample-render-minphase): `build_master` (bus, master, stem chains) and `bind_bus_taps` (graphs reading a tap) call `ReadAhead.prepare`, which switches every resampler on a path to the span-fed source that was given no `mode:` and hasn't started to `:min_phase` (`ReadAhead.use_min_phase`), then measures what still reads ahead (`ReadAhead.frames`).  `:min_phase` reads nothing ahead, so the chain's latency is 0 and its samples are the same graph's on a track with `:min_phase` given.  One rule for realtime and offline Sessions, so a chain rendered offline is bit-identical to the same chain live (spec; before, renders kept `:libsamplerate_best` and a bus pair came out 315 frames late).  A resampler given a mode keeps it; resamplers on tracks and in bare graphs keep the default (they can read ahead).  `:min_phase` itself: graph_nodes.md "Resampling modes".
- MixSource channels keep frames a read leaves for the next read (a `:min_phase` resampler reads just what its output covers, a frame behind the span now and then: before, the frames were dropped at the next write, 2.2 dB off a 44.1 kHz round trip), and a channel nothing read since the last write drops all but its last `read_ahead` frames (chains that don't read the mix, or skip a buffer).  Bus taps address the source by session frame (the span's frames plus `read_ahead` + 256 frames before them), so a graph whose reads lag or lead a little continues where it left off, and one starting or waking reads from its own frame as before.
- Taps whose graphs read ahead get every span (fix-batch22, found by batch 22's SLOW=1 suite: `with_buffer(300)` after a tap at 128/801/7-frame buffers came out -0.0 dB from the track): such a graph doesn't read in every span (the BufferAdapter's block covers several 7-frame spans), and a tap only added a span to its history when read, so after a skipped span it reset the history and the next block read those frames as silence.  A tap with `read_ahead` registers on its first read (`BusTap#keep_spans` -> `Session#keep_tap_spans`); after each routed span the Session calls `BusTap#catch_up`, which keeps the span in every channel no read kept, and drops the tap once no channel has been read for `read_ahead + KEEP` frames (its graph stopped or sleeps; a read registers it again).  Regression examples in `read_ahead_spec.rb` ("a tap read through a BufferAdapter").
- Also found: a chain or a routed player whose output was DFloat (the Ruby-mode resamplers) played silence (`o[r].inplace + d` with an SFloat view makes a new array); chain outputs, routed players, triggers, and CUE now cast to SFloat.
- Guards: `spec/lib/mb/sound/graph_node/read_ahead_spec.rb` (`spec/support/read_ahead_sweep.rb`: 11 chains, every resampler mode, a 44.1 kHz round trip, a filter between, an oversample region, a BufferAdapter, a dry path beside a resampled one, each as a bus, master, and tap chain against the track at 800, 367, and 128/801/7 frames (slow tier), equal to the track (for chains given no mode, `TWINS`: the same chain with `:min_phase` given) `latency` frames later within -80 dB, `ZERO_LATENCY` chains declaring 0 (since resample-render-minphase; live and offline Sessions switching alike, and a bus chain live and offline bit for bit, are examples there) (measured: bit-identical, the 44.1 kHz round trip within 3.6e-7), the latency the same at every size; a guard fails for a new class with `#read_ahead` the sweep doesn't build), and a SessionFuzz command (an oversampled `:ovs` bus fed by a melodic part, sometimes read through a tap; :buffer_size fails on the old code).
