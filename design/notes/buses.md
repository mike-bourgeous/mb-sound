# Buses, sends, and bus sidechains

Branch buses-1 (2026-10-13).  The maintainer queued "Buses, sends, bus sidechain" (persona consensus B; Kez Volta asked for `duck(:drums, only: :kick)`; earlier: longer delay and reverb tails should come through "future effect sends" rather than delay discovery).  CLAUDE.md keeps a summary and points here.  Update both when behavior changes.

## API

```ruby
bus(:verb) { |sig| sig.reverb(:hall, mix: 1) }        # a named bus: its own effect chain, into the master
bus(:slap, to: :verb) { |sig| sig.delay(1.n8) }       # into another bus (no loops)
bus(:drums) { |sig| sig.compress(threshold: -18.db) } # the same kind of bus, used as a group
track(:keys, send: { verb: -12.db }) { |c| ... }      # sends (post-fader), per player name
track(:kick, to: :drums) { |k| tr808(k) }             # the track's main out goes into a bus
bg :pad, graph, send: { verb: -6.db, slap: :space }   # bg too; a knob name follows the knob
feed :keys, :verb, -6.db, over: 2, on: :bar           # change a send (journaled, undoable)
feed :keys, :verb, 0                                  # off
bass.duck(:drums)                                     # sidechain from a bus or a track
bass.duck(:drums, only: :kick)                        # one named node inside a track's graph
pad.compress(sidechain: bus(:drums))                  # bus(:name) reads a bus or track anywhere
master { |mix| mix.duck(:kick_bus) }                  # master chains read them too
mute :verb; solo :verb                                # buses are strip names
buses; routes                                         # listings
render('x.flac', stems: 'stems/') { ... }             # one stem per bus too
```

## Decisions (agent's, open to the maintainer's review)

- **One concept** (maintainer, 2026-10-18: "bus and send should be the same thing unlike in some DAWs"): a bus is a named chain; a player reaches it with a level (`send:`, `feed`) or with all of its sound (`to:`).  There are no aux, return, or group kinds: the routing tree, the buses pane, and the meters (`Snapshot#bus_levels`, `#send_levels`, terminal_ui.md "UI round 4") show one kind of bus with its sends and sources.

- **Names.** Buses share the Session namespace with tracks, groups, and knobs (`Names#claim(name, :bus)`), so a bus can't be named like a track; `:master` stays reserved.  `send` is `Object#send` (every object, used all over the library), so the console command is `feed` (aliases `send_level`, `fx_send`; maintainer 2026-10-13: keep `feed`, add `fx_send`); `send:` stays the keyword on `track`/`bg`.
- **The bus is a master-like chain with its own input.** A bus reuses `Session::Master`'s chain machinery (`Chain`, `build_master`, spill/fade/cut handover): the block gets the bus input as a bundle (one parameter) or per channel, `bus :verb { ... }` again swaps the chain at a launch point with the old one spilling over (or `fade:`), and undo rebuilds the previous chain from its block (`:bus` changes, `BusState`).  Bus chains are installed as plans like players (`Plan.install`): the `MixSource` channels are boundaries, the chain behind them fuses.
- **Routing belongs to names**, like mute flags: a graph replacing `:keys` keeps its sends.  Each player has a main out (the master, or a bus with `to:`) and any number of sends.  Sends are post-fader: after the fade ramps and mute/solo (contract K7's order: fade, gain, mute/solo, then routes), so a muted or faded track sends nothing, and a ringing-out track keeps sending its tail.  Armed monitors (`:"lead/live"`) use their track's routes.
- **Send levels** are linear gains (`-12.db` reads as its gain) or a knob (a name or `knob(:x)`) to follow.  Internally each send is an unregistered `GraphNode::Knob` advanced with the Session's knobs, so ramps land on exact frames at any buffer size, `over:` takes bars, Durations, or Lengths with any `curve:`, and undo restores the level the same way knob turns do.  Ramps are linear in gain, like every fade.  `feed` lands right away (with the knob glide) unless given a launch point.  Negative numbers raise (write `-6.db`).
- **Order.** Each span renders players and buses in dependency order: a player before the buses it feeds, a bus before the bus it feeds, any source before a graph that reads it (`bus(:x)`, `duck(:x)`).  Ranks come from the longest path; equal ranks keep the existing order, so sessions without buses or readers render exactly as before (the same summation order).  A cycle goes through `live_error` when it is made (`bus`, `track`, `bg`, a reader added) and is broken at render time (the reader gets silence) if one appears anyway.
- **Readers** (`GraphNode::BusTap`): `bus(:name)` is a bundle of the Session's channels; `bus(:name, only: :kick)` is mono.  They read the current span's signal of their source: a bus's output (before its mute), a player name's output (after its fades, before its mute, solo, and routing), or with `only:` a node inside the named track's graph (a drum `Voice` named like it, or a node given `.named(:kick)`), read through a spy as the track renders (before the track's fade and mute: it's the voice itself).  Exact at any buffer size (the source renders first in the same span).  A source that something reads keeps rendering while muted or not soloed, so soloing a ducked bass keeps it pumping (its muted kick's CPU stays spent while read; found by tunnel_vision_spec, which solos the Reese).  A reader outside a Session reads silence.  Readers are plan boundaries for now.
- **Mute and solo** (maintainer, 2026-10-13: yes, solo-in-place, and sidechain sources keep feeding readers when muted). A muted bus sleeps (its senders' sends are dropped, their direct sound is untouched).  Solo is solo-in-place through the routing: a soloed track keeps the buses it feeds audible (so its reverb stays), and a soloed bus keeps the tracks feeding it audible (dry too: a track's sends and main out are one strip).  Tracks sending to the same bus that aren't soloed are silent as usual.
- **Tails and sleep.** A bus processes while anything is sent to it and rings out after its senders stop, sleep, or ring out, so delays and reverbs on buses finish on their own (no delay discovery).  It sleeps once its input and output have both stayed below `Master::TAIL_THRESHOLD` (-90 dB) for `TAIL_QUIET_SECONDS` (1 s), checked on the 800-frame session grid (`Synth::SKIP_GRID`), and wakes on the exact frame its input reaches the threshold, so output and CPU decisions are the same at any buffer size.  No cap: a frozen reverb rings until muted.  `render` keeps rendering after the last player until buses and master chains are quiet (as before, at most `MAX_TAIL_SECONDS`).
- Bus chains for stem copies are built on the render thread inside `Session.with_context(session: self)`, so blocks that call console commands such as `knob(:x)` find the rendering Session (round 3 found `No knob :lift` from a stems render).
- **Stems** (maintainer, 2026-10-13: "Use final versions of stems through all non-mastering processing"): a track's stem is the track as heard before the master chain: its main out if that goes to the master, plus its own share of every bus it sends or plays into, rendered by its own copy of each bus it reaches (`Buses#stem_shadow`: a chain built from the bus's block, fed only by that track, following the bus's chain swaps and mute, routed through its own copies of downstream buses).  So stems sum to the pre-master mix (exactly for buses linear in their input, like delays, reverbs, and ducks by a sidechain; up to the nonlinearity of compressors and clippers on buses), and nothing counts twice.  `render(stems:, bus_stems: true)` also writes each bus's output ("<bus>.flac").  Costs a copy of each bus per sending track, in stems renders only.
- **The master gain** applies to the sum of players' main outs and bus outputs (pre-chain by default), as before.

## Measurements

CPU per 800-frame stereo buffer (2026-10-13, Linux desktop, no YJIT, median of 600 after 60 warm-up buffers, two rounds agreeing within 5%; `/tmp/buses-1/bench.rb` in the branch report): 16 constant players 120 us; the same sending to one passthrough bus 209 us (~5.5 us per send: one multiply-add per channel); routed `to:` a passthrough bus 133 us; plus four asleep reverb buses nothing is sent to 101 us (asleep buses cost nothing, and the routed path's in-place adds are a little faster than the plain mix); 16 noise players each with their own `:hall` 1543 us vs sending to one `:hall` bus 544 us (the point of buses); a pad ducked by `duck(:drums, only: :kick)` 253 us vs the same pad ducked by a ghost kick 290 us (the reader replaces a second kick voice).  Worst case per send stays one vector multiply-add per channel per buffer; a bus costs its chain while awake and nothing asleep.

Plans: bus chains are planned regions (installed like players' graphs; their `MixSource` input is the region boundary); readers (`BusTap`) are boundaries for now, so a `duck(:drums)` fuses with its sidechain as a boundary input, as before.

Demo: `bin/songs/tunnel_vision.rb` (buses by default, `--no-buses` for Kez's original; round 2: the :hall return gain `-H` dB, after "Buses, way more hall (-30dBFS or more?)"; round 3: +18 dB by default, the maintainer's pick ("18 sounds right during the notes"), the return at about -35 dBFS RMS in the breakdown with the breakdown at the original's -9.1 LUFS; a `:lift` knob (`-U`; on by default since patches-5, the maintainer's pick, with the lifted return 6 dB down, so +12 dB, "With the lift I might take the wet mix down 6dB or so"; lift 0 is round 3's +18 dB return) blends in an upward compressor on the return that lifts the hall's decaying tail (+6..+12 dB in the outro's thin bars; the breakdown's sustained pad keeps it above the threshold); small hall sends from the drums, Reese, neuro, boom, and riser, with the hall input highpassed at 250 Hz so the kick's body stays out; the pullup riser that plays on after the others ring out is Kez's arrangement, identical in both versions): the pad and liquid pluck dry, sending to a `:hall` bus ducked by the kick and an `:echo` bus (the `:space` knob is its send), and the basses ducked by the drums' own kick voice.  Same loudness as the original (-7.5 LUFS); the drop nulls to -44 dB against the ghost-kick version.  Renders and bench set: `/app/tmp/listening/buses-1/`.

## Shared nodes (fixes-13, 2026-10-14)

A bus chain may share nodes with players (`lfo = 3.hz.lfo; bg :a, lfo * 0.5; bus(:fx) { |sig| sig * (lfo * 0.5 + 1) }`), like master chains since fixes-12 (`master_effects.md`).  Bus chains run in segments of a span (split on the sleep grid), sleep while nothing is sent or while muted, and a chain may start in a later segment, so each part of the bookkeeping applies:
- Every non-bypass bus chain (stem copies' too) is a Session graph for `Strip#span_graphs` (`Buses#bus_chain_graphs`), so a muted player sharing a node only with a bus chain still reads its branch.
- `:bus` changes (a new bus or chain, an undo's restore) carry the chain's `ChainGraph`, and chains landed but not started are waiting graphs for `Strip#catch_up_waiting`: their shared branches skip to the Tees' leaders at the start of every span.
- `Buses#bus_read_shared` keeps `Chain#read_to` (the session frame a chain read its shared branches up to): before each segment the chains read the frames they missed (asleep before waking, or before starting in this span) on their shared branches only, and after the last segment the frames they slept through (falling asleep on the grid, a mute ramp's end, asleep all span), like a sleeping player's `read_while_asleep`.  The chains' own nodes still sleep.
- Stem copies (`#stem_shadow`) are made at the start of the span, before players render (`#prepare_stem_shadows`, for the same sends `#deliver_player` used to make them for), so their new branches start on the span's first frame.

Measured on master-ai b6b06139 (mono, 120 bpm, 128/801/7, 800, and 7-frame buffers): a chain queued 0.3 s ahead read the LFO 0.155-0.176 off, 1.5 s raised `BranchBufferOverflow`; a sleeping bus waking after 1.5 s, a muted bus unmuted, a muted sender sharing the LFO only with the bus, a replacement chain while the old one spilled over, and an undo back to an LFO chain all raised; a track's stem copy read the LFO a span ahead (0.039 off in a 0.25 stem).  After: within 1.2e-7 everywhere (`buses_spec` 'nodes shared with players', 9 examples, all failing before).  Cost: 16 players sending to one bus with four asleep reverb buses, 800-frame stereo buffers, 311/320 us vs master-ai 307/308 (alternating, within noise).

## Key tracks (duck-keys, 2026-10-18)

A key route (`route(name, key: true)`, made by `sidechain :pump, clip` or `track(..., key: true)`) is a player name whose sound goes only to its readers: no main out, sends, stems, CUE, or meters; `to:`/`send:`/`feed` raise.  Readers read it like any source (before its mute; it keeps rendering while read), and any key route turns on the routed render.  `Session#key_tracks`, `#key_track?`, `#bus_readers_of` (source => reader names, for `sidechains`).  Details and measurements in dynamics.md ("Key tracks").
