# Audio I/O

Detailed notes moved from CLAUDE.md (2026-10-10); CLAUDE.md keeps a summary and points here.  Update both when behavior changes.


Device I/O goes through miniaudio (the old JackFFI, Jack/Alsa outputs and inputs, and the mb-sound-jackffi gem are gone; ffmpeg stays for files and ffmpeg outputs).  `OUTPUT_TYPE`/`INPUT_TYPE` are `device` (default), `ffmpeg` (output only), or `null`; unknown types raise.  `MB::Sound::DeviceOutput` (`lib/mb/sound/device_output.rb`) writes into a lock-free ring that a C callback on miniaudio's device thread drains (`FastAudio::Playback`); Ruby never runs on the audio thread.  `#write` keeps at most `AUDIO_LATENCY` seconds queued: a write that doesn't fit queues what fits and waits without the GVL until the rest fits, so the sound card's clock paces the Session one buffer at a time, with evenly spaced writes (and live MIDI reads) and the queue within about a period of full (2026-10-04, JACK dummy, period 128: `:default` write spacing 10.67 ms, sd 0.3 ms).  `MB::Sound::DeviceInput` (`lib/mb/sound/device_input.rb`, `INPUT_DEVICE`) records through `FastAudio::Capture`: `#read` waits without the GVL, skips the oldest audio beyond the queue limit so live input stays near real time, and resamples from the card's rate; `test_pattern: true` records a frame counter on the null device for specs.

Latency profiles (`DeviceOutput::PROFILES`, `AUDIO_PROFILE` or `profile:`; chosen with `bin/audio_load_check.rb` on the user's old Mac; rerun it after big performance changes): `:default` write 512 / period 128 / queue 50 ms (45-56 ms, clean with fm_bass and stereo_drone together), `:low` 256 / 128 / two writes (16-19 ms, light patches only), `:video` 400 / 128 / 50 ms (120 fps frames; 8-10 points more load, so 512 stays the default per the user), `:safe` 800 / miniaudio's default period (`period: nil`, 10 ms = 480 frames at 48 kHz) / 85 ms (about 110 ms; 60 fps frames).  `AUDIO_BUFFER`, `AUDIO_PERIOD`, and `AUDIO_LATENCY` override a profile; offline renders take `render(buffer_size:)`.  The queue is adaptive: it grows by half after dropouts, up to the `:safe` queue, and shrinks by a third back to the profile's after `DeviceOutput::SHRINK_AFTER` (10) seconds without dropouts (notes on stderr; `AUDIO_ADAPTIVE=0` disables).  `latency :low` (alias `lag`) restarts the background session on a device output with that profile.  Effect/synth/song scripts take `-L/--latency-profile` and a `profile:` keyword (`-L` wins, then `AUDIO_PROFILE`, then the script's default) and call `MB::Sound.warm_up` before live playback (synths: `warm_up(midi: true)`).  Live MIDI switches to `:low` (user decision, 2026-10-04): opening it (console `midi`, synth scripts, effect MIDI controls) calls `live_midi_latency`, which restarts the idle background session on a `:low` device output unless `AUDIO_PROFILE` is set or the user gave `latency`/`use_output` an output (`Session.output_chosen?`); not for ffmpeg/null outputs; with players or master effects it prints a `latency :low` hint instead.  Exact MIDI timing's latency follows the adaptive queue (console live sources follow output switches through `LiveSource#output=`).

Environment: `AUDIO_BACKEND` (e.g. `jack,pulseaudio`; on Linux JACK first only if a JACK server answers (including PipeWire's), then PulseAudio/PipeWire, then ALSA; CoreAudio on macOS; `null` is miniaudio's timer-driven fake sound card, used by the specs), `OUTPUT_DEVICE`/`DEVICE` (index or part of a name), `AUDIO_SAMPLE_RATE` (the rate written, 48000 by default), `JACK_CLIENT_NAME` (default: the script's name; also the PulseAudio/PipeWire application name).  Mono outputs open two channels.  Sample rates (user's choice): graphs and Sessions stay at 48 kHz, and when the card runs at another rate (e.g. 44.1 kHz on the Mac after jackd changed it) the writer resamples the mix with libsamplerate (`AUDIO_RESAMPLE`/`resample:` fastest sinc by default, ~0.8% CPU for stereo; medium, best, linear, zoh, or off to run at the card's rate); `#sample_rate` is the written rate, `#device_rate` the card's; `AUDIO_DEVICE_RATE` forces a card rate (specs use it with the null device); `AUDIO_SET_DEVICE_RATE=1` lets CoreAudio switch the card's system-wide rate.  `Session#sample_rate` is the output's; `Session#add` sets graphs at another rate to it, or resamples nodes that can't change rate (file inputs, raw Biquads); filenames open at it.  Most filters have `sample_rate=` (FirstOrder, Butterworth, HilbertIIR, FIR from a gain Hash, Gain, FilterBank, envelope followers; `spec/lib/mb/sound/filter/sample_rate_setters_spec.rb`), and DSL methods use the node's rate.

JACK has its own small backend instead of miniaudio's and RtMidi's (user requirement, 2026-10-04: every port of a script on one JACK/PipeWire node, added at any time, for their qpwgraph arrangement feature): `ext/mb/sound/fast_audio/mb_jack.c` loads libjack at run time and keeps one client per process; units (a port set plus a realtime process function) attach and detach at any time through an atomically swapped list, detaching after every cycle that might hold the old list has finished.  `Playback.new`/`Capture.new` take optional JACK port names (14th/11th argument) and reuse their rings, resampler, and adaptive queue on JACK's thread; `FastAudio::JackMIDIInput`/`JackMIDIOutput` are byte rings of [JACK frame time, bytes] records.  Ruby side: `MB::Sound::Jack` (`lib/mb/sound/jack.rb`; port names `out_N`, `in_N`, `midi_in`/`midi_in_2`, numbered after those in use; the user's old JackFFI is a reference for structure, not a spec); `DeviceOutput`/`DeviceInput`/`MIDI::Input`/`MIDI::Output` use it whenever JACK leads the backends and fall back to the next backend if it can't open.  JACK servers are never started; new audio ports are connected once (to the physical ports, to ports whose names contain `OUTPUT_DEVICE`/`INPUT_DEVICE`, or nowhere with `none`), and later rewiring by qjackctl/qpwgraph/session managers is left alone.  `FastAudio.jack_connect`/`jack_disconnect` wait (up to 200 ms) until JACK's graph shows the change (otherwise connections are listed late and first messages lost).  Specs: `spec/ext/mb/sound/fast_audio_jack_spec.rb`, `spec/lib/mb/sound/jack_spec.rb` (one-node acceptance test, sample-exact loopbacks).

Removing ports (2026-10-12, branch jack-crash): libjack (jackd2 1.9.22) can't unregister a port of an active client safely.  `jack_port_unregister` erases the port from the client's `std::list` on the caller's thread while the client's notification thread may be walking that list in `JackClient::HandleLatencyCallback` (the server sends latency notifications to every client after any graph change anywhere), which then reads the freed node.  A `spec:parallel` worker segfaulted there (runner osc-env-1-1; symbolized with the Debian debug file from debuginfod: `HandleLatencyCallback`, JackClient.cpp:354); JACK2 issue #216 has the same backtrace, and JACK's maintainer answers "deactivate before unregistering".  A C reproduction (one port unregistered and re-registered every 0-3 ms while another client connects and disconnects it) crashed about once a minute; with `jack_deactivate` before each unregister it didn't (reproduction, scripts, and rates: branch `research-jack-crash`, 8a9d0048).  So `mb_jack_detach` releases ports instead of unregistering them: disconnected, renamed `spare_<audio|midi>_<in|out>_<n>`, and kept; `mb_jack_register` reuses a spare of the same kind (renamed with `jack_port_rename`) before registering a new port.  Once no unit holds a port, spares are unregistered between `jack_deactivate` (which returns only after a notification in progress has been answered; inactive clients skip latency notifications) and `jack_activate`, which interrupts nothing; `jack_client_close` deactivates first anyway.  So while other ports are open, closed ports show in qjackctl/qpwgraph as disconnected spares (at most the peak number of ports of each kind).  Registering ports while active stays (a `push_back` that the walk tolerates).  RtMidi's JACK clients (specs' outside clients) get the same treatment: `fast_midi`'s `mb_rtmidi_jack_release` deactivates before their port goes (`rtmidi_build.cpp` compiles the unmodified `RtMidi.cpp` with that helper).  Specs: `spec/ext/mb/sound/jack_port_teardown_spec.rb` (spares; `--tag jack_stress` with `JACK_STRESS_SECONDS` for long churn runs).

Reopening under a stalled server (omnibus9, 2026-10-18): live_source_spec's JACK group failed on the Mac VM under parallel specs when a starved first attempt closed the shared client and the reopen hit "Could not activate the JACK client".  Reproduced here by stopping jackd (SIGSTOP from another process: the open holds the GVL) for 0.3, 1.5, and 4 s during a reopen: "Could not connect to a JACK server" at once every time.  `mb_jack_open` now retries for up to 3 s (`MB_JACK_OPEN_RETRY_NS`; pauses from 20 ms doubling to 250 ms) when a server answered before in this process or the client opened but couldn't activate; without a server ever reached it still fails at once, so backends without JACK fall through quickly.  The retry sleeps holding the GVL (only on that failure path).  0.3 and 1.5 s stalls now reopen (0.28/1.48 s); 4 s still fails after 3.95 s.  Spec: jack_spec's stalled-server reopen (failed before with the connect error).  The JACK spec group's retry no longer `warn`s (the warning guard failed every retried example): it records each retry in the example's metadata (`:jack_retries`) and the formatter output.

Late clients (2026-10-13, branch jack-flake-1): an asynchronous JACK server (jackd2's default; `--sync` makes it wait) starts every cycle on time even when a client hasn't finished the last one (`JackEngine::Process` reruns the current graph), so a client thread that isn't scheduled for more than a period misses cycles (whatever another client's output port held in them is gone: the sender's next cycle overwrites it) or is called twice for one server cycle, reading the same port buffers at the same frame time.  Measured with a receiver stalled 12 ms every 7th callback (`JackMIDIInput#stall`, for specs) and 1280 messages from an RtMidi client: 330 lost and 157 duplicated before; the C input now drops a cycle with the last one's frame time and message fingerprint (`midi_in_process`, `stats[:repeated]`): 323 lost, 0 duplicated; with `--sync`, 0 and 0.  Lost messages can't be recovered.  `mb_jack.c` counts `:skipped_cycles`/`:repeated_cycles` in `Jack.info` (process thread: counters only), and `MIDI::Input#read_raw` warns once per process on the first repeat, suggesting `jackd --sync` or a lighter load.  libjack has no call that tells whether the server is synchronous, so `bin/midi_check.rb` can't hint at it.  Audio units too (jack-flake-2): a playback callback with the last cycle's frame time writes that cycle's period again from the ring instead of pulling a new one over it (JACK playback rings hold a period more than `max_queue` so it's still there; ring, device clock, and `#jack_clock` unchanged), and capture drops the repeat; both count it (`stats[:repeated]`, `#repeated`), and `DeviceOutput#write`/`DeviceInput#read` warn once per process (`Jack.warn_audio_repeats`).  Measured (async, the shared client stalled 12 ms every 7th callback, ramps to and from a forked outside client, 2 s): playback lost 12032 frames before, 0 after; capture duplicated 11520 before, 0 after (23040 lost to skipped cycles either way); normal callbacks cost the same within noise (about 3 us per 256-frame stereo callback).  Repeats reach the units whose frame-time read comes after the delay: a stall inside a unit after `process()` read the frame time shows up only as skips in `Jack.info` (`repeated_cycles: 0`) while later units see repeats, so the audio specs stall the whole client with `FastAudio.jack_stall(us, every)` (spec-only, at the very start of `process()`, before the frame-time read, like a thread that wasn't scheduled; one relaxed load per callback when off; cleared when the client opens), independent of unit order.  Capture dedupes on frame time alone (a real repeat reads the same port buffers; a fingerprint like MIDI's would cost a pass over the period every callback).  Untested on PipeWire's JACK (pipewire-jack isn't in the container, and the host's socket isn't mounted; maintainer's call, 2026-10-13).  Spec servers (`JackDummy`) run with `--sync` (`start(sync: false)` for async), which fixed input_spec's lost note-on flake; `spec/ext/mb/sound/jack_late_client_spec.rb` covers both modes.  Its async audio example allows only audio lost to lateness it can attribute (jack-spec-1, 2026-10-15): either client can be late on its own under load or Valgrind (cycles one client misses and the other runs; callbacks that run into the next cycle, which can read or write ports around the other client's next cycle, or have a unit see the next frame time and drop that cycle as a repeat), and Jack.info's counters can't tell those from shared skips (the fixes-9 allowance, the outside client's skips beyond ours, failed 5 of 6 Valgrind runs and 3 of 5 under 16 busy loops), so both clients log each callback's start and end frame times with the spec-only `FastAudio.jack_frame_log(true/false)` (one relaxed load per callback when off) and the example allows a period per lone missed cycle and per overrun (up to 20 periods measured under load or Valgrind, against 27-35 lost there and duplicated here without the dedupe).  Units still read the frame time themselves: caching process()'s read fixed the capture case but broke MIDI input's repeat detection after a stall inside its unit.

Tools and threads: `bin/latency_probe.rb` (latency_probe.md) tells system stalls (VM, OS) from Ruby's (GVL, GC, YJIT) and lines a Session's underruns up with them; `bin/audio_check.rb` lists devices and measures latency, underruns, clock drift, write spacing, and queue range (`--busy` adds GVL contention).  A busy Ruby thread can starve the writer for a whole time slice (100 ms by default, longer than the queue; 131 underruns in 10 s on the user's Mac), so bin/ scripts set `RUBY_THREAD_TIMESLICE=10` in their shebang (user's choice; 0 underruns measured; read only when Ruby starts, so `ruby bin/x.rb`, irb, and `fork_script` don't get it); a priority of -3 on the busy thread also works.  The Session render thread calls `FastAudio.boost_thread_priority` (user-interactive QoS on macOS via `pthread_set_qos_class_self_np`, no privileges; a no-op elsewhere).  `vis` shows each buffer when it reaches the speakers (now + `output.latency`).  `use_output(obj_or_type)` gives the background session another output (refuses while players run); `render` accepts an output object; `OUTPUT_TYPE=ffmpeg` is any live ffmpeg output (`OUTPUT_FORMAT`, default audiotoolbox on macOS and pulse elsewhere; `OUTPUT_CODEC`; `OUTPUT_DEVICE` as the name or URL; about 0.4 s latency), wrapped in `BackgroundOutput` (feeds paced silence so ffmpeg never runs dry; kept separate from FFMPEGOutput by choice).

## Underrun concealment (audio-safety-1, 2026-10-25)

Why: research-gvl-render (86ecf51c) recommended a safety net so a missed deadline isn't a click; the maintainer picked "repeat last grain", then (same day) changed it: a grain tied to the buffer size buzzes at its repetition rate (128 samples: 375-750 Hz), and any fixed grain buzzes at rate / length, so grains come from jittered positions in a longer history with jittered lengths, decaying over long gaps, with fixed-grain and fade-to-silence variants shown beside it.

Default: **repeat** (jittered grains; `Concealment::DEFAULT`) since omnibus13: the maintainer's Bench verdict on the audio-safety-1 set (2026-10-25) was that jittered grains won for house, ambient, and acid.  `AUDIO_CONCEAL=silence` / `conceal: :silence` is the old behavior; specs that count frames between nonzero samples through underruns pass it.

Design (`ext/mb/sound/fast_audio/mb_conceal.h`, run by `playback_pull` on miniaudio's device thread and JACK's process thread; Ruby reference `MB::Sound::Concealment::Reference`, compared within 1e-6 on the specs' synthetic ring states: same operations in the same order, measured identical on x86-64 GCC with fast_audio's unchanged flags):
- Every real frame the device plays goes into a history ring (the last 120 ms, ring of twice that so the crossfade back can push frames without overwriting what grains read; allocated at open, at the device's rate).  Normal pulls only copy into it.
- Entry (the pull the ring ran dry in): the first grain starts at the lag 20-30 ms back whose preceding 1 ms best matches the last 1 ms (least squares, early exit), and the remaining step is an offset decaying over 2 ms; no fade-in (the gap is already there).
- Grains: lengths drawn from 20-60 ms and start positions from anywhere in the history (counter-based splitmix64 of a seed and the draw count, so the same events give the same samples); each crossfades into the next over an equal-power (sine/cosine) seam as long as min(rest of this grain, half the next) allows, so at most two grains sound and there is no fixed period.  Equal power rather than Hann amplitude because grains from random positions are uncorrelated on average (a Hann sum dips 3 dB mid-seam); correlated material (two kick hits) can sum 3 dB over, so concealed samples, and the crossfade back, are clipped at the history's peak (or the real sample's, if louder).
- Decay: full level for `hold:` (100 ms, provisional; omnibus13, below), then -60 dB over `fade:` (1 s) then zeros; once the writer marked the end of its audio (`Playback#end_stream`, `DeviceOutput#end_stream`, called by `Session#close` after its render thread stops) a gap starting there isn't concealed and a running concealment falls 60 dB over `quiet_fade:` (20 ms).
- Return: when audio arrives, it fades in over 5 ms (equal power) while the grains continue and fade out; running dry again mid-return just continues the grains.  **Late audio is played, not dropped** (chosen over catching up): the ring's read position, `frames_played`, `jack_clock`, and underrun counting move exactly as before, so the Session clock, MIDI timing, adaptive queue, `bin/audio_check.rb`, and the latency probe's Session watch see the same numbers; the adaptive queue already absorbs the added latency.  Dropping late audio would desync `jack_clock`'s ring-to-JACK-frame map and lose notes' starts.
- JACK cycles an asynchronous server runs twice (`playback_jack_process`'s repeat path) keep the first call's port buffers when it concealed or crossfaded, since the ring doesn't hold that audio.
- Settings (`MB::Sound::Concealment.settings`): `DeviceOutput.new(conceal:)` / `AUDIO_CONCEAL` (`repeat` the grains and the default, `silence` the old behavior, `fixed` loops the latest grain for comparisons; `repeat:20-60` grain range in ms); a Hash overrides `grain:` (Range or one length; Lengths like `20.ms`, `128.samples`), `history:`, `hold:`, `fade:` (nil: no decay), `quiet_fade:`, `return_fade:`, `match:`, `search:`, `seed:`.  `Playback.new` without the 15th argument is silence.  `stats[:concealed]` (frames) and `[:concealed_gaps]`.
- `MB::Sound::Concealment.simulate(audio, gaps: [[start, length], ...], conceal:)` runs the C kernel over audio with forced gaps as a device would play it (for listening; the Bench set uses it).  `FastAudio::Concealer` is the kernel without a device (`#process`, `#state`, `#benchmark`).

## Monitor trim (help-1, 2026-10-13)

`Session.monitor_gain` (console `monitor_gain`/`monitor`, set by `help.level`) is a live-only listening gain on what monitored Sessions (realtime by default) and foreground `play` write to the output, after the master chain, limiter, and master gain; renders, stems, `rec_audio`, taps, and takes never see it, and over-full-scale peaks it causes are clipped with a warning.  Details in `help.md` (`Session::MonitorTrim`, `lib/mb/sound/session/monitor_trim.rb`).

## Closing at exit without keeping things alive (gc-leak-1, 2026-10-17)

Realtime Sessions, `DeviceOutput`s, and `BackgroundOutput`s are closed at exit (threads stopped, queues drained) through `MB::Sound::ExitClose` (`lib/mb/sound/exit_close.rb`): one `at_exit` hook for the process and an `ObjectSpace::WeakMap` of what it closes, latest first (a Session before the output it opened, as separate hooks did); `#close` unregisters.  Before, each Session that started its render thread registered `at_exit { close }`, and a block given to `at_exit` is a GC root: every such Session, closed or not, kept every graph it had played alive until exit.  play-1 made `play` Session-based, so a full spec run (seed 2300) ended with 12 Synths held by about ten closed Sessions, and `plan/installation_spec.rb`'s process-wide Synth count failed.  Rule (guarded by `spec/lib/mb/sound/exit_close_spec.rb`, which scans `lib/` for `at_exit` blocks): library code never captures objects in an `at_exit` block; register them with `ExitClose` (blocks that touch only module-level state, like `UI`'s band and tiles, are allowed with a reason).

## Sessions in specs: the virtual clock and the render budget (gc-leak-1 round 2, 2026-10-17)

A realtime Session on an unpaced `NullOutput` (`sleep: false`) renders as fast as it can while whoever waits on it sleeps by wall clock.  play-1's monitor_trim_spec "reaches foreground play" did that into an output subclass keeping every buffer: 6 s and ~0.8 GB alone, +3.5 GB in a parallel worker, and once 22 GB (that worker crawled for 30 minutes, and another worker's realtime JACK example timed out under the memory pressure).  A paced output (`sleep: true`, the default) behaves like a sound card but makes specs wait real time.  Maintainer decisions (2026-10-17), the convention in CLAUDE.md's spec conventions:

- Specs use `Session.new(realtime: false)` and `#process_buffer` unless a render thread is under test.
- Realtime cases use `NullOutput.new(..., sleep: :virtual)`: `#write` blocks once it is `ahead:` frames (default three buffers) past what `#consume(seconds)` has let through, so time moves as fast as the waiter consumes audio, memory stays bounded, and each check sees the same frames (`#consume` returns once the writer reached its limit; a one-second stall without writes returns as a safety net, not a clock).  `MB::Sound::Internal.wait_audio(session, seconds)` is the waiters' sleep: foreground `play`, `wait`, and take replays consume on a virtual output and sleep otherwise.  `Session#close` releases a blocked writer (`NullOutput#release_writer`) before joining the render thread.  Wall-clock pacing stays only where wall-clock timing is what's tested (`wait(timeout:)`, the UI painter's timing, typed keys in the tiles, a stuck scheduler thread, `null_output_spec`'s own pacing cases).
- A render budget (`spec/support/render_budget.rb`): unpaced NullOutputs (`sleep: false` or `:virtual`) may render `RenderBudget::DEFAULT_SECONDS` (60 s) of audio per example, all outputs and threads together; past it `NullOutput#write` raises `RenderBudget::Exceeded` (stopping a spinning render thread) and the example fails even if the raise was rescued.  Long offline renders say so with a reason (`render_budget: { seconds: 400, reason: 'whole form' }`; form_spec and take_spec have four, 64-384 s measured); `MB_SOUND_RENDER_BUDGET=report` lists the examples over budget at exit instead.
- `rake spec:parallel` reports examples whose RSS grew over 200 MB (`spec/support/rss_report.rb`, one `N.rss.json` per worker), next to the slow examples.

Lessons, as mechanisms: a spec's waiting must be tied to the audio it waits for (virtual clock, not wall clock) -> runaway render threads, wall-clock flakes; unbounded work becomes a failure, not a slow run (render budget) -> spinning Sessions, accidental minutes-long renders; memory growth gets a number per example (RSS report) -> leaks and buffer-keeping outputs found by the example that caused them rather than by whichever worker ran out.

A running default Session is process-wide state too: `play`/`bg` leave its render thread running (as the console wants), and a later example then shared it (midi_methods_spec's JACK example read nothing after channels_spec's `play`: a running realtime Session pumps its `MidiInput` from the render thread, so a graph sampled from the spec thread at its own positions never saw the note).  spec_helper closes it before each example when its thread is running, next to `close_outputs`.
