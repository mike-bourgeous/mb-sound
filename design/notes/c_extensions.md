# C Extensions (compiled via rake-compiler)

<!-- summary -->
25 C extensions under `ext/mb/sound/` (plus `ext/mb/fast_sound/` and mb-term's `fast_term`), each building `lib/mb/sound/<name>.so` (`rake compile`).  New C code goes in purpose-specific extensions, not `fast_sound`; shared helpers are `static inline` in `ext/mb/sound/include/mb_ext_helpers.h` and shared kernels in `ext/mb/sound/include/mb_*.h`.  Every kernel has a Ruby reference that specs compare with it (existing ones exact mirrors, several built with `-ffp-contract=off`; new ones may use a stated tolerance), registered in MB::Sound::Kernels (kernels.md).  `depend` files list each extension's headers (`rake depend:check`); a change to ext/ structure refreshes the memcheck map.  `rake memcheck`/`memcheck:changed` run their spec files in parallel Valgrind processes (`MEMCHECK_PARALLEL=N`; about 10 min for the full list at 8 on the Mac, estimated).
<!-- /summary -->

## Quick reference

- Build: `bundle exec rake compile` (`-j N`); after merges touching `ext/`, `rake clean compile`; after changing a `depend` file or removing a source, `rm -rf tmp/<platform>/<extension>`.
- Check: `rake depend:check`; `rake memcheck:changed` before merging ext/ work; `rake memcheck:map` (and commit the map) when the ext/ structure changes.
- New code in purpose-specific extensions; shared helpers `static inline` in `ext/mb/sound/include/mb_ext_helpers.h`; every kernel registered with its Ruby mirror in `MB::Sound::Kernels` (kernels.md).
- Clang on the Mac fails on unused static functions in `.c` files: check every one is still called.

Parallel builds (omnibus11, 2026-10-22): `rake compile` builds the extensions side by side (`compile:<platform>` is a multitask; rake's thread pool, `-j N`, default CPU count + 3; `MAKE_JOBS=N` adds make's own -j, worth ~10% more).  Mac i9 container, clean build: 81.6 s at `-j 1`, 21.4 s by default, 18.9 s with `MAKE_JOBS=4`.  rake-compiler builds inside `chdir(tmp) { sh make }`, which changes the process's directory; under `rake -m` another thread's relative `mkdir_p` then ran in the wrong directory (`Errno::EEXIST ... tmp/x86_64-linux/stage/lib/mb`, the reported `-j -m` crash), so the Rakefile's `ParallelExtensionBuild` (prepended to `Rake::ExtensionTask`) keeps that directory per thread and passes it as `sh(..., chdir:)`.  `rake -jm` is `-j m` (a thread count), not multitask.

New C code goes in purpose-specific extensions (the user's preference) rather than growing `fast_sound`; helpers shared between them (`mb_wrap`, `mb_ensure_inplace_sfloat`, `mb_read_signal_input` / `struct mb_signal` + `mb_signal_input`/`mb_signal_at`, `mb_finite_entry`, `mb_tan_pade` (libm-independent tan, mirrored by `FourPole.tan`), ...) are `static inline` in `ext/mb/sound/include/mb_ext_helpers.h`, added to the include path by each `extconf.rb`.  Each kernel has an exact Ruby mirror that specs compare sample for sample (keep the operations identical, including float32 reads of signal inputs), registered beside it in MB::Sound::Kernels (kernels.md, kernels-1, 2026-10-30): a new C function registers with its mirror (`Kernels.register :name, c: FastX.method(:f), ruby: ...`) or goes in `Kernels::UNMIRRORED` with a reason, lib/ calls it only from a `*_c` method or through the registry, and `kernels_guard_spec.rb` fails otherwise; `MB_SOUND_KERNELS=check` runs every kernel beside its mirror and compares them.  That holds for the existing kernels; new kernels may compare with their Ruby reference within a stated tolerance instead (maintainer, 2026-10-22, "Ears win": exactness where it is heard or a workflow needs it; `.claude/collaboration.md`).  Shared kernels (not just helpers) are `static inline` in `ext/mb/sound/include/mb_*.h` headers (`mb_svf.h`, `mb_envelope.h`, `mb_resonator.h`, ...), so the plan executor and loop programs run the same code as the node kernels.  `depend` files list an extension's headers (rake doesn't rebuild on header changes otherwise; `rake depend:check` and `spec/valgrind/memcheck_selection_spec.rb` compare them with the scanned includes); after changing `depend` or removing a source file, `rm -rf tmp/<platform>/<extension>` so the Makefile is regenerated.  A branch that adds a source, header, extension, `Fast*` module, or include, or changes a `depend` file, also refreshes the selective memcheck map (`rake -f Rakefile memcheck:map`, ~5 min natively) and commits `spec/valgrind/memcheck_map.json` with it: the map records the ext/ structure it knows, and `memcheck_selection_spec.rb` and `memcheck:changed` fail on a stale one (2026-10-18; the full `rake memcheck` is manual, before public releases or for leak hunts).

Parallel memcheck (memcheck-par-1, 2026-10-30; the maintainer chose parallel Valgrind processes over a sanitizer lane, review-2026-10 tests-gems.md A5 option b): Valgrind runs a process's threads one at a time, so one rspec under it uses one core (the full list took 53 min on 2026-10-16).  `spec/valgrind/memcheck_parallel.rb` (`MemcheckParallel`, called by the Rakefile's `run_memcheck`) splits the selected files into groups by their expected Valgrind times (longest first into the least loaded group, like `spec/parallel_specs.rb`) and runs each group as its own `valgrind ruby rspec` with its own ruby_memcheck Configuration (temp dir for the per-PID XML, loaded-features file, an output IO for its report); after every process ends, each group's XML goes through its own `TestTaskReporter` (the Rakefile's truncated-XML and undef filters still apply), errors print with the group's files, and the task fails (`MemcheckParallel::Failed`) on an rspec failure or a Valgrind error.  Logs: `tmp/memcheck/N.log` (progress and summary) and `N.err`; per-example times merged into `tmp/memcheck_times.json` (with a `processes` list: files, expected and measured seconds, peak memory).  Expected times live in the main checkout's `tmp/memcheck_file_times.json` (shared by every worktree like the full-run stamp; updated from the processes that passed, with the median per-process startup; seeded from the `tmp/memcheck_times.json` files; files without a time are estimated from native times times the median slowdown, else size).  Process count: `MEMCHECK_PARALLEL`, else the fewest within 10% of the best expected time, at most half the CPUs and one per 2.5 GB of MemAvailable.  A status line every minute (examples done, processes running, resident memory) and a line per process as it ends (time against expected, peak RSS of its process tree, sampled from /proc every 2 s).  The rspec command is built directly (RSpec's RakeTask runs its block only when invoked, so a pattern set there is ignored and the child runs the whole suite; Rake's options are an OpenStruct, a `:performance` warning), with a check that it names every file.  `memcheck_parallel_spec.rb` (normal suite) runs three groups through a stand-in Valgrind (a shell script writing XML, an invalid read for one group).  The runner is selection tooling (`TOOL_FILES`): changing it doesn't select the full list.
