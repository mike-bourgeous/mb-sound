# Latency probe (`fast_latency`, `MB::Sound::LatencyProbe`, `bin/latency_probe.rb`)

<!-- summary -->
`bin/latency_probe.rb -t 1h` / `MB::Sound::LatencyProbe.start(dir:)` tells system stalls from mb-sound's own: `FastLatency::Probe` is a pthread outside the GVL on an absolute-deadline 1 ms loop timing a memory walk and a CPU loop, with per-second aggregates, histograms, and stall episodes in C, drained through a lock-free ring by a Ruby consumer; a Ruby ticker sees GVL/GC/YJIT stalls too, and `#watch(session)` logs slow buffers and underruns.
Reports give percentiles, top stalls with wall times, periodicity (":59.9 of each minute"), Ruby stalls by cause, and plots; `MB_SOUND_LATENCY_PROBE=1` probes any live script.
<!-- /summary -->

Branch `latency-probe-1`, 2026-10-25.  The maintainer: "Before all else, build and merge a latency detector that uses a GVL-free C thread on a short wakeup loop to detect system stalls and passes data through a queue to another C thread that pulls the data into Ruby for storage and analysis. Incorporate whatever ideas the jit agent used for detecting system latency, and if necessary ask me questions and add your own understanding of the space to extend the feature set in ways we are likely to need. I want to be able to leave this running for, say, an hour or more and get a histogram and time plot of latencies, etc."  Then: "also track free memory, load average and/or CPU percentage, as metrics on the plots where useful."

Why: scene-jit-1 (2026-10-24, `design/notes/arrangement.md`, Transition compiling) found the Mac's Docker VM slows memory-touching work ~10x at the top of every wall-clock minute (:59.8-:00.8; its probe3.rb: 33 ms of work took 357 ms) while a CPU-only probe missed it, and container underruns couldn't be told apart from mb-sound's own stalls (YJIT compiles, GC, GVL holds).  A thread outside the GVL sees only the system; a Ruby thread in the same process sees the system plus the GVL, GC, and YJIT; the difference attributes each stall.

## Threads and the queue

- **Probe thread** (`FastLatency::Probe`, `ext/mb/sound/fast_latency/fast_latency.c`): a pthread that never touches Ruby.  Absolute deadlines every `period` (1 ms): `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME)` on Linux, `mach_wait_until` on macOS (mach absolute time converted with the timebase).  Each tick records its wake lateness and, optionally, times fixed work: a read-modify-write walk of `memory_touch` bytes (128 KiB, one byte per 64-byte line) cycling through a `memory` buffer (64 MiB, larger than the caches; allocated and touched on the Ruby thread before the probe starts), with the thread CPU time of that walk; and `cpu_iterations` (10000) of a dependent xorshift loop.  Deadlines that already passed count as missed ticks (the next deadline skips ahead), so a 300 ms stall is one late tick plus ~300 missed.
- **Baselines and stalls**: the medians of the first 256 ticks' work times are the baselines (`stats[:memory_base_ns]`, `:cpu_base_ns`); a tick's stall is the larger of its lateness and its work's excess over the baseline.  A tick is over the threshold when the lateness or an excess exceeds `threshold` (2 ms), or a work time exceeds `work_ratio` (5) times its baseline and is `work_min` (0.25 ms) longer: the VM's 10x memory slowdown of a ~30 µs walk is only ~0.3 ms of excess, so a pure time threshold would miss it.
- **Aggregates in C**: per CLOCK_REALTIME second (so minute boundaries are wall-clock ones) a record with ticks, missed, over, max/p50/p99 lateness, memory and CPU work (from per-second log-bucket histograms), the worst stall and its wall time, the thread's CPU time, voluntary and involuntary context switches (Linux `RUSAGE_THREAD`; -1 on macOS), CPU migrations and the last CPU (`sched_getcpu`; -1 on macOS); lifetime histograms of lateness, memory work, CPU work, and stall.  Ticks over the threshold become tick events (at most `events_per_second`, 100; the rest counted as dropped) and merge into **episodes** (over-threshold ticks with gaps up to `gap`, 100 ms, closed after 10 s at most): start wall/mono time (the missed deadline for late ticks), duration, ticks, over, missed, worst lateness/memory/CPU/stall, the worst tick's wall time and CPU.  Episodes are the unit the report counts and the periodicity detector reads.
- **Histogram buckets** (`FastLatency.bucket`, mirror `LatencyProbe::Histogram.bucket`, compared in `fast_latency_spec.rb`): one bucket per value under 16 ns, then 16 per power of two (each at most 1/16 of its value wide) up to 2^41 ns (~37 min), 608 buckets; percentiles report the middle of the first bucket whose running count reaches ceil(q n) (`FastLatency.percentile` = `Histogram.percentile`).
- **Ring**: a single-producer single-consumer ring of fixed records (4096 by default, a power of two; C11 atomics, release/acquire on head and tail).  A full ring drops the record and counts `overflow`; the probe never waits.  It wakes the consumer after a second or episode record (or past half full) only through `pthread_mutex_trylock` + `pthread_cond_signal`, which never block; a missed wake costs at most the consumer's 250 ms timeout.
- **Consumer**: "another C thread that pulls the data into Ruby" is done as a Ruby thread (`latency-consumer`) that waits in `Probe#wait` with the GVL released (`rb_thread_call_without_gvl` on the condition variable, with an unblock function so Thread#kill and #raise interrupt it), then `Probe#drain` copies the records into Hashes with the GVL.  A plain C thread can't create Ruby objects or take the GVL safely, so this is the safe form of the same design.  The consumer also files the Ruby ticker's and the Session watch's records, samples GC/YJIT/System once a wall second, and flushes files.
- **Ruby ticker** (`LatencyProbe::Ticker`, thread `latency-ticker`): the same absolute-deadline loop in Ruby (`sleep` to the next deadline, every `ruby_period`, 2 ms), so its lateness includes waiting for the GVL, GC, and YJIT compiles.  Per-second rows (Ruby `Histogram`) and events over the threshold through a Thread::Queue.
- **Session watch** (`LatencyProbe#watch(session)`, `SessionWatch`): a mix tap (`Session#add_tap`, on the render thread) counting buffers, the slowest render (`Session#render_load` x buffer duration), the longest gap between buffers, and underruns (outputs with `#underruns`, e.g. DeviceOutput) per second, with events for slow renders (over 0.8 of the buffer's duration), gaps (over twice the buffer plus the threshold), and each new underrun.

## Priorities

`boost: true` (default): macOS `THREAD_TIME_CONSTRAINT_POLICY` (period = the probe's period, computation half of it up to 50 ms, constraint = period, preemptible; no privileges needed), else user-interactive QoS; Linux `SCHED_FIFO` priority `rt_priority` (10), else `setpriority` on the thread's tid to `nice` (-10), else normal.  What was obtained (with the errors) is `stats[:priority]`, printed at start and in the report.  Until 2026-10-26 the Mac container ran as root without CAP_SYS_NICE ("normal (SCHED_FIFO 10: Operation not permitted; nice -10: Permission denied)"); both containers have CAP_SYS_NICE since then (checked 2026-10-30 in the Mac container: `CapEff` 0xa88425fb includes it, and `chrt -f 10` and `nice -n -5` succeed), so the probe gets `SCHED_FIFO` there now.  Optional `pin_cpu:` (Linux `pthread_setaffinity_np`) and `mlock:` (the work buffer and the ring).

## Per-second rows, files, memory bounds

`LatencyProbe::COLUMNS` (CSV order; times in ms): the probe's second (`late_*`, `mem_*`, `cpu_*`, `stall_max_ms`, `thread_cpu_ms`, `nivcsw`, `migrations`, `cpu`), the ticker's (`r_*`), GC deltas (`gc_count`, `gc_major`, `gc_ms` from `GC.stat[:time]`), YJIT compile ms (`RubyVM::YJIT.runtime_stats(:compile_time_ns)` deltas, with YJIT on), the session's (`s_*`), and `System::COLUMNS`: `mem_available_mb`, `mem_total_mb`, `load1`, `cpu_busy_pct`, `cpu_steal_pct`, `cpu_iowait_pct` (Linux `/proc/meminfo`, `/proc/loadavg`, `/proc/stat`), PSI `psi_cpu_some_ms`, `psi_mem_some_ms`, `psi_mem_full_ms`, `psi_io_some_ms` (ms stalled per second from `/proc/pressure/*` totals, when present), `major_faults`, `compact_stalls`, `swap_out` (`/proc/vmstat` deltas), `cpu_mhz` (mean of `/proc/cpuinfo`, every 5 s); on macOS `FastLatency.system_sample` (getloadavg, `HOST_CPU_LOAD_INFO` ticks, `host_statistics64` free + inactive + speculative + purgeable pages as available, `hw.memsize`, page-ins and swap-outs).  Read on the consumer thread, never the probe.  In a container, /proc shows the VM's whole machine (what matters for VM stalls).

Rows are filed 3 s after their second (every series has reported by then); seconds the probe never reported (a stall over a second) are filled with 0 ticks.  Memory: rows as Arrays for the last `keep_seconds` (24 h), event lists capped at `max_events` (100k; tick events 10k), the top 50 episodes kept apart, lifetime histograms in C.  With `dir:`, `seconds.csv` and `events.csv` get appended every `flush_every` (10 s), `histograms.json` rewritten, `meta.json` written at start and stop, so a crash keeps everything up to the last flush.

## Report

`LatencyProbe#report` / `Report#text`: run span, priority, wake clock, work probes and baselines; percentiles (p50 .. p99.99, max) and ticks at least 1/5/10/20/50/80 ms for wake lateness, memory work, CPU work, probe stall, the Ruby ticker, and session render (per-second max); episodes at least each limit; the top 10 episodes with wall times and second of the minute, plus the slowest memory work as a multiple of its baseline with its thread-CPU share (near 100%: the CPU or memory itself was slow; low: the thread was descheduled); periodicity; Ruby ticker stalls by cause (`:system` if probe episodes at the same time stalled at least a quarter as long (omnibus13: any overlap blamed a 300 ms GVL hold on a loaded machine's 20-50 ms episodes), else `:gc` if that second had GC time, else `:yjit` if YJIT compiled, else `:process`: a GVL hold or other in-process work); GC and YJIT totals; session buffers, slow renders, underruns, and what each session event was near (system / process / render); System means, minima, and maxima.

Periodicity (`LatencyProbe::Periodicity`, run by `Report#periodicity` on episodes of at least 20, 10, 5, 2 ms, then all, reporting the first size with a period: the soak below had a dozen 10-14 ms minute stalls among ~300 small episodes, which hid them from a test over all episodes): episodes' worst-tick times, merged within 1 s; for candidate periods (5 s .. 1 h) the densest phase window (5% of the period, at least 1 s) gives the phase, the share of episodes in it, and the coverage (cycles of the run with an episode in the window); the best share x coverage wins if the window beats chance (share >= 0.3, coverage >= 0.4, at least 3 merged episodes, and a scan-corrected Poisson tail <= 0.001: the tail for a window as wide as the cluster really is, at least `MIN_WIDTH` 0.5 s, times the number of such windows in a period, since the window was put where the episodes are).  omnibus14: three big episodes at :00.2, :00.2, :00.2 of a five-minute run (probe-20261026-052506, 2026-10-26) reported none found (4 needed, and the whole 3 s window's tail was 0.008); now found at the 10 ms tier, and random times give fewer false periods than before (seeded runs of 2000: 8 times in an hour 44 -> 4, 20 times 69 -> 8, 3-5 times 0-2 either way).  Phases are against the epoch, so a 60 s period reads ":59.9 of each minute".  A circular mean was tried first and lost to noise: ten random stalls pulled the mean phase of fifteen minute-boundary stalls 1.7 s off and made 30 s win; the densest window ignores them.  Also an autocorrelation of the per-second "had a stall" series (best lag reported when r > 0.2).

Plots (`Report#plots`, MB::Sound::Plot; `save` writes .svg, .png, .txt): `time` (a Figure: worst stall per second with probe wake p99, the Ruby ticker's max, session render max, and episodes as points on a log ms axis; CPU busy/steal and PSI memory/cpu as %; load average; available memory; dashed rules on wall-clock minutes (10-minute or hourly for longer runs); x in minutes from the start), `histogram` (log-log steps per bucket for wake late, stall, memory work, Ruby ticker), `phase` (episodes and Ruby stalls by second of the wall-clock minute).

## Script and hooks

`bin/latency_probe.rb -t 1h [-o DIR] [--period 1ms] [--threshold 2ms] [--memory 64MB] [--touch 128KB] [--no-memory] [--no-cpu] [--ruby-period 2ms] [--no-ruby] [--no-boost] [--rt-priority N] [--pin CPU] [--mlock] [--with-session] [--flush 10] [--formats svg,png,txt]`; `-t 0` (default) runs until Ctrl-C; `--report DIR` writes the report and plots again from a saved or crashed run (`LatencyProbe.load(dir)`, `LatencyProbe::Saved`: the files read back with the readers Report uses; histograms.json keeps exact maxima); a status line every second on a terminal (`\r`), every 10 s into a pipe; `--compare DIR1,DIR2` prints both runs' tables from their histograms.json/meta.json.  `MB::Sound::LatencyProbe.start(dir:)` (any of the probe's options) starts the same probe from Ruby.  `MB_SOUND_LATENCY_PROBE=DIR` (`MB_SOUND_LATENCY_PROBE=1` for `tmp/latency_probe/<script>-<time>/`) makes `ScriptRunner#live` probe any live script with its Session watched (SVG and text plots at the end).

Cost (Mac container): ~6% of one core at the defaults (thread CPU per second ~60 ms: ~16 µs memory walk, ~14 µs CPU loop, clock reads); `--no-memory --no-cpu` is wake-only.

## Measured (Mac container, i9-9880H Docker VM, 2026-10-25)

16-minute soak, defaults (`bin/latency_probe.rb -t 16m`, YJIT; plots in `/tmp/claude-0/latency-probe-1/soak1/`, re-reported with the tiered periodicity in `soak1-rereport/`), another session's suite loading the VM from minute 10.5 to 15 (CPU busy ~55%, load 8):

- Priority: none obtainable in the container then (no CAP_SYS_NICE until 2026-10-26).  Baselines: memory walk 24 µs, CPU loop 24 µs.  954k ticks, 6083 missed, ring overflow 0, 322 episodes.
- Wake lateness p50 0.19 ms, p99 0.61, p99.9 1.6, p99.99 10.7, max 14.4 ms (the VM's timer wakes run ~0.2-0.6 ms late at all times).  Ruby ticker p99 0.67 ms, max 23.6 ms.
- **The minute stall**: "stalls cluster at :00.2 of each minute (72% of stall episodes; in 13 of 16 minutes), among the 18 episodes of at least 10 ms".  Each is ~330 ms long (from :00.2 to :00.55; 20-35 ticks over the threshold), and within it single ticks of the 128 KiB memory walk take ~10.5 ms (460x its baseline) with the thread's CPU time equal to the wall time, and often the CPU-only loop takes ~10.6 ms too: the vCPU itself runs slow (it isn't descheduled; steal stays 0), memory work most of all, then the next deadline is ~12-14 ms late.  scene-jit-1 saw 5-10x slower CPU from :59.8 to :00.8 with a 33 ms memory workload.
- Other big episodes at random seconds (:41.3, :06.5, :15, :48) look the same (~10.5 ms walks).
- Ruby ticker stalls over 2 ms: 705, of which 649 during probe episodes (system), 28 process, 19 GC, 9 YJIT; GC 14 runs (no majors), 126 ms in all.

## GC stalls seen by the probe (dropouts-2, 2026-10-28)

What the Ruby ticker attributes to `:gc` in a live set is mostly minor collections, not majors: a scene's or bus's build leaves young survivors that every minor marks until they are promoted, 10-20 ms for the first two or three minors after a big build (arrangement.md, Live allocation and GC off).  With the branch's allocation cuts a live song collects 3-6 times a minute less often (night_bus_flow at 256 frames: 14.0 -> 3.0 runs a minute, GC 709 -> 193 ms over 150 s); `bin/gc_soak.rb --gc on` reports runs, majors, and the worst audio second's GC time for a song.
