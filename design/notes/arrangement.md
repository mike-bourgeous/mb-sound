# Arrangement and the Session groundwork

Phase 1 of the arrangement plan (branch `arrange-1`, 2026-10-10): the shared Session groundwork ("G0") and the Set layer.  Phase 2 (branch `arrange-form`, 2026-10-10/11): ring-outs, song forms (`flow`) with labels, gotos, and picks, performer controls, fills, the marker table, and the meter map (sections below the Set layer).  Phase 3 (branch `arrange-3`, 2026-10-11): knobs (K6), snapshots, MIDI learn, and tracks that lead the beat or nudge their notes (Knobs, below).  Phase 4 (branch `arrange-4`, 2026-10-11): recording (the Session MIDI input, `arm`/`rec`/`capture`, audio `rec`, takes that replay MIDI; Recording, below; `take.song` is later).  CLAUDE.md keeps a summary and points here.  Update both when behavior changes.

Sources: the study on branch `research-arrangement` (`research/arrangement/README.md`, prototype in `prototype/`), the interconnect contracts K1-K10 on `research-plan-interconnect` (`research/plan-interconnect/README.md`), and the maintainer's decisions of 2026-10-10 (quoted below).

## Session groundwork (G0)

Built to the interconnect contracts so the terminal UI and glhtui can use it later; only what phase 1 needs is built.

- **Stamps (K1)**: `Session::Stamp` (`lib/mb/sound/session/journal.rb`) = `frame` (session frames since the Session was created; monotonic, never reset by seeks, rewinds, or tempo changes; `Session#frame`) + `pos` (Rational whole notes), plus `bar_length` for display only.  Shown as `bar:beat` (`9:1`, `13:2.5`), never parsed.  `Session#clock` is the stamp of the next frame (where a change made now lands); `Session#transport_record` is the per-buffer `{frame, pos, bpm, bar_length, playing}`.
- **Journal (K3)**: `Session::Journal` keeps up to 10,000 `Journal::Entry`s (`seq, kind, subject, issued, commits, lands, status, source, line, data, undoes`); status is `:queued`, `:landed`, `:cancelled`, or `:failed`, and a status change is a new entry with the same `seq` (`journal.entries` has all of them, `journal.changes` the latest per change, `journal[seq]`).  `subscribe { |entry| }`.  The render thread only pushes small notes onto a `Thread::Queue`; they become entries when the journal is next read or written.  Entries print as `bg :bass lands 9:1 (queued)`; `entry.name` is the subject.  Sources: `:console`, `:schedule`, `:replay`, `:undo`, `:set`.
- **Change queue** (`session/changes.rb`): every change to what plays goes through `Session#change(kind, subject, time, data:) { |t| ... }`: `add` (`:bg`), `remove` (`:stop`), `resume`, `swap`, `master`, mute/solo, `:restore` (undo), `:scene`.  A change landing now applies right away; a future one waits in a sorted queue (time, then issue order) and is applied at the start of the buffer that holds its time, on its exact sample (`commit_due`, after scheduled blocks run, before players render).  This fixed the study's finding 2: a clip source holds one pending swap and a player one stop time, so `swap :bass, b, on: 4` then `swap :bass, c` lost the first swap; queued graphs, stops, swaps, and master chains for one name now all land.  Validation errors (no such player, unrelated clips) still raise when the command is made; a queued change that fails when it lands is journaled `:failed` and printed (raised with `raise_errors`).
  - Changes apply under a render lock (a `Monitor` that `process_buffer` holds until the mix is done, released before `output.write`), so a console change lands exactly at the next buffer's start, and the journal says where.  Lock order: render lock, then the session mutex.
  - `players` lists graphs waiting to start ("starts at bar N") and queued stops; `idle?`, the timeline, and new player numbers count queued starts; a stop for now cancels queued starts of that name; a queued start after a queued stop plays (the old code dropped graphs that "would never have played").
  - `Session#queued(name)`, `#cancel_changes(*seqs)`, `#playing_after_queue?(name)`, `#timeline_nodes_of(name)`.
- **Launch points count from `Session#now`**: the scheduled block's time inside `at_bar`/`after`/`every` blocks (finding 1: `at_bar(5) { bg :x, g, on: :beat }` landed a beat and a half early, because the scheduler runs blocks up to half a bar ahead), a take's recorded issue time while it replays, and the transport position otherwise.
- **Exact fades** (`session/fades.rb`): fades and mute ramps are `Fades::Ramp`s counted in session frames from their first sample (level `k * slope + from` at frame offset k, so any buffer size gives the same levels), and fade-outs start on the exact sample of their stop time (they used to start at the next buffer start).  Levels are cast to SFloat before multiplying audio (Numo's SFloat * DFloat is ~20x slower).
- **Commands return journal entries**: `bg`, `swap`, `resume`, `master`, `mute`/`solo`, `go` return the change's entry (`stop`/`panic` still return names; inside scheduled blocks commands return names); `stop`/`swap`/`resume`/`mute` accept an entry in place of a name.  Every console command (and every scheduled block's batch) is one undo step (`Session#command(label) { }`).
- **Names (K2)**: `Session::Names` (`session/names.rb`): tracks, mute groups, and later knobs share one namespace; `:master` and `:cue` are reserved; a name claimed for two kinds goes through `MB::Sound.live_error` (maintainer decision 6).  `Names.path(:bass, :cut, 3)` is `"bass/cut/3"` (display and files only).
- Not built yet (later projects): the player strip's gain and route stages (K7; mute/solo is built), the session stream (K4).  Markers (K8) arrived in phase 2, knobs (K6) in phase 3 (below).

## Mute and solo (`session/strip.rb`)

Maintainer, 2026-10-10: "Sleep; softmute now; use or extend existing fade functionality for synced fades or mutes".

- `mute`/`unmute`/`solo`/`unsolo` (Session and console) take player names or mute groups (`mutes :breakdown, :drums, :bass`, alias `mute_group`).  Right away by default with a 5 ms declick (`Fades::DECLICK_SECONDS`), or at a launch point (`on: :bar`, `in: 1.beat`, `at: bar(17)`) over a `fade:` in bars (a synced fade), through the change queue.  `solo` with no names clears every solo, and `unmute`/`unsolo` with no names everything, resolved when the change lands (subject `:strip`), so a solo still in the queue isn't missed (the demo render found this).
- Flags belong to names, so a graph replacing a muted one starts muted.  The strip runs fade, then mute/solo (K7 order; gain and routes come later).
- A silent player sleeps: its graph isn't rendered (no CPU).  A mute ramp ending inside a buffer stops reading on its last frame, so oscillators fall asleep at the same sample at any buffer size.  On the unmute sample its timeline nodes restart there like after a seek (clips and tempo-locked tones come back in time); everything else is stale.
- Cost per 800-frame buffer (median, 2026-10-10): 64 constant players 1013 us unmuted, 55 us all muted (asleep), 1858 us all ramping (~13 us per ramping player); 64 ramp+lp4 tracks 2769 / 52 / 3698 us (`/tmp` bench in the arrange-1 report).

## Undo (`session/undo.rb`)

Maintainer: "Raw commands also, and yes, CPU permitting"; quantized to the next bar by default.

- Each change snapshots its subject as it lands: `PlayerState` (current Player, stopped Player, each clip source's clip, mute/solo flags), `MasterState` (the chain's block), `StripState` (all flags, for `:strip`).  `undo` issues `:restore` changes that put each subject back to its state before the step's first change, at the next bar (`on: :now` right away), through the change queue (exact, journaled with `undoes:`, replayed by takes).  Graphs come back as the same objects (stale state, as with `resume`) with a 5 ms declick crossfade; master chains are rebuilt from their blocks; Set state (track clips, current scene) through participants (`Session#note_undo_extra`, `Arrangement#restore_undo_state`).
- A step whose changes haven't landed (by the logical time, `Session#now`) is cancelled right away; `redo!` queues them again.  Undo and redo are symmetric (each pushes the reverse step on the other list).  Steps print as `undo go :drop lands 9:1`; `changes` lists them (`history` is a Pry command).
- Bounds: 64 steps, and at most 8 retired graphs (neither playing on nor resumable) held by the lists (oldest steps dropped).  Measured live heap (`ObjectSpace.memsize_of_all`) with 8-voice `sq80_voice` Synths replaced 16 times: 13.6 MB at limit 0, 74.7 MB at 8, 134.6 MB at 16, i.e. ~7.5 MB per retired graph, ~60 MB worst case at the bound.  A snapshot of that player takes 4 us; a console mute with journal, snapshots, and pruning ~170 us.
- Later (graph-io): undo could keep recipes instead of live graphs.

## The Set layer (`lib/mb/sound/arrangement.rb`, console `ArrangementMethods`)

Maintainer: "Yes, with a realtime demo script that shows a set being sculpted".  One `Arrangement` per Session (`Session#arrangement`).

- `track :bass, q: 1 do |clip| patch end` (alias `define_track`) or `track :pad, graph`: a named player remembering its patch or graph, its clip, launch quantization `q:`, and `fade:`.  `bg :bass, clip` on a track with a patch builds the patch with that clip.  `tracks` lists them.
- Clip names (maintainer, 2026-10-11: ".named 100%"): `seq(...).loop.named(:bass_a)`, `grid(...).named(:beat)` (`Sequence::Named` on Clip, Seq, Kit: `named`, `name`, `named?`).  Listings (`tracks`, `scenes`, player descriptions) show the name, else the kind (seq, clip, kit); `Arrangement#label` is gone (the flow's `label` is the only label).  graph-io records `named` on clips, so `to_ruby` prints it and uses it as the variable name; kit chains don't print yet.  A name belongs to its object: `bass_a.transpose(12)` has none until named.
- `scene :verse, pad: chords, bass: bass_a, drums: beat` (alias `define_scene`): a full state; values are a Clip or Kit, `:on`, `:off`/`nil`, `:cut`, or `:keep`; tracks not named stop unless `others: :keep` (partial scenes like fills and risers); a block runs at launch with commands landing at the launch time.  Stopping tracks ring out (phase 2, below) unless `others: :cut` (or the value `:cut`) or a fade.  `scenes` lists them (current one marked).
- `go :drop` (alias `launch_scene`, `on:`/`in:`/`at:`, `fade:`): each track changes at its own launch point (the call's `on:`/`in:`/`at:`, then the track's `q:`, the scene's `q:`, the set's `quant`, 1 bar by default).  Only differences change: a patch track already playing swaps clips (keeping graph and effect state), rebuilding when swap can't map the clips or a Kit brings rows the old kit lacks; a track playing the scene's clip is left alone; stops ring out (phase 2) unless the scene says `others: :cut` (5 ms declick) or the scene, call, or track gives a fade.  One undo step; returns the `:scene` journal entry (`scene :drop lands 13:1 (queued)`).
- Track and scene `q:` and `quant` are alignments (`on:` values): `:now`, `:beat`, `:bar`, `:clip`, a Duration, or a number of **bars** (fades are bars too).
- Scene keys naming a non-track (e.g. a mute group) go through `live_error`; unknown tracks raise at `go`.
- Scene keys naming knobs turn them at the scene's launch point (Knobs, below).  Tracks take `lead:` and `nudge:` (below).  Forms are below.

## Launch points: `on:`, `in:`, `at:` (`lib/mb/sound/launch_point.rb`)

Maintainer, 2026-10-10 ("Do we have a name for alignment vs placement elsewhere? Eg on vs in"; "Yeah, make that change in bg"): `at:` used to mean alignment everywhere with different units (`bg ... at: 4` was the next quarter note, Set `at: 4` the next 4-bar line).  Now every command that lands a change (`bg`, `swap`, `resume`, `master`, `mute`/`unmute`/`solo`/`unsolo`, `go`, `undo`/`redo!`, their Session methods, `Arrangement#go`/`#play`) takes three keywords, and plain numbers are bars everywhere:

```ruby
go :drop, on: :bar                # alignment: :now, :beat, :bar, :clip, 4 (bars), 1.n4, 2.beats
go :drop, in: 2.bars              # relative placement from Session#now (bars, Durations, Lengths)
go :drop, at: bar(33)             # absolute placement: bar(n, beat: 1), counting from 1 like at_bar
go :drop, in: 2.bars, on: :beat   # two bars from now, then the next beat
```

- Order: start from `Session#now`, add `in:` or jump to `at:`, then align forward to `on:` (ceil; a time already on the grid stays).  Without `on:`, a change still aligns the way it would without `in:`/`at:` (maintainer, 2026-10-10: "Tracks should keep the same time alignment they would have otherwise"): `bg`/`swap`/`resume`/`master` to `:now` if idle, else `:bar` (so `bg :x, g, in: 2.bars` lands on the bar line after two bars while something plays); Set tracks to their effective `q:` (track, scene, `quant`), each on its own; mutes/solos not at all (exactly at `in:`/`at:`, right away without them); `undo` to `:bar`.  Write `on: :now` for an exact offset or position.  Take replays force recorded landing times, so they stay exact.
- `at:` takes only `bar(n)`/`bar(n, beat:)` (and alignment Symbols as aliases of `on:`, "at the bar").  Through `live_error`: a plain number (suggesting `on: 1.n4` / `on: 4` / `in: 4` / `at: bar(4)`), a Duration or Length (maintainer: "Agreed"; `at: 32.bars` would have been bar 33; the message points to `bar(n)`; they stay valid in `in:` and `on:`), `at:` with `in:`, `at: :bar` with `on:`, `in: bar(n)`, and a position that has already passed (maintainer: "live_error"; live, it warns and lands now; a replaying take lands it now silently, where the take forces it).  `at_bar` blocks keep warning and skipping for passed bars (unchanged: raising there could break scripts that schedule blocks after playback has moved on).
- One resolver: `LaunchPoint.of(binding)` reads the keywords (the only place that reads the `in` keyword), validates, and returns a frozen `LaunchPoint` (nil if skipped in live mode); console methods pass it down as `at:`; `Session#launch_time(point, nodes, default:)` and `Arrangement#resolve(q, track, point)` (the effective `q:` as the default alignment) call `LaunchPoint#resolve`.  Landing samples are unchanged for equivalent inputs (old `at: 4r` = `on: 4`; the take replay spec still matches bit for bit).
- Name check for the console `bar(n)` (`ScheduleMethods#bar`, returns `LaunchPoint::Bar`): no collision with `MB::Sound`, `Kernel`, `GraphNode`, or Pry commands; `Numeric#bar` (`1.bar`, a Duration) lives on a receiver.

## Takes (`lib/mb/sound/take.rb`, `take/replay.rb`)

Maintainer: takes on by default; "Repo sets if standalone or requested, user data directory otherwise, with file path printed".

- `MB::Sound::Take.current` records every console line (Pry `:before_eval`/`:after_eval` hooks in `bin/sound.rb`, started after `warm_up`) with its issue Stamp and where each change it made landed.  `take` shows the last lines; `take.entries` their journal entries; `take.restart`.
- `take.save(path = nil, repo: false)` writes an executable replay script: explicit path, else `take.home`, else `sets/` with `repo: true`, else the user data dir (`$XDG_DATA_HOME`/`~/.local/share/mb-sound/takes`, macOS `~/Library/Application Support/mb-sound/takes`); prints the path.  Lines starting with foreground or display commands (`play`, `plot`, `vis`, `wait`, `take`, `players`, ...) stay as comments.  `take.form` prints a note (forms are phase 2) and returns the scene launches.
- `Take::Replay` restores tempo, bar length, master gain, default fades, and the root random generator (Marshal), then schedules each line at min(issue time, landings) in a fresh console-like binding (`Take.console_binding`), with its landing times forced on its changes (`Session.with_perform(forced:, now:)`) and `Session#now` = the issue time, so undo/cancel decisions match although lines run ahead.  The saved script renders with `-o file` (`-b 367,368` cycles buffer sizes) or plays.
- Measured (spec/lib/mb/sound/take_spec.rb, 960 buffers of tracks, scenes, mutes, solos with fades, two queued changes on one track, undo of a queued change, stop + undo now, a mute group fade): clip and constant sources replay bit for bit at buffer sizes 800, 367/368, 64, 1001/13; band-limited tones exactly at the live buffer size and within 3.7e-9 (-151 dB re peak) at others (Tone phase accumulates per buffer).
- Not exact: tempo and master gain changes (applied at buffer starts / when the line runs), nondeterministic code.  Live MIDI replays exactly since phase 4 (Recording, below).

## Ring-outs (`lib/mb/sound/session/tails.rb`, phase 2)

Maintainer, 2026-10-10 ("Queue ringdown for p2"): when a scene drops a clip-driven track, the clip stops sending notes, the graph keeps rendering until it is silent, capped, then the track sleeps.

- `Session#remove(name, ring: true)` (console `stop :bass, ring: true`; the Set's default for tracks a scene stops): on the exact sample of the stop time every `MIDI::ClipSource` in the graph swaps to `Clip.silent` (notes in progress get note-offs there) and the player keeps rendering.  It sleeps (retired and kept for `resume`) once its output stays below `Master::TAIL_THRESHOLD` (-90 dB) for `RING_QUIET_SECONDS` (= `TAIL_QUIET_SECONDS`, 1 s), cut on the sample where that stretch ends, so the sleep frame is the same at any buffer size (spec: 800, 367, 64).  After `Master::MAX_TAIL_SECONDS` (10 s) a `TAIL_FADE_SECONDS` fade starts on that exact frame.
- The real clips come back when the player sleeps (`ClipSource#ring_out`/`#end_ring_out`/`#ring_clip`); swaps and undo snapshots see the ring clip, and a swap of a ringing source changes the clip it will play again.
- Graphs without clip sources (drones, files, raw oscillators) fade over `RING_DRONE_FADE` (1/4 bar).  Graphs whose sound doesn't come from notes but that do read clips (a `tween`-driven riser) ring to the cap: give their track a `fade:` (the demo's riser does).
- Launching the same graph while it rings (resume, undo, a scene bringing a patch track back with the same clip, a graph track) revives the ringing player (no second copy; its notes come back at the launch).  A later cut or fade takes over from a ringing tail; a muted ringing player sleeps right away.
- Journal: the stop's data is `{ ring: true }`; a `:rung_out` entry (source `:session`, data `seconds:`, `capped:`) is noted from the render thread when the tail ends (`Journal#note_entry`).  `players` shows "(ringing out)".  Takes replay ring-outs exactly (the stop's landing is forced; the tail is the graph's own output).
- Cost (2026-10-10, 800-frame stereo buffers): following one ringing player 12 us per buffer (fast paths for silent buffers and buffers ending loud; 42 us before them); the graph's own render as before.

## Song forms (`lib/mb/sound/form.rb`, `form/`, console `FormMethods`)

Maintainer, 2026-10-10: "I'd vote for the block builder" (`flow` alias of `form`; strings withdrawn), fills "close; may tweak after it's built".  2026-10-11: follow actions moved from section definitions to the flow ("The decision should be attached to the outer structure. For generative infinite pieces, goto (potentially with a random choice target). Maybe there are also label entries in the flow for goto to use as targets."; then "Yes. Seek should also accept labels in this regime."): a section's `next:` applied at every appearance, so a weighted choice after a section's second appearance could wrap the playhead backwards.

```ruby
flow do
  fill :turn, every: 8              # a phrase fill (below)
  intro  8
  label  :top                       # a target, takes no time
  verse  8, times: 2
  chorus 8, fill: :roll
  pick   verse: 3, chorus: 1        # plays one of them, then carries on
  drop   16, fill: [:riser, 4]
  goto   :top, times: 2             # back to :top twice more, then fall through
  outro  8                          # the end of the order ends the form
end

flow do                             # generative, never ends
  label :a; groove 8
  pick do |p|                       # groups, or nothing
    p.option(2) { hook 4; hook }
    p.option(1) { stab 2 }
    p.option(1) { }
  end
  label :b; breakdown 8
  goto a: 3, b: 1                   # weighted random target
end
```

- Builder (`Form::Builder < BasicObject`, `instance_exec`): the first call with a length declares the section (a singleton method on the builder) and plays it; bare calls play it again (`verse`, `verse times: 2`); the same declaration again also plays it; a different one raises.  `method_missing` only declares: a bare unknown name is a `NoMethodError` whose message suggests names (`Form.suggest`, `DidYouMean::SpellChecker`; did_you_mean's own method checker needs `#methods`, which BasicObject lacks).  Section names can be anything except the steps `repeat`, `fill`, `label`, `goto`, `pick` (`Form::STEP_NAMES`) and keywords (`break`, `next`, `redo`: write `breakdown`).
- Section options: `times:`, `fill:` (below), `scene:` (the scene launched; the section's name by default, `false` for none), `fade:`.  `next:` raises with a pointer to goto/pick; other unknown options suggest names.  Lengths are Durations or plain numbers of bars (counted through the meter map where the section starts; Durations are fixed whole notes).  Trap: `verse 8.bars * 2` is one 16-bar verse (spec'd).
- Steps: `label :name` (unique, not a section name, not inside `repeat`, which would repeat it, and not `:next`); `goto :label` (always), `goto :label, times: n` (n jumps, then it falls through once and its count starts over, so a goto inside a bigger loop repeats its own loop on every pass of the bigger one, like nested repeats), `goto a: 3, b: 1` (a weighted label; `next:` weighs carrying on, `goto top: 3, next: 1`, maintainer: "goto next: ... sounds great"; `nil => w` is accepted quietly as `next:`; times: counts only jumps), `goto ->(f) { }` (a Proc given a read-only `Form::State` with `section`, `pass`, `plays(name)`, `history`, `bars`, `previous`; returns a label, or nil or `:next` to carry on); `pick :a, :b` (even odds), `pick a: 3, b: 1`, or `pick do |p| p.option(w) { sections } end` (groups; an empty or blockless option plays nothing).  Targets of in-flow gotos are labels only; a backward goto with no section between it and its label raises (it would loop forever), and a decision that walks 10,000 steps without reaching a section raises.  Sections named in a pick Hash must be declared somewhere in the flow (checked when the block ends, with a hint to declare them).
- `section :verse, 8.bars, fill: :roll` (console, alias `define_section`; `Arrangement#section`) declares a section outside a flow; bare calls and picks in later flows play it.  `flow(play: false) { }` builds without playing; `play_form(form)`.
- `Form#to_ruby`/`#inspect` print the flow block back (picks as `pick :a, :b` or `pick a: 3` when their sections are already declared, else the block form); `eval` of it builds an equal Form (`Form#==` compares the code).  Goto Procs print as a `->(f) { nil }` placeholder with a comment.  `take.form` returns a linear Form of what played (passes as `times:`, gotos and picks resolved; without a form, scene launches as sections lasting until the next launch).
- `Form#program` compiles the order to flat instructions (`[:play, name, times]`, `[:label, name]`, `[:goto, target, times]`, `[:pick, [[weight, index], ...], end]`, `[:jump, index]`; repeats unrolled, each pick option ends with a jump past the pick); `Form#labels` maps labels to indices; `Form#steps` is the order straight through (gotos not taken, first pick options), which `Form#bars` sums.
- Playback (`Form::Playback`, `Arrangement#playback`; `flow` with no block shows it: `▶ a pass 1/1 (bar 2 of 4), next :b at 5:1 (open)`, `next ?` while chance or a Proc decides): each pass launches its section's scene on the pass's first sample (`go scene, on: :now` in a scheduled block; the scene's block may change the meter before the section's length is counted), sets phrase fills and a `:section` marker, and schedules the commit point and the boundary.  A form starting now launches its first section right away (a scheduled block would run a buffer later when idle, which made take replays a buffer late).  The end of the order rings every player out at the boundary.  Scenes are checked at start (a missing one goes through `live_error`).
- Labels become `:label` markers (`Session::Markers` kind) where the flow passes them: at the start of the section after them, set when that decision commits (like the next section's marker), so `at_marker(:top)` runs there.

### Decisions, commit points, and controls

- Commit point of a pass: the start of its fill, else its end (the bar line where the next section starts).  The decision there is the next pass of the section (`times:`, `loop!`), else a walk from the next instruction through labels, gotos, picks, and jumps to the next section (a `Playback::Step`).  Controls issued before the commit point (by logical time, `Session#now`) change that boundary; after it, the following one.  The decision runs in a scheduled block, which the scheduler runs up to half a bar early; a control arriving after the block ran but before the commit point re-decides it (the queued fill scene is cancelled and the Set state restored), so the boundary a control applies to depends only on its time and takes replay the same way (spec: a goto inside the lookahead window replays bit for bit at 800 and 367/368).
- Decisions are pure: goto counts are copied into the Step and adopted when the next pass starts, so a re-decided commit starts from the same counts.
- Chance: one `Random.new(seed * 1_000_003 + passes played)` per decision (several picks and weighted gotos in one walk draw in turn), the seed from `MB::Sound.next_seed` (takes restore the root generator) or `flow(seed:)`; live, replayed, and re-decided commits draw the same numbers.  The demo's pick draws exactly what its old `next: { breakdown: 3, drop: 1 }` drew (2026-10-11: the full seed-1 track and the seed-12 branch through bar 54 render sample for sample the same as before).
- Console (`FormMethods`; names checked against `MB::Sound`, Object/Kernel, and Pry's commands, spec'd): `loop!` (alias `loop_section`; repeats the section until `onward`, alias `unloop!`, `continue_form`; the maintainer: "loop! preferred over hold, you pick the inverse name"), `goto :x` (`goto_section`; a label: the flow carries on from it; a section: its next appearance in the order, wrapping), `finish` (`finish_form`; the last section in the order next), `skip` / `skip :x` (`skip_section`; leave at the next bar line or a launch point, `skip on: :beat`, `skip :drop, in: 2.beats`, never at the pass's own start; honors a pending goto/finish, ends a loop; the timeline keeps running; returns a `:skip` journal entry, which isn't an undo step), `practice :x` (`rehearse`; goto + loop!), `seek :x` (below).  `loop!`, `onward`, `goto`, `finish`, `practice` stay boundary-based and return a `Playback::Decision` (`next :c at 5:1 (open)`) (maintainer, 2026-10-11: "Ok").  Unknown names raise with the form's sections and labels and did_you_mean suggestions.
- `seek :x` (maintainer: "Agreed" that it moves the timeline; then "Cool" to going through the change queue, 2026-10-11) with a section or label of the playing form moves the timeline to where it last started or is set to start next (its marker from this playback), else to its place in the form played straight through (gotos not taken; instructions in a pick's other options at the pick's position), and plays the form on from there (`Playback#seek_now`): the current commit, a scene launch the scheduler queued ahead, queued skips, and fills after that point are dropped (a pass launched ahead leaves the history).  Seeks in general: below (Seeks).
- The form's own launches (each section's scene, fill scenes) run outside the console's undo groups (`Session#without_command`), so `undo` takes back the performer's last command, not the form's last section launch (the take spec found `undo` undoing a fill scene).

### Fills

- A section's `fill:` plays in its last bar by default (`fill: :roll`), for a length (`fill: [:riser, 4.bars]`), alternating names per pass (`fill: [:a, :b]`, `[:a, :b, 2.bars]`), or only when leaving (`fill: { names: [:z], on: :leave }`; default `on: :pass`, every pass including `times:`, `:again`, and `loop!` repeats).  A fill whose name is a scene launches it at the fill's start (a partial scene like a riser; the next pass's scene, a full state, takes it away).  The fill is set at the commit point.
- Phrase fills: `fill :big, every: 16` (`length:` default 1 bar, `layer:`) in the flow plays fill `:big` at the end of every 16 bars from each section's start.  Only clips with fill marks react (no scenes: nothing would take a scene away mid-section).
- `Sequence::FillMap` (`Transport#fills`): intervals with priorities; a section's fill beats phrase fills, a longer period beats a shorter one ("Fizzbuzz for drums almost"), `layer: true` plays alongside.  A form prunes fills that ended over a whole note before each section start.
- Note marks (Elektron's FILL condition; `sequences.md`): `Event#fill_mark` / `Seq::Step#fill_mark` = `[:fill or :nofill, name]`; `C4.fill`, `C4.fill(:big)`, `.nofill`, `Seq#fill`/`#nofill`, `Clip#fill` with no argument or a Symbol (`fill(span)` still repeats to a span), `Clip#nofill`, `Kit#fill(name, rows / Kit / block)` layering fill rows onto the kit (`beat.fill(:turn) { grid(16, clap: '....X...x.x.xXXX') }`), `Kit#nofill(*rows, name:)`.  `Clip#edges(fills:)` keeps or drops marked notes by the fills at each note-on (`ClipSource` maps clip positions to the timeline); without a form nothing is a fill.  Cost: 26 us vs 25 us per 800-frame read of a 16-step marked row (177 us before only events in the window asked).

## Seeks (`lib/mb/sound/session/seeks.rb`)

Maintainer, 2026-10-11 ("Cool"): seek goes through the change queue with launch points, returns a journal entry, is undoable, and replays exactly from takes.

```ruby
seek 17                  # bar 17, now (the default alignment)
seek :top, on: :bar      # a form label at the next bar line
seek :drop, in: 2.beats  # a form section; markers work too
undo                     # back where the timeline was when the seek landed (at the next bar)
```

- `Session#seek(target, at:, start_time:)` issues a `:seek` change (subject: the target); console `seek` (SequenceMethods) is one undo step and returns the entry (`seek :top lands 13:1 (queued)`).  Targets are checked when issued and resolved when the seek lands: a section or label of the playing form (`Playback#seek_now`), a marker, or a bar number through the meter map.  `rewind` stays a direct reset (spec cleanups and scripts use it).
- Exact frames: `process_buffer` renders in spans; a timeline change landing inside a buffer splits it (`frames_before_seek`: the first frame at or after its time), `commit_due` leaves timeline changes for the start of the next span, and `commit_due_seeks` lands them there after any change due before them in queue order.  The rest of the buffer renders from the new position (players' timeline nodes restart as after any seek).  Spec: a seek at `bar(3, beat: 4)` and its undo land on the same frames at 800 and 367/368 buffers, sample for sample.
- Undo: the `:seek` change snapshots the timeline (`TimelineState`: the position where it landed, and the form's pass, or the pass before one the scheduler launched ahead).  Undo issues a `:restore` change of subject `:timeline` (also a timeline change, so exact) that seeks back there and resumes that pass of the form (`Playback#restore_seek`, without adding it to the history).  Changes the form makes while restarting belong to the seek, not to an undo step of their own.
- Takes: `Session#epoch` counts timeline changes landed; positions repeat after a backward seek, so take lines record the epoch they were typed in (`r.line ..., epoch: 1`), replays schedule them for that epoch (`Scheduler` entries take `epoch:`), and render until the end position in the last epoch (`ends_epoch:`).  The take spec seeks back from bar 12 to bar 3 and undoes it, bit for bit at 800 and 367/368.
- Not handled: changes queued for times after a backward seek's landing (e.g. `go :x, on: 4` issued before it) land when the timeline reaches their time again; a skip line replayed ahead of time (lines run up to half a bar early) sees the form state of that moment, not of its issue time, if the form commits in between (seen when a skip was issued between a seek and its landing; avoided in the spec).

## Markers (`lib/mb/sound/session/markers.rb`, K8)

One table per Session (`Session#markers`), name -> `Marker(kind, pos or seconds)`: `:section` (forms register each section where it starts, and the next section when it is committed), `:label` (a form's labels, where the flow passes them), `:position` (`marker :vo, at: bar(5, beat: 2)`), `:time` (`marker :hit, at: 12.5.seconds`, any Length; absolute times that don't move with the tempo, converted at the current tempo when used since ramps don't exist yet).  `markers` lists them; `at_marker(:drop) { }` (alias `on_marker`) runs a block at the marker if it is ahead, else the next time it is set ahead of now (e.g. when a form next reaches the section or label), warning with suggestions for a name that is neither a marker nor a form name yet; `seek :name` moves the timeline to a marker (sections and labels of a playing form: above; Seeks).  `marker` refuses names of the playing form's sections and labels (the form moves those).  Marker files/imports: later.

## Knobs (`lib/mb/sound/graph_node/knob.rb`, `session/knobs.rb`, console `KnobMethods`; phase 3, K6)

Maintainer, 2026-10-10: `turn` for knobs with `move` as an alias; tracks, groups, and knobs share one namespace (collisions through `live_error`).

```ruby
knob :cut, 800, range: 100..8000, curve: :exp, unit: 'Hz'   # define (again: new options, same value and readers)
bg :bass, bass.tone.ramp.lp4(knob(:cut))                     # a GraphNode anywhere a node goes
turn :cut, 3000                          # now, with a 5 ms glide (smooth: 0 for an exact jump)
turn :cut, 400, over: 2.bars, curve: :smooth, on: :bar      # ramps: bars, Durations, Lengths; any Curve
turn :cut, 2600, from: 900, over: 8      # jump to 900, then ramp
turn :cut, tween([400, 8000], 8.bars)    # follow a node (or follow: :other_knob) until turned again
move :cut, 1200, in: 1.beat              # move is turn
scene :drop, bass: b, cut: 8000, space: [0.5, over: 2]      # knob values in scenes
flow do; drop 8, cut: 8000; end          # and in sections (turned as each pass starts)
snap :dark; recall :dark, over: 4.bars   # snapshots of every knob
knob :morph, 0; xfade :dark, :bright, :morph; turn :morph, 1, over: 8   # a crossfader (xfade :a, :b, 0.3 for a fixed amount)
learn :cut                               # the next MIDI controller moved (knob ..., cc: 74 for a number)
```

- **The node** (`GraphNode::Knob`): a `Knob::Spec` shaped like `MIDI::ControlSpec` (name, default, range, curve `:linear`/`:exp`, unit, cc, takeover `:pickup`/`:jump`, smooth).  Its value is a function of the session frame: segments starting on exact frames (`Hold`; `Ramp` over N frames in the knob's scale, octaves for `:exp`, shaped by a Curve, the value on frame start + j being `from + (to - from) * curve((j + 1) / length)` and exactly `to` on the last frame; `Follow` a node, clamped to the range or mapped).  Ramps start from the value on the frame before they land (or `from:`).  Same values at any buffer size (spec'd at 1, 7, 128, 800, 367/368 standalone; 800, 367, 64, 1001/13 in a Session).
- **Readers**: `get_sampler` returns a new `Knob::Reader` per consumer (no Tee).  The Session advances every knob once per span, after `commit_due` and before players and master effects (`advance_knobs`, `Session#knob_frame`), and readers return that span's values (a frozen buffer; a cached view for a shorter read).  So knobs drive any number of graphs, including sleeping (muted) players, without falling behind.  Outside a Session readers count their own frames (a new reader starts at the block being read).  Oversampled reads (more frames than the span) aren't supported.
- **Plans**: readers describe themselves as `p.param` (`plan_param` gives a Float while the knob holds still over the block, else the block's buffer), so planned graphs keep fusing; check mode (`MB_SOUND_PLAN_CHECK`) reads the same cached block twice.
- **Changes**: `Session#turn` (and `snap`, `recall`, `xfade`, scene and section values) go through the change queue: kind `:turn`, subject the knob name, data `{value:, over:, curve:, from:}` or `{follow:}`; exact landing frames (`@landing_frame`), journaled (`turn :cut lands 2:1 (queued)`), one undo step per command.  Default alignment: none (right away or exactly at `in:`/`at:`, like mutes).  Undo snapshots the knob (`Knobs::KnobSubject`, `KnobState`: the held value, a ramp's target, or the followed node) and restores it with the knob's glide (or following the same node again).  `:snap` is a change without undo snapshots.
- **Follows**: a followed node's timeline nodes (a tween's clip, tempo LFOs) start at position 0 on the turn's frame, so automation started by a turn plays from its beginning (a looping tween launched as a player instead follows the timeline: since omnibus4 it resumes the step the timeline is in, or starts at its first keyframe with `tween(..., align: :launch)`; see curves.md).
- **Snapshots**: `snap :a` records every knob's held value or ramp target (a follow's current value) when it lands; `recall :a, over:` turns each knob; `xfade :a, :b, x` moves every knob x of the way in its own scale, or with a node or knob name follows it as a crossfader (the crossfader knob itself is left out).  Snapshot names are their own table (not the shared namespace).
- **MIDI**: `Knob#listen(stream)` reads controller events per span (exact frames from the event times), `#cc=`, `#learn` (the next controller moved); `:pickup` takeover waits until the controller passes the knob's position (or is within half a step), `:jump` moves right away; moves glide over `smooth:`, and a turn makes a pickup controller catch the knob again.  `Session#knob_midi` is the Session's default MIDI input (phase 4: `Session::MidiInput`, read on exact frames; the console attaches live input on `learn` or `cc:`) unless set to another stream.  Phase 4: controller gestures are `:cc` journal entries and takes replay the moves from their MIDI log; `learn` is a `:learn` change (Recording, below).  `Knob#control_specs` gives a ControlSpec, so `MIDI::ControlMap` and ACID XML list knobs used in graphs.
- **Names**: `knob`, `knobs`, `turn`/`move`, `snap`, `snaps`, `recall`, `xfade`/`crossfade`, `learn`: no collision with `MB::Sound`, Object/Kernel, GraphNode, or Pry commands (spec).  `knobs` and `snaps` are display commands in takes.
- **Cost** (2026-10-11, container, median per 800-frame buffer, 64 players each `lp4(knob)`): holding knobs +0.3 us each (1398 vs 1408 us with Constants); ramping 10.5 us each; following `2000 + 1000 * 0.3.hz.lfo` 16.9 us each, mostly the followed graph (followed nodes aren't planned).
- **graph-io**: `to_ruby` prints knobs as `GraphNode::Knob.new(...)`; graph documents (since omnibus4) write a `knob :cut, 800.0, range: 50.0..4000.0, curve: :exp, unit: "Hz", cc: 74` header line per knob (the console's `knob` syntax, with the knob's held value) and use the bare name in the graph; loading makes one standalone `GraphNode::Knob` per line (not registered with a Session), overridable like params (`params: { cut: 1200 }`) and turned by `Document#set`.  Moves are performance state (takes replay them), not graph structure: a moving knob saves the value on its last rendered frame, after a comment saying what it was doing (decision 2026-10-11, omnibus4; it raised DumpError for a few hours after the arrange-3/graph-io-2 merge).

## Leading the beat and nudges (`Arrangement#track`, `MIDI::ClipSource#ahead`)

Maintainer, 2026-10-11 ("yes" for phase 3): "Slow pads sometimes need to lead the beat because of their slow attack."

- `track :pad, lead: :attack do |c| ... end` plays the track early: bars, a Duration, a Length, or `:attack` (the longest attack of the patch's `amp_env` envelopes, `Envelope#preset_name`, else of any envelope; measured each time the patch is built), capped at `Arrangement::ATTACK_LEAD_MAX` (1 bar; maintainer-approved 2026-10-11, omnibus4: a 4 s pad attack would lead by 2 bars at 120 BPM) unless `lead_max:` (bars, Duration, Length) says otherwise; `tracks` shows "(attack capped)".  `lead: 0.5.attack` leads by that fraction of the attack (maintainer, 2026-10-11: "Might be good to have a fractional lead amount on the attack as well", then "What about lead: 0.5.attack so attack is like any other time unit?"; omnibus5): `Numeric#attack` (alias `attacks`) makes a `Length::Attack` (a fraction of attack times; not a Length, since it has no time of its own: `#of(attack)` resolves it, `to_ruby`/`inspect` print `0.5.attack`); `:attack` is stored as `1.attack`; the cap applies to the result; spec: half a 0.25 s attack leads 6000 frames, bit-identical at 800 and 367 buffers).  Fix found then (omnibus5): voice envelopes (`v.amp_env` in a Synth) scale their times by the GM2 controllers through nodes (`NoteEnvelope#gm`, on by default), so `Envelope#attack_time` was nil and `:attack` measured 0: night_bus_flow's pad never led (the arrange-3 "lead vs no lead" renders differed only by random state: renders in one process draw different seeds unless `MB::Sound.seed` is reset).  `Arrangement#envelope_attack` falls back to the attack as given (`base_times`, CC 73 at its center).  `nudge: 6.ms` moves its notes by a fixed time (negative early).  `ahead = lead - nudge` in whole notes at the tempo when set (`Arrangement#ahead(name)`; `tracks` shows "ahead 476 ms").
- `MIDI::ClipSource#ahead`: every timeline time the source is given (`start_at`, `swap_clip`, `ring_out`, `end_ring_out`) counts that much later, so notes sound early, and the track's launches, swaps, and stops land `ahead` earlier (so a lead's first notes play and the old clip's last ones still end on time).  Seeks, wakes, and ring-outs keep the offset.  A launch too close to make its lead lands now (the first notes chase in late).  Mutes aren't shifted.
- Spec: a 1-beat lead moves edges 24000 frames early at 800 and 367 buffers; a 0.25 s attack peaks within 2 frames of the downbeat; 10 ms nudge = 480 frames.

## Recording (phase 4: `session/midi_input.rb`, `session/midi_in.rb`, `midi/capture.rb`, `arrangement/recording.rb`, `session/audio_recording.rb`, console `RecordMethods`)

Branch `arrange-4` (2026-10-11), the study's phase 4 `arrange-record` minus `take.song` (maintainer: "Later, agreed").

```ruby
arm :lead                  # hear the keyboard through :lead's patch (player :"lead/live")
rec 4                      # looper: the next 4 bars (from :lead's q:) loop on :lead when they close
rec :bass, 2.bars, quantize: 16   # a named track, a Duration, cleanup
capture :lead              # Capture MIDI: the last phrase loops from the next launch point
capture :lead, 2, quantize: [16, amount: 0.8], humanize: 1.n64
captures                   # => {lead_1: Clip(...), lead_2: ...}; scene :x, lead: captures[:lead_1]
learn :cut                 # controller moves are journaled (:cc) and replayed by takes
rec 'sets/take3.flac'      # the master bus from now (on:/in:/at:), `rec` alone: a timestamped file
stop_rec on: :bar
disarm                     # every armed track
```

- **The Session MIDI input** (`Session::MidiInput`, one per input name, `Session#midi_in(name)`): reads its input (live input; any Stream as a stand-in) once per rendered span, after scheduled blocks and before changes land, knobs advance, and players render.  Every event gets `Stamped(frame, pos, epoch, event)`: the frame of its time and the exact Rational position of that frame (`pos = from + offset * per_sample`).  Consumers: taps (`#stream`, a `Tap` source per stream) give graphs each span's events on the same frames with no added latency (a graph starting partway through a buffer starts there and never hears older events, which also fixed the lag of a late-built reader on a live stream something else kept reading; outside a running realtime Session a tap reads the input itself, e.g. foreground `play`); knobs (`Knob#listen(input)`); the history (64 whole notes, 100,000 events at most) for `rec`/`capture`; the Session MIDI log for takes (`[input, epoch, pos, bytes]`); `:cc` journal entries per controller gesture (CC, bend, channel pressure; moves under 0.25 s apart; source `:midi`; subject the knob it moved, else `:cc74`/`:bend`/`:pressure`; data `control, channel, from, to, moves, knobs`), noted when the gesture stops.
- Console `midi`/`midi_stream` (and so synth/effect scripts' live MIDI) are Notes/streams on the default session's input: `attach_live_midi` opens the LiveSource once and gives it to the input (one tap stream per input shared by the pedaled and dry Notes; `Tap#live_source` reaches the LiveSource).  Events arriving while the timeline is stopped all have the stopped position; a replay gives them in one span (they only reach knobs then, since anything playing moves the timeline).
- **Clips from events** (`MIDI::Capture.clip(events, from:, length:, grace: 1/64r, channel:, sustain: true)`): a note belongs to the clip if its note-on is in `[from - grace, from + length - grace)`; a downbeat played up to a 64th early wraps to the loop's end (so it plays as early before every downbeat, and the next loop's early downbeat stays out).  Notes end at their note-offs (held by CC 64 unless `sustain: false`), a re-struck key ends the earlier note, notes still held end where the window ends.  Starts are exact Rationals; the clip is a timeline loop, so it plays in phase wherever it lands.
- **arm/disarm** (`Arrangement::Recording`): arming is Set state set when the command runs (so `arm :lead; rec 4` works while the `:arm` change waits, as in replays where lines run ahead) plus an `:arm` change at `Session#now`; with a patch and `monitor: true` (default) the patch is built on a `MidiInput::LiveClip` (clip output methods and `#transpose` on new taps, pedals applied; other clip methods raise and the monitor is skipped with a warning) and launched now as `:"name/live"`.  `tracks` shows "armed"; undo restores the armed set (undo extras).
- **rec N** (looper) and **capture**: one undo step of changes: `:rec` where the window opens (rec only; the track's launch point: call `on:`/`in:`/`at:`, else its `q:`, the set's `quant`), the track's change to a silent placeholder clip where it closes (a swap if it plays, else a launch: the patch is built when the command runs, never on the render thread), and `:capture` right after it at the same time, which builds the clip from the history (events up to the span are known: the input is read before changes land), applies `quantize:`/`humanize:` (`Clip#quantize`/`#humanize` arguments, or `[arg, {options}]`), names it `track_N`, and swaps it in for the placeholder (`swap_now`, lineage rederives patch transforms).  `capture` without a length takes the last phrase: back from the launch point to the first note-on after a gap of a bar or more between note-ons, rounded up to 1, 2, 4, 8, or 16 bars, decided when it lands.  Lengths are bars (numbers) or Durations, at most 63 bars of 4/4.  Errors (no armed or named track, a graph track, nothing played) go through `live_error`; nothing played is checked when issued (not in replays, whose lines run ahead of the MIDI).
- Spec'd (`recording_spec.rb`): rec at 800, 367/368, 64, 1001/13 buffers gives the same clip and the swap on the closing frame (192000 for bar 3); swapping into a playing graph keeps it; quantize; undo before landing; phrase capture; monitors.
- **Audio** (`Session::AudioRecording`, `rec 'path.flac'` / `rec` / `stop_rec`): a `:record` change (subject `:audio`) starts a `Recorder` on its landing frame; `process_buffer` hands each written buffer (after master gain) with its first frame to the recorders, which copy the frames between start and stop onto a queue; a writer thread sends them to an ffmpeg file output and closes it.  `:stop_record` sets the stop frame; a `:recorded` entry (path, seconds, peak) is noted when the last frame is queued.  Paths: given, else `rec_<time>.flac` in `Take#home`, `sets/` with `repo: true`, else the take data directory; existing files need `overwrite: true`; the path is printed.  In a replay the change is made (keeping forced landing times in step) but nothing is written.  `Session#close` finishes recordings.  Spec'd: start/stop frames and samples equal the mix at four buffer sizes; a FLAC's length and level.
- **Takes** (`Take#midi`, `Replay#midi`): the take saves the session's MIDI log since it started (`r.midi [[epoch, pos, bytes], ...]`, `input:` for named inputs; `take` counts the events); a replay puts its session in MIDI replay mode (`Session#replay_midi!`: every input, now or later, plays the rows on the frames of their positions in their epochs, never live input; `Replay#play` leaves it afterwards), so monitors, knob moves (`learn` lands on its recorded frame and only learns controllers moved from there), rec loops, and captures happen again on the same frames.  Spec'd (`take_spec.rb`): a performance with `arm`, `rec 1`, `learn :cut` and a CC sweep, and `capture :bass, 1, quantize: 16` replays bit for bit in memory and from the saved script at 800, 367/368, and 64.
- Names: `rec`/`record`, `stop_rec`/`stop_recording`, `arm`/`arm_track`, `disarm`/`disarm_track`, `armed`/`armed_tracks`, `capture`/`capture_midi`, `captures`/`recorded_clips`, `recordings`: no collision with `MB::Sound`, Object/Kernel, GraphNode, or Pry commands (spec).
- Limits: tracks that lead the beat (`lead:`/`nudge:`) close recordings `ahead` early, so the last `ahead` of the window isn't recorded; a seek during a recording keeps only the current epoch's events; no overdub (a recording replaces the track's clip); the MIDI log isn't trimmed while the session lives (~150 bytes per event); `knob ..., cc:` binds when the line runs (a replay runs it a little early).
