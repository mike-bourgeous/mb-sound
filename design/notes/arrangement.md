# Arrangement and the Session groundwork

<!-- summary -->
The Session groundwork: `Session::Stamp` (frame + Rational position), `Session::Journal`, and one change queue (`Session#change`) through which every command lands on an exact sample, with mute/solo, undo, launch points (`on:`/`in:`/`at:`), and takes that replay exactly at any buffer size.
On top, the Set layer (`MB::Sound::Arrangement`, `Session#arrangement`): `track`, `scene`, `go`, the clip matrix (`launch`, `tweak`), ring-outs, song forms (`flow` with labels, gotos, picks, fills), seeks, markers, knobs (`knob`, `turn`, scenes and sections turning them), clocks, and recording (`arm`, `rec`, `capture`, `rec_audio`).
Rules: changes go through `Session#change`; scene graphs build on the scheduler thread ahead of their landing and new graphs are warmed in a sandbox first; never enable a TracePoint in library code (YJIT drops its compiled code); Sessions keep one instance variable layout.
<!-- /summary -->

## Quick reference

- Set commands: `track`, `scene`, `go`, `launch`, `tweak`, `flow`, `knob`, `turn`, `arm`, `rec`, `capture`; launch points `on:` / `in:` / `at:`; `undo`.
- Every change goes through `Session#change` (an exact sample, under the render lock); specs use `Session.new(realtime: false)` + `#process_buffer` and close sessions in `after` blocks.
- Code `lib/mb/sound/session.rb` + `session/`, `lib/mb/sound/arrangement.rb`; specs `spec/lib/mb/sound/session_spec.rb`, `spec/lib/mb/sound/arrangement_spec.rb`, `spec/lib/mb/sound/take_spec.rb`; help `help :sets`, `help :flow`.

Phase 1 of the arrangement plan (branch `arrange-1`, 2026-10-10): the shared Session groundwork ("G0") and the Set layer.  Phase 2 (branch `arrange-form`, 2026-10-10/11): ring-outs, song forms (`flow`) with labels, gotos, and picks, performer controls, fills, the marker table, and the meter map (sections below the Set layer).  Phase 3 (branch `arrange-3`, 2026-10-11): knobs (K6), snapshots, MIDI learn, and tracks that lead the beat or nudge their notes (Knobs, below).  Phase 4 (branch `arrange-4`, 2026-10-11): recording (the Session MIDI input, `arm`/`rec`/`capture`, audio `rec_audio` (since omnibus6), takes that replay MIDI; Recording, below; `take.song` is later).  The summary block above feeds the generated index (`design/notes/README.md`, `rake docs:index`).  Update it when behavior changes.

Sources: the study on branch `research-arrangement` (`research/arrangement/README.md`, prototype in `prototype/`), the interconnect contracts K1-K10 on `research-plan-interconnect` (`research/plan-interconnect/README.md`), and the maintainer's decisions of 2026-10-10 (quoted below).

## Session groundwork (G0)

Built to the interconnect contracts so the terminal UI and glhtui can use it later; only what phase 1 needs is built.

- **Stamps (K1)**: `Session::Stamp` (`lib/mb/sound/session/journal.rb`) = `frame` (session frames since the Session was created; monotonic, never reset by seeks, rewinds, or tempo changes; `Session#frame`) + `pos` (Rational whole notes), plus `bar_length` for display only.  Shown as `bar:beat` (`9:1`, `13:2.5`), never parsed.  `Session#clock` is the stamp of the next frame (where a change made now lands); `Session#transport_record` is the per-buffer `{frame, pos, bpm, bar_length, playing}`.
- **Journal (K3)**: `Session::Journal` keeps up to 10,000 `Journal::Entry`s (`seq, kind, subject, issued, commits, lands, status, source, line, data, undoes`); status is `:queued`, `:landed`, `:cancelled`, or `:failed`, and a status change is a new entry with the same `seq` (`journal.entries` has all of them, `journal.changes` the latest per change, `journal[seq]`).  `subscribe { |entry| }`.  The render thread only pushes small notes onto a `Thread::Queue`; they become entries when the journal is next read or written.  Entries print as `bg :bass lands 9:1 (queued)`; `entry.name` is the subject.  Sources: `:console`, `:schedule`, `:replay`, `:undo`, `:set`.
- **Change queue** (`session/changes.rb`): every change to what plays goes through `Session#change(kind, subject, time, data:) { |t| ... }`: `add` (`:bg`), `remove` (`:stop`), `resume`, `swap`, `master`, mute/solo, `:restore` (undo), `:scene`.  A change landing now applies right away; a future one waits in a sorted queue (time, then issue order) and is applied at the start of the buffer that holds its time, on its exact sample (`commit_due`, after scheduled blocks run, before players render).  This fixed the study's finding 2: a clip source holds one pending swap and a player one stop time, so `swap :bass, b, on: 4` then `swap :bass, c` lost the first swap; queued graphs, stops, swaps, and master chains for one name now all land.  Validation errors (no such player, unrelated clips) still raise when the command is made; a queued change that fails when it lands is journaled `:failed` and printed (raised with `raise_errors`).
  - Changes apply under a render lock (a `Monitor` that `process_buffer` holds until the mix is done, released before `output.write`), so a console change lands exactly at the next buffer's start, and the journal says where.  Lock order: render lock, then the session mutex.
  - `players` lists graphs waiting to start ("starts at bar N") and queued stops; `idle?`, the timeline, and new player numbers count queued starts; a stop for now cancels queued starts of that name; a queued start after a queued stop plays (the old code dropped graphs that "would never have played").
  - `Session#queued(name)`, `#cancel_changes(*seqs)`, `#playing_after_queue?(name)`, `#timeline_nodes_of(name)`.
- **Launch points count from `Session#now`**: the scheduled block's time inside `at_bar`/`after`/`every` blocks (finding 1: `at_bar(5) { bg :x, g, on: :beat }` landed a beat and a half early, because the scheduler runs blocks up to half a bar ahead), a take's recorded issue time while it replays, and the transport position otherwise.
- **Command context** (session-core-1, 2026-10-30; arch-session review section 5; `session/context.rb`): who issued the commands running on a thread, and when, is one frozen `Session::Context` per thread (`Session.context`, nil before anything set one) instead of eight thread-local keys and two untyped Hashes (`Session.context` and `Session.perform`, which both answered "now").  Fields: the issuing context (`session`, `time`, `batch`, `source`; `Session.with_context(session:, time:, batch:, source:)` sets all four), a take replay or an undo (`perform_session`, `perform_source`, `forced` (a `Session::Forced` queue of the line's landings), `now`; `Session.with_perform(session:, forced:, now:, source:)` sets those given), the undo group (`command`, an `Undo::CommandGroup`), the take line being recorded (`take_line`), a replayed line's answers (`choices`), a scheduled block's deadline (`deadline`), the track whose patch builds (`patch_track`), and the replayed song script (`song_replay`).  `Session.with_context_fields(**fields) { }` sets fields for a block and puts back only those (as the separate keys did, so helpers nest in any order); `Session.set_context_fields` for the take line between Pry's hooks.  `Context#now_for(session)` (a replayed line's issue time, else a scheduled block's time; `Session#now`), `#time_for(session)`, `#source_for(session)`, `#replaying?`.  A scheduled block's deferred commands and the tempo a `bpm` in it queued are a `Session::Batch` (they used to be keys written into the context Hash).  `debug_dump` writes every thread's context (`contexts.txt`).  Other thread-local settings save/set/restore through `Internal.with_local(key, value) { }`; `spec/lib/mb/sound/session/context_spec.rb` lists every thread-local key in lib/, bin/, and gems/ with what it holds, so a new one is a decision (provenance goes in the Context).  The render path's keys (`:mb_sound_span`, plan deferral, `Steer.origin`) stay as they were.
- **Exact fades** (`session/fades.rb`): fades and mute ramps are `Fades::Ramp`s counted in session frames from their first sample (level `k * slope + from` at frame offset k, so any buffer size gives the same levels), and fade-outs start on the exact sample of their stop time (they used to start at the next buffer start) and end on their last frame: a fading-out graph is read up to that frame, not to the end of the buffer holding it (batch-fixes-1030), so its state when kept for resume/undo and what `only:` spies inside it wrote (a faded-out kit's kick tail into `duck(:t1, only: :kick)`, SessionFuzz seed 766044) are the same at any buffer size.  Levels are cast to SFloat before multiplying audio (Numo's SFloat * DFloat is ~20x slower).
- **Commands return journal entries**: `bg`, `swap`, `resume`, `master`, `mute`/`solo`, `go`, `stop`/`outro`, `forget` return the change's entry (an Array for several players; `panic` the stops plus the changes it cancelled; maintainer decision 2026-10-13, research-api-surface P9; inside scheduled blocks commands return names); `stop`/`swap`/`resume`/`mute` accept an entry in place of a name.  `stop`/`outro` take launch points (`stop :bass, on: :bar`; without one they land now or at the scheduled block's time).  `forget` is a `:forget` change (undo makes the player resumable again).  Every console command (and every scheduled block's batch) is one undo step (`Session#command(label) { }`).
- **Names (K2)**: `Session::Names` (`session/names.rb`): tracks, mute groups, and later knobs share one namespace; `:master` and `:cue` are reserved; a name claimed for two kinds goes through `MB::Sound.live_error` (maintainer decision 6).  `Names.path(:bass, :cut, 3)` is `"bass/cut/3"` (display and files only).  Names with structure (`:"lead/live"` a track's monitor, `:"lead/cue"` its cue player, `:"bass/level"` its level, `:"bass/cutoff"` a track param's knob, `:"dub/space"` / `:"bass/dub/space"` rack knobs) are built and taken apart only by `Session::Name` (s-names, omnibus17): `Name[x]` (cached frozen value: `owner`, `leaf`, `base`, `monitor?`/`monitored`, `cue?`/`cued`, `level?`, `strip_owner`), `Name.join`, `.monitor`, `.cue`, `.level`, `.param` (a param named `level`, `live`, or `cue` becomes `:"bass/patch_level"`), `.send_knob` (`:"keys>verb"`), `.monitored`/`.cued` (nil for non-Symbols).  It replaced `Arrangement::Recording.monitor_name`/`.monitored_track` and `Session::Cue.cue_name`/`.cued_name`/`SUFFIX` (so the Session layer no longer calls into the Arrangement for the `/live` rule) and about 12 `split('/').last` sites in the UI, help, Param, and Knobs; `spec/lib/mb/sound/session/name_spec.rb` fails on new hand parsing or building in lib/ and bin/.
- The player strip (K7) is complete since omnibus17: fade, gain (track levels, below), mute/solo, then routes (post-fader sends came with buses-1, 98a0c78d, `buses.md`).  Not built yet: the session stream (K4).  Markers (K8) arrived in phase 2, knobs (K6) in phase 3 (below).

## Mute and solo (`session/strip.rb`)

Maintainer, 2026-10-10: "Sleep; softmute now; use or extend existing fade functionality for synced fades or mutes".

- `mute`/`unmute`/`solo`/`unsolo` (Session and console) take player names or mute groups (`mutes :breakdown, :drums, :bass`, alias `mute_group`).  Right away by default with a 5 ms declick (`Fades::DECLICK_SECONDS`), or at a launch point (`on: :bar`, `in: 1.beat`, `at: bar(17)`) over a `fade:` in bars (a synced fade), through the change queue.  `solo` with no names clears every solo, and `unmute`/`unsolo` with no names everything, resolved when the change lands (subject `:strip`), so a solo still in the queue isn't missed (the demo render found this).
- Flags belong to names, so a graph replacing a muted one starts muted.  An armed track's monitor player (`:"lead/live"`) follows its track's flags as well as its own (omnibus6, agreed 2026-10-12: "mute :lead also mutes its monitor"): `mute :lead` silences the keyboard through the patch too, `solo :lead` keeps it audible, and `mute :"lead/live"` still mutes only the monitor (`Session::Name#monitored`, `Strip#audible_unlocked?`; `recording_spec.rb`).  The strip runs fade, then level, then mute/solo, then the routes (K7 order).
- A silent player sleeps: its graph isn't rendered (no CPU).  A mute ramp ending inside a buffer stops reading on its last frame, so oscillators fall asleep at the same sample at any buffer size.  On the unmute sample its timeline nodes restart there like after a seek (clips and tempo-locked tones come back in time); everything else is stale.  A sleeping player still reads its branches of nodes another player's graph also reads (`Strip#asleep_reads`, like a skipped Synth lane; fixes-9, 2026-10-13: the Tee left it behind and unmuting after more than a second raised `BranchBufferOverflow`), so those nodes run while anyone playing them sleeps, even if everyone does (decided 2026-10-13: a node shared only by muted players keeps running, its own cost only; the players' graphs still sleep); branches nothing in the Session plays (an unused `lfo * 2`) don't count, so they don't change what a muted player hears.  Graphs kept for `resume` or `undo` (stopped graphs, and replaced or forgotten ones the undo list still holds, at most `RETIRED_GRAPH_LIMIT`) do the same while kept (`Strip#read_kept_graphs`, fixes-10, 2026-10-13: resuming or undoing back to one more than a second after its stop raised `BranchBufferOverflow` when it shared a node with a playing graph): each reads its shared branches at the end of every span, for exactly the frames since its stop (`Player#read_to`, `KeptGraph`), and a graph playing again reads up to its first frame before it plays (`#catch_up_kept`), so it comes back in phase with the node at any buffer size.  Kept graphs count as Session graphs for each other and for sleeping players, so a node only kept graphs share runs too.  Each span drops graphs no longer kept (not in `@stopped` or the undo list's cached inputs, `Undo#undo_inputs`) or playing again; `forget` drops a graph once no undo step holds it.  Cost per 800-frame buffer (median, 2026-10-13, one playing LFO graph): ~0.45 us per kept graph sharing the LFO (64: 59 us vs 30.5 on master-ai), ~0.3 us per kept graph sharing nothing (64: 40 vs 21.5).  A new graph waiting to start (queued by `bg` while playing, which lands on the next bar; scene builds run up to two bars ahead; a player starting later in the span) isn't read, so before fixes-11 (2026-10-13) it played a node it shared with a playing graph late by its wait (0.3 s: 0.06 off for `lfo * 0.1`), and after more than a second its first read raised `BranchBufferOverflow`.  Now at the start of every span (after changes land, before players render, when every played branch is at the span's first frame) its branches of shared nodes (`Strip#asleep_reads`) skip to their Tee's leader (`Tee::Branch#catch_up`: discards exactly the frames the branch skipped, or gives an overflowed branch a new reader there), without running the node; on its first frame the player reads the span's frames before it on those branches (`Strip#catch_up_started`), so it starts reading the node on that frame at any buffer size, as if built then (specs: 0.3 s and 1.5 s waits, a queued replacement, a scene built ahead with a clip swap, at 128/801/7, 800, and 7-frame buffers).  :bg changes carry their graph (`Change#graph`); kept graphs (resume, undo) read instead.  `#asleep_reads` now counts a graph's own branches (ones no other graph reads) of Tees with another branch in another graph: before, a Tee counted only if one of its branches was outside the graph, so a muted graph playing `x * 0.1 + lfo * 0.1` while another played `x = lfo * 2` left its own `lfo` branch unread, and unmuting after a second raised `BranchBufferOverflow` (fixes-11 found it).  Cost per 800-frame buffer (median, alternating with master-ai): ~0.25 us per waiting graph sharing nothing (64: 44 vs 28.5 us), ~0.55 us per waiting graph sharing the playing LFO (64: 57 us vs 21.7 with none waiting; master-ai took 43.5 us copying the lagging branches through the Tee's CircularBuffer, and raised after a second).  Master chains take part too since fixes-12 (2026-10-14): running chains count as Session graphs, and chains waiting to start catch up like waiting graphs (see `master_effects.md`).
- Cost per 800-frame buffer (median, 2026-10-10): 64 constant players 1013 us unmuted, 55 us all muted (asleep), 1858 us all ramping (~13 us per ramping player); 64 ramp+lp4 tracks 2769 / 52 / 3698 us (`/tmp` bench in the arrange-1 report).

## Track levels (`session/faders.rb`, omnibus17, 2026-10-30)

The strip's gain stage (K7): every player name has a level, the Session knob `:"name/level"` (a linear gain, `0.0..4.0`, i.e. up to +12 dB; `Faders::LEVEL_RANGE`), made at unity the first time something sets it: console/Session `level :bass, -6.db` (launch points `on:`/`in:`/`at:`, `over:` ramps with `curve:`/`from:`, a knob name or node to follow), `turn :bass, x` (the track's name stands for it), scene and section values (`bass: -6.db`, `bass: [0.5, over: 1/4r]`, `"bass/level": x`), or a trigger track's route.  Being a knob, it is journaled (`:turn` changes), undoable, exact at any buffer size, replayed by takes (the console line), and saved by set documents (a `knob :"bass/level", (0.0..4.0).at(0.501...)` header line; levels print as plain gains since a plain range refuses `-6.db`).  A Session that never sets a level makes no knobs and renders exactly as before (`render_player` multiplies nothing at unity).

- Order: fade, level, mute/solo, then the routes (main out, sends, stems, CUE all post-level).  Readers (`duck(:kick)`, `bus(:kick)`) hear the player after its level and before its mute (the tap moved from fade to fade times level): so a trigger track's level, which was its own `Route#level` knob applied in `deliver_trigger` (0..1), is now this fader for every track, one mechanism.
- Levels belong to names: a graph replacing `:bass` plays at `:bass`'s level; an armed track's monitor (`:"lead/live"`) and a cue player (`:"lead/cue"`) play at their track's (`Session::Name#strip_owner`), so a launch from CUE keeps the level.
- Listings: `level` (every level set, name => Decibels), `level :bass` (a Decibels; `0.db` when unset), `track_info` and `now` ("level -6.0.db"), the tracks pane (`UI::TrackInfo#level`, "-6 dB").
- Name: `level` (checked against MB::Sound methods, GraphNode DSL, and Pry commands: none of `level`, `gain`, `fader` collided).  Picked over `gain` (Tone#gain is a DSL method inside oscillators, `master_gain` is pre-chain, and Player#gain is the internal fade level) and `fader` (a noun; `level :pad, 0, over: 8` reads as a mix move); it matches the knob's leaf and genre roles' `level:`.
- Genre roles' `level:` stay a multiply inside the patch (before its duck): moving them onto the fader would change saved set documents and template round trips and the float order of the patch's samples, and removes no mechanism (one line), so they don't map (yet).
- Not built: bus faders (a bus's chain scales), a dB-curve knob spelling for levels (the range is linear in gain, so arrow keys in the racks pane step linearly).

## Undo (`session/undo.rb`)

Maintainer: "Raw commands also, and yes, CPU permitting"; quantized to the next bar by default.

- Each change snapshots its subject as it lands: `PlayerState` (current Player, stopped Player, each clip source's clip, mute/solo flags), `MasterState` (the chain's block), `StripState` (all flags, for `:strip`).  `undo` issues `:restore` changes that put each subject back to its state before the step's first change, at the next bar (`on: :now` right away), through the change queue (exact, journaled with `undoes:`, replayed by takes).  Graphs come back as the same objects (stale state, as with `resume`) with a 5 ms declick crossfade; master chains are rebuilt from their blocks; Set state (track clips, current scene) through participants (`Session#note_undo_extra`, `Arrangement#restore_undo_state`).
- Subjects are registered (session-core-1, 2026-10-30; arch-session review section 3): each module owning an undoable kind of state declares its subject type next to the methods that snapshot and restore it, `Undo.subject MasterSubject, snapshot: :master_undo_snapshot, restore: :restore_master_change, symbol: :master`, and modules that claim changes by kind add `Undo.claim :bus_undo_subject, order: 20`.  `Undo#snapshot_subject(change)` tries the claims in order (CUE 10, buses and sends 20, seeks 30, knob turns 40), then the subject Symbols (`:master`, `:strip`, `:timeline`, `:tempo`, `:key`), else `Undo::PlayerSubject.new(name)`; `#undo_snapshot` and `#restore_change` dispatch on the subject's class.  The types: `Undo::PlayerSubject`, `Master::MasterSubject`, `Strip::StripSubject`, `Seeks::TimelineSubject`, `TempoChanges::TempoSubject`, `KeyChanges::KeySubject`, `Knobs::KnobSubject`, `Buses::BusSubject`/`SendSubject`, `Cue::CueSubject`.  Before, Undo's ladders of `if subject == ...` were extended by Buses and Cue overriding the three methods and calling `super`, which worked only in one include order.  `spec/lib/mb/sound/session/undo_subjects_spec.rb` fails a new `*Subject` type without a registration and a module defining the three methods again.  (Buses and Cue still extend `Strip#audible_unlocked?`/`#apply_strip` through `super`.)
- A step whose changes haven't landed (by the logical time, `Session#now`) is cancelled right away; `redo!` queues them again.  Undo and redo are symmetric (each pushes the reverse step on the other list).  Steps print as `undo go :drop lands 9:1`; `changes` lists them (`history` is a Pry command).
- Bounds: 64 steps, and at most 8 retired graphs (neither playing on nor resumable) held by the lists (oldest steps dropped).  Measured live heap (`ObjectSpace.memsize_of_all`) with 8-voice `sq80_voice` Synths replaced 16 times: 13.6 MB at limit 0, 74.7 MB at 8, 134.6 MB at 16, i.e. ~7.5 MB per retired graph, ~60 MB worst case at the bound.  A snapshot of that player takes 4 us; a console mute with journal, snapshots, and pruning ~170 us.
- Later (graph-io): undo could keep recipes instead of live graphs.

## The Set layer (`MB::Sound::Arrangement`, `lib/mb/sound/arrangement.rb`, console `ArrangementMethods`)

Maintainer: "Yes, with a realtime demo script that shows a set being sculpted".  One `Arrangement` per Session (`Session#arrangement`).

- `track :bass, q: 1 do |clip| patch end` (`track :bass, q: 1 do |clip| ... end`; alias `define_track`) or `track :pad, graph`: a named player remembering its patch or graph, its clip, launch quantization `q:`, and `fade:`.  `bg :bass, clip` on a track with a patch builds the patch with that clip.  `tracks` lists them.
- Clip names (maintainer, 2026-10-11: ".named 100%"): `seq(...).loop.named(:bass_a)`, `grid(...).named(:beat)` (`Sequence::Named` on Clip, Seq, Kit: `named`, `name`, `named?`).  Listings (`tracks`, `scenes`, player descriptions) show the name, else the kind (seq, clip, kit); `Arrangement#label` is gone (the flow's `label` is the only label).  graph-io records `named` on clips and kits, so `to_ruby` prints it and uses it as the variable name (kit chains print since graph-io-3).  `save :gig, set` / `preset :gig` save and reopen the Set layer as a `kind: :set` graph document (graph_io.md, Phase 3; scene blocks are left out).  A name belongs to its object: `bass_a.transpose(12)` has none until named.
- `scene :verse, pad: chords, bass: bass_a, drums: beat` (`scene :drop, bass: b, drums: beat`; alias `define_scene`): a full state; values are a Clip or Kit, `:on`, `:off`/`nil`, `:cut`, or `:keep`; tracks not named stop unless `others: :keep` (partial scenes like fills and risers), except trigger tracks, which play on through scenes that don't name them (omnibus17, Munro's M5: a hand-built set pumped only until its first `go`; `pump: :off` stops one; `Arrangement#unnamed_value`, also the clip matrix's cells); a block runs at launch with commands landing at the launch time.  Stopping tracks ring out (phase 2, below) unless `others: :cut` (or the value `:cut`) or a fade.  `scenes` lists them (current one marked).
- `go :drop` (alias `launch_scene`, `on:`/`in:`/`at:`, `fade:`): each track changes at its own launch point (the call's `on:`/`in:`/`at:`, then the track's `q:`, the scene's `q:`, the set's `quant`, 1 bar by default).  Only differences change: a patch track already playing swaps clips (keeping graph and effect state), rebuilding when swap can't map the clips or a Kit brings rows the old kit lacks (rows the new kit lacks swap to a silent loop, so they stop: patches-5, 2026-10-13, found by genre :dnb's hats-only breakdown, which kept the drop's kick and snares); a track playing the scene's clip is left alone; stops ring out (phase 2) unless the scene says `others: :cut` (5 ms declick) or the scene, call, or track gives a fade.  One undo step; returns the `:scene` journal entry (`scene :drop lands 13:1 (queued)`).
- Library instruments (library-instruments-1, 2026-10-28; library.md, Instruments on tracks): `track :bass, L.inst.dnb.dnb_reese`, `track :bass, :dnb_reese`, `track :bass, riff, :dnb_reese` (the clip is the track's clip; either order) are patches built from the track's clip (`Arrangement::InstrumentPatch`); effects raise with where they go; resonator effects play as struck instruments.  Giving a playing track another instrument (`track :bass, :jungle_reese` again) builds it at its launch point in one `Session#command` (`Arrangement#change_instrument`: journaled, one undo step `track :bass -> L.inst.jungle_reese`, routing kept); redefinitions with a patch block still take effect at the next launch (as before).  `swap :bass, L.inst.x` explains the difference.  A graph document the patch loads makes its params the track's knobs (`:"bass/cutoff"`, `Arrangement::TrackKnobs`; Arrangement.counted runs every track patch inside `TrackKnobs.building`); set documents print instrument tracks as `track :bass, :dnb_reese, q: 1` and the knobs as header lines.  Session fuzz songs use library instruments and change them mid-song (`SessionFuzz::INSTRUMENTS`).
- Track and scene `q:` and `quant` are alignments (`on:` values): `:now`, `:beat`, `:bar`, `:clip`, a Duration, or a number of **bars** (fades are bars too).
- Scene keys naming a non-track (e.g. a mute group) go through `live_error`; unknown tracks raise at `go`.
- Scene keys naming knobs turn them at the scene's launch point (Knobs, below).  Tracks take `lead:` and `nudge:` (below).  Forms are below.

## Launch points: `on:`, `in:`, `at:` (`lib/mb/sound/launch_point.rb`)

Maintainer, 2026-10-10 ("Do we have a name for alignment vs placement elsewhere? Eg on vs in"; "Yeah, make that change in bg"): `at:` used to mean alignment everywhere with different units (`bg ... at: 4` was the next quarter note, Set `at: 4` the next 4-bar line).  Now every command that lands a change (`bg`, `swap`, `resume`, `master`, `mute`/`unmute`/`solo`/`unsolo`, `go`, `undo`/`redo!`, their Session methods, `Arrangement#go`/`#play`) takes three keywords, and plain numbers are bars everywhere:

```ruby
go :drop, on: :bar                # alignment: :now, :beat, :bar, :clip, 4 (bars), 1.n4, 2.beats
go :drop, in: 2.bars              # relative placement from Session#now (bars, Durations, Lengths)
go :drop, at: bar(33)             # absolute placement: bar(n, beat: 1), counting from 1 like at_bar
go :drop, in: 2.bars, on: :beat   # two bars from now, then the next beat
```

- Order: start from `Session#now`, add `in:` or jump to `at:`, then align forward to `on:` (ceil; a time already on the grid stays).  Without `on:`, a change still aligns the way it would without `in:`/`at:` (maintainer, 2026-10-10: "Tracks should keep the same time alignment they would have otherwise"): `bg`/`swap`/`resume`/`master` to `:now` if idle, else `:bar` (so `bg :x, g, in: 2.bars` lands on the bar line after two bars while something plays); Set tracks to their effective `q:` (track, scene, `quant`), each on its own; mutes/solos not at all (exactly at `in:`/`at:`, right away without them); `undo` to `:bar`.  Write `on: :now` for an exact offset or position.  Take replays force recorded landing times, so they stay exact.
- `at:` takes only `bar(n)`/`bar(n, beat:)` (and alignment Symbols as aliases of `on:`, "at the bar").  Through `live_error`: a plain number (suggesting `on: 1.n4` / `on: 4` / `in: 4` / `at: bar(4)`), a Duration or Length (maintainer: "Agreed"; `at: 32.bars` would have been bar 33; the message points to `bar(n)`; they stay valid in `in:` and `on:`), `at:` with `in:`, `at: :bar` with `on:`, `in: bar(n)`, and a position that has already passed (maintainer: "live_error"; live, it warns and lands now; a replaying take lands it now silently, where the take forces it).  `at_bar` blocks keep warning and skipping for passed bars (unchanged: raising there could break scripts that schedule blocks after playback has moved on).
- One resolver: `LaunchPoint.of(binding)` reads the keywords (the only place that reads the `in` keyword), validates, and returns a frozen `LaunchPoint` (nil if skipped in live mode); console methods pass it down as `at:`; `Session#launch_time(point, nodes, default:)` and `Arrangement#resolve(q, track, point)` (the effective `q:` as the default alignment) call `LaunchPoint#resolve`.  Landing samples are unchanged for equivalent inputs (old `at: 4r` = `on: 4`; the take replay spec still matches bit for bit).
- Name check for the console `bar(n)` (`ScheduleMethods#bar`, returns `LaunchPoint::Bar`): no collision with `MB::Sound`, `Kernel`, `GraphNode`, or Pry commands; `Numeric#bar` (`1.bar`, a Duration) lives on a receiver.

## Ring-outs (`Session::Tails`, `lib/mb/sound/session/tails.rb`, phase 2)

Maintainer, 2026-10-10 ("Queue ringdown for p2"): when a scene drops a clip-driven track, the clip stops sending notes, the graph keeps rendering until it is silent, capped, then the track sleeps.

- `Session#remove(name, ring: true)` (`remove(ring: true)`; console `stop :bass, ring: true`, `stop :x, ring: true`; the Set's default for tracks a scene stops): on the exact sample of the stop time every `MIDI::ClipSource` in the graph swaps to `Clip.silent` (notes in progress get note-offs there) and the player keeps rendering.  It sleeps (retired and kept for `resume`) once its output stays below `Master::TAIL_THRESHOLD` (-90 dB) for `RING_QUIET_SECONDS` (= `TAIL_QUIET_SECONDS`, 1 s), cut on the sample where that stretch ends, so the sleep frame is the same at any buffer size (spec: 800, 367, 64).  The graph is read in pieces that end where the quiet stretch would (omnibus13), so it sleeps having rendered exactly to that frame: before, it rendered to the end of the buffer, and a graph revived later (a scene relaunching the track) carried a buffer-size-dependent state (SessionFuzz seed 1194: a tr808 kit relaunched by `go`, differences up to 0.24 between 367- and 800-frame buffers; now bit-identical).  After `Master::MAX_TAIL_SECONDS` (10 s) a `TAIL_FADE_SECONDS` fade starts on that exact frame.
- The real clips come back when the player sleeps (`ClipSource#ring_out`/`#end_ring_out`/`#ring_clip`); swaps and undo snapshots see the ring clip, and a swap of a ringing source changes the clip it will play again.
- Graphs without clip sources (drones, files, raw oscillators) fade over `RING_DRONE_FADE` (1/4 bar).  Graphs whose sound doesn't come from notes but that do read clips (a `tween`-driven riser) ring to the cap: give their track a `fade:` (the demo's riser does).
- Launching the same graph while it rings (resume, undo, a scene bringing a patch track back with the same clip, a graph track) revives the ringing player (no second copy; its notes come back at the launch).  A later cut or fade takes over from a ringing tail; a muted ringing player sleeps right away.
- Journal: the stop's data is `{ ring: true }`; a `:rung_out` entry (source `:session`, data `seconds:`, `capped:`) is noted from the render thread when the tail ends (`Journal#note_entry`).  `players` shows "(ringing out)".  Takes replay ring-outs exactly (the stop's landing is forced; the tail is the graph's own output).
- Cost (2026-10-10, 800-frame stereo buffers): following one ringing player 12 us per buffer (fast paths for silent buffers and buffers ending loud; 42 us before them); the graph's own render as before.

## Scene builds (branch `scene-build`, 2026-10-12)

Measured by the demo-song-2 agent: scene changes built their graphs for 200-350 ms per one-voice synth, up to 0.75 s per scene in Small Talk (`bin/songs/small_talk.rb`, branch demo-song-2) and 1.56 s in `night_bus_flow.rb`, against the scheduler's half-bar lookahead, and the render thread stalled up to ~200-270 ms where a change landed.  A profile (scheduled blocks timed by phase, every render buffer with YJIT's counters) found where the time went:

- **YJIT invalidation (the render stalls).** Recipes read build block locals with a `TracePoint(:b_return)` targeted at each block call (every synth lane, feedback loop, unison), and enabling any TracePoint makes YJIT discard all compiled code (`invalidate_everything`).  The render thread then recompiled every playing graph's code: 50-120 ms buffers right after each build.  Now the recorder takes the Binding of the block's frame through the VM's debug inspector (`FastRecipe.frame_binding`, ext `fast_recipe`) and reads the locals after the block returns (graph_io.md, Recording).  Rule: library code never enables a TracePoint.
- **Graph traversal.** `GraphNode.graph` moved revisited nodes to the end of an Array with `delete` (O(n) each): ~52 ms per traversal of night_bus_flow's 1431-node pad, three traversals per build.  An insertion-ordered Hash gives the same order in ~5 ms.
- **First-use compiling.** With YJIT, a patch's first build costs 5-20x later ones (night_bus_flow drums 107 -> 19 ms, the pluck answer ~100-150 -> 25-31 ms; without YJIT the first build is no slower), and a new graph's first buffers compile its sampling code on the render thread.  `Arrangement#warm_up` builds every patch track with each clip its scenes give it in a sandbox Session (its own transport at the session's tempo and meter, copies of the knobs, current while the patch runs), adds it there and plays half a bar, then drops it.  Patches that reach nodes made outside them (detected by building twice and looking for shared nodes) are only built, since playing them would advance nodes live graphs read; the root random generator is restored, so seeds drawn later are unchanged (only while idle: `with_seed` swaps the generator for every thread).  `play_form` runs it in an idle realtime session with YJIT (`warm_up: :auto`) and prints one line ("Warmed up 12 tracks in 2.0 s", noting tracks only built); `flow(warm_up: false) { }` skips it (maintainer, 2026-10-12: on by default with a note and an option); console `warm_up(tracks: true)`.  Full renders of both songs are sample-identical with and without it (and to master-ai).  Cost before the music starts: ~2 s for night_bus_flow (12 tracks), ~1.8 s for Small Talk (8).  With a form (`play_form`), tracks are built but not played alone, and the form's rehearsal plays them instead (Transition compiling, below).
- **Schedule handles and the scheduler's panic button** (maintainer decisions 2026-10-13): `at_bar`/`after`/`every` take launch points (`at_bar in: 2.beats`, `at_bar 9, on: :beat`, `after 2, on: :beat`, `every 1.n4, on: :beat`, `every 4, at: bar(9)`; `after`/`every` count from `Session#now`) and return a `Session::Scheduler::Handle` that prints the command and when it runs (`at_bar 9 runs 9:1`, `every 4 runs next 5:1`, `... ran 9:1`, `... cancelled`) and has `#cancel`; `scheduled` lists handles, `cancel` takes handles or ids (none: every block `ScheduleMethods` scheduled).  Entries have an owner (`:user`, `:form`, `:take`, `:script`) and a status (`:pending`, `:due` once handed to the runner up to the lookahead early, `:running`, `:ran`, `:cancelled`); a block cancelled while due doesn't run.  `reset_scheduler` (console) / `Session#reset_scheduler` stops the song form, cancels every block except a take's replayed lines (so a recorded `panic` replays without cancelling the take), and on a realtime session replaces a dead scheduler thread, or one whose block is still running after `Scheduler::RESET_WAIT` (1 s) more (`Thread#raise`, then `#kill`; a fresh thread takes the queue), printing what it did.  `panic` does the same, cancels every change still waiting to land, and stops the players, always printing one line (`panic: stopped 2 players; cancelled 1 queued change; ...`; maintainer decisions 2026-10-13: panic cancels everything, one summary line always); the end of a script's `--bars` resets the scheduler too.
- **Scheduler.** Blocks run `Session#lookahead` ahead (`:auto`: half a bar, or twice the slowest of the last 16 blocks plus 0.1 s, up to 2 bars; a number of bars or a Duration; renders always half a bar, so they don't depend on timing).  Blocks still running at their time are listed in `Session#late_blocks` and go through `MB::Sound.live_error` (maintainer, 2026-10-12: warn live, raise in scripts; branch scene-build-2): in live mode each change such a block makes after its time warns (`Session::LateChange`) and lands right away, late, and the block's end warns (`Scheduler::LateBlock`); in scripts and specs the first such change raises `LateChange` before it lands (nothing journaled; the block's earlier changes stay) and a block that only finishes late raises `LateBlock` (printed by the scheduler thread, raised with `raise_errors`), so a song script drops a late scene change with an error rather than playing it late.  Either way the commands a late block collected for its time (`bg` etc. inside `at_bar`) are skipped, and blocks that run when their time has already come (nothing playing) aren't late.  The scheduler thread runs at Ruby priority -3, so a long build gets short time slices and the render thread waits less for the GVL; the render thread runs at 3 (`Session::RENDER_THREAD_PRIORITY`, ux-fix-2), since at 0 a timer tick inside a player's read handed the GVL to a building scheduler thread for a whole 10 ms slice (Linux, no YJIT, night_bus_flow's pickup build: drums' 10-buffer read average 23.4% for 5.6% of CPU; the slow-player warning blamed the player on the slower Mac).  Caches of what sleeping, kept, and waiting graphs, skipped drum voices and Synth lanes, and sub-lanes keep reading are kept while the Tees they read keep their branches (`GraphNode::BranchWatch`, per-Tee `branch_version`) and, for Session graphs, while their node sets keep their structure (`GraphNode.structure_changes`, counted by `Plan.changed` for nodes of Session graphs) and the graphs stay the same, with each graph's nodes listed and counted once per set of graphs (`Strip#asleep_index`).  Before (keyed on `Tee.branch_changes`, every Tee's), every branch the scheduler thread made for the next scene rebuilt them all, each buffer of a build: render-thread CPU per 512-frame buffer at the pickup build up to 52 ms (45 ms of it these rebuilds) -> 2.4 ms; with an emulated 0.7 s build (a Mac-like slow build) ~20 ms per buffer -> ~1.5 ms.
- Building on a background thread was already the case in realtime sessions (the scheduler thread); the render thread only swaps prepared graphs on the landing sample through the change queue.  Plan install was not the bottleneck once compiled: `Region#compile` + `Installation#build` ~10-30 ms for the biggest scene, so programs aren't cached across lanes yet.

```ruby
flow do intro 8; label :top; verse 8; chorus 8; pick verse: 3, chorus: 1; goto :top, times: 1; outro 8 end   # one line

flow do
  fill :turn, every: 8              # a phrase fill (below)
  intro  8
  label  :top                       # a target, takes no time
  verse  8, times: 2
  chorus 8, fill: :roll
  pick   verse: 3, chorus: 1        # plays one of them, then carries on
  drop   16, fill: [:riser, 4]
  goto   :top, times: 2             # back to :top twice more, then fall through
  outro  8                          # the end of the order ends the form
end

flow do                             # generative, never ends
  label :a; groove 8
  pick do |p|                       # groups, or nothing
    p.option(2) { hook 4; hook }
    p.option(1) { stab 2 }
    p.option(1) { }

Lengths are Durations or plain numbers of bars (counted through the meter map where the section starts; Durations are fixed whole notes).  Trap: `verse 8.bars * 2` is one 16-bar verse (spec'd).

### Decisions, commit points, and controls

- Commit point of a pass: the start of its fill, else its end (the bar line where the next section starts).  The decision there is the next pass of the section (`times:`, `loop!`), else a walk from the next instruction through labels, gotos, picks, and jumps to the next section (a `Playback::Step`).  Controls issued before the commit point (by logical time, `Session#now`) change that boundary; after it, the following one.  The decision runs in a scheduled block, which the scheduler runs up to half a bar early; a control arriving after the block ran but before the commit point re-decides it (the queued fill scene is cancelled and the Set state restored), so the boundary a control applies to depends only on its time and takes replay the same way (spec: a goto inside the lookahead window replays bit for bit at 800 and 367/368).
- Decisions are pure: goto counts are copied into the Step and adopted when the next pass starts, so a re-decided commit starts from the same counts.
- Chance: one `Random.new(seed * 1_000_003 + passes played)` per decision (several picks and weighted gotos in one walk draw in turn), the seed from `MB::Sound.next_seed` (takes restore the root generator) or `flow(seed:)`; live, replayed, and re-decided commits draw the same numbers.  The demo's pick draws exactly what its old `next: { breakdown: 3, drop: 1 }` drew (2026-10-11: the full seed-1 track and the seed-12 branch through bar 54 render sample for sample the same as before).
- Console (`FormMethods`; names checked against `MB::Sound`, Object/Kernel, and Pry's commands, spec'd): `loop!` (alias `loop_section`; repeats the section until `onward`, alias `unloop!`, `continue_form`; the maintainer: "loop! preferred over hold, you pick the inverse name"), `goto :x` (`goto_section`; a label: the flow carries on from it; a section: its next appearance in the order, wrapping), `finish` (`finish_form`; the last section in the order next), `skip` / `skip :x` (`skip_section`; leave at the next bar line or a launch point, `skip on: :beat`, `skip :drop, in: 2.beats`, never at the pass's own start; honors a pending goto/finish, ends a loop; the timeline keeps running; returns a `:skip` journal entry, which isn't an undo step), `practice :x` (`rehearse`; goto + loop!), `seek :x` (below).  `loop!`, `onward`, `goto`, `finish`, `practice` stay boundary-based and return a `Playback::Decision` (`next :c at 5:1 (open)`) (maintainer, 2026-10-11: "Ok"). ### Fills

- A section's `fill:` plays in its last bar by default (`fill: :roll`), for a length (`fill: [:riser, 4.bars]`), alternating names per pass (`fill: [:a, :b]`, `[:a, :b, 2.bars]`), or only when leaving (`fill: { names: [:z], on: :leave }`; default `on: :pass`, every pass including `times:`, `:again`, and `loop!` repeats).  A fill whose name is a scene launches it at the fill's start (a partial scene like a riser; the next pass's scene, a full state, takes it away).  The fill is set at the commit point.
- Phrase fills: `fill :big, every: 16` (`length:` default 1 bar, `layer:`) in the flow plays fill `:big` at the end of every 16 bars from each section's start.  Only clips with fill marks react (no scenes: nothing would take a scene away mid-section).
- `Sequence::FillMap` (`Transport#fills`): intervals with priorities; a section's fill beats phrase fills, a longer period beats a shorter one ("Fizzbuzz for drums almost"), `layer: true` plays alongside.  A form prunes fills that ended over a whole note before each section start.
- Note marks (Elektron's FILL condition; `sequences.md`): `Event#fill_mark` / `Seq::Step#fill_mark` = `[:fill or :nofill, name]`; `C4.fill`, `C4.fill(:big)`, `.nofill`, `Seq#fill`/`#nofill`, `Clip#fill` with no argument or a Symbol (`fill(span)` still repeats to a span), `Clip#nofill`, `Kit#fill(name, rows / Kit / block)` layering fill rows onto the kit (`beat.fill(:turn) { grid(16, clap: '....X...x.x.xXXX') }`), `Kit#nofill(*rows, name:)`.  `Clip#edges(fills:)` keeps or drops marked notes by the fills at each note-on (`ClipSource` maps clip positions to the timeline); without a form nothing is a fill.  Cost: 26 us vs 25 us per 800-frame read of a 16-step marked row (177 us before only events in the window asked).

## Seeks (`lib/mb/sound/session/seeks.rb`)

Maintainer, 2026-10-11 ("Cool"): seek goes through the change queue with launch points, returns a journal entry, is undoable, and replays exactly from takes.

Position spellings (ui-api-1, 2026-10-18; maintainer: "`seek` should take any position spelling"): `Session#seek_position` dispatches through `ArgTypes.classify`: bar numbers (`17`, `2.5`, Rationals) and `bar(12, beat: 3)` (`LaunchPoint::Bar`) count from bar 1; `seek 11, 2` is bar 11 beat 2 (quarter-note beats); lengths (`12.bars`, `43.n16`, `32.seconds`, samples; tempo-dependent ones at the current tempo when the seek lands) are offsets from the start of the timeline, so `12.bars` lands on bar 13 (a counter from 0; open question for the maintainer); names as before.  Anything else raises listing the spellings.

Transport (ui-api-1): `start` (`start_playback`; also `play`, `go` with no arguments) plays on a paused realtime Session, else plays the loaded flow (`Arrangement#last_form`, which a demo's set loading builds, else `demo_document.form`) when none is playing, else says what plays (`TransportMethods::Status`).  `pause` (`toggle_playback`; NAV Space in the tiles runs `start` or `pause` as a take line, `TransportMethods.toggle_line`) toggles `Session#paused=`, starting instead when nothing has started; in renders and take replays only the start part happens.  A bare `play` line isn't foreground in takes (`Take::TRANSPORT_PLAY`).  Ending a flow: `Form::Playback#end_at(time)` stops sections from beginning at or after `time` (dropping a pass the scheduler began early and a fill commit after it); `outro`/`stop :all` call it at their launch point, and a console `go :scene` while a flow plays seeks within the flow (maintainer, 2026-10-18: "Seek within the flow"): a :seek change to the next section that plays the scene (`Playback#section_for_scene`: the first forward of the current section in the play order, else the nearest behind; maintainer: "Always forward if present, nearest back if not"; `go :drop, section: :drop2` picks one by name, a live_error listing the choices otherwise) at the scene's launch point (its `q:`, else the set's quant), the flow playing on from there; a scene no section plays launches and ends the flow where it lands ("you're driving").  Not undoable yet: undoing the outro brings the players back but not the flow.  `panic` with a launch point is a live_error naming outro/finish.  `flow` with no block shows the playing flow (`Playback#show`: sections with the current one in brackets, steer and end commands), else the loaded Form after a line saying `start` plays it.

```ruby
seek 17                  # bar 17, now (the default alignment)
seek :top, on: :bar      # a form label at the next bar line
seek :drop, in: 2.beats  # a form section; markers work too
undo                     # back where the timeline was when the seek landed (at the next bar)
```

- `Session#seek(target, at:, start_time:)` issues a `:seek` change (subject: the target); console `seek` (SequenceMethods) is one undo step and returns the entry (`seek :top lands 13:1 (queued)`).  Targets are checked when issued and resolved when the seek lands: a section or label of the playing form (`Playback#seek_now`), a marker, or a bar number through the meter map.
- A seek to a bar or other position inside a playing form (generative-g4, 2026-10-29) plays the form on from the pass an uninterrupted run plays there (`Playback#seek_position` with the playback's `Form::Plan`: the pass's scene launches at the seek, mid-section, and its boundary is where the run's is; decisions after it count passes as the run did, `@decision_offset`, so they draw what it draws; a position past a finite form's end ends it).  Before, the timeline moved and the form kept its scheduled boundary (a backward seek made the current pass that much longer).  Performer controls aren't replayed (the run is the form as written); goto Procs see what actually played.  The plan is worked out to the target when the seek is issued (`Playback#prepare_seek`, the console's thread), so the landing only adopts the pass (~25 us a pass to work out: an hour into the endless ambient, 6 ms).  `seek :x` for a section only generate steps play seeks to where the run next plays it.  `rewind` stays a direct reset (spec cleanups and scripts use it).
- Exact frames: `process_buffer` renders in spans; a timeline change landing inside a buffer splits it (`frames_before_seek`: the first frame at or after its time), `commit_due` leaves timeline changes for the start of the next span, and `commit_due_seeks` lands them there after any change due before them in queue order.  A change landing now first lands queued changes whose time has come between buffers (a buffer ending on their bar line, or a seek that landed now), in queue order (`Changes#commit_queued_due`, outside the console command's undo step; fixes-ui-specs, 2026-10-17: arm_state_spec's walk with seed 11181 queued `go :both` for 2:1, then `seek 2` and `go :none` landed at 2:1 now, and the scene's swap of the stopped `:y` failed on the next buffer).  Rule: at equal times, issue order, wherever a change is committed.  The rest of the buffer renders from the new position (players' timeline nodes restart as after any seek).  Spec: a seek at `bar(3, beat: 4)` and its undo land on the same frames at 800 and 367/368 buffers, sample for sample.
- Seek actions run outside the take line that issued them (`Seeks#without_command_or_line`; generative-g4): a seek landing now inside its line restarts the form there, and the take recorded the form's scene launches as the line's landings (in the next epoch), so replays ran the line early; the form makes them again when the replayed seek lands.
- Undo: the `:seek` change snapshots the timeline (`TimelineState`: the position where it landed, and the form's pass, or the pass before one the scheduler launched ahead).  Undo issues a `:restore` change of subject `:timeline` (also a timeline change, so exact) that seeks back there and resumes that pass of the form (`Playback#restore_seek`, without adding it to the history).  Changes the form makes while restarting belong to the seek, not to an undo step of their own.
- Takes: `Session#epoch` counts timeline changes landed; positions repeat after a backward seek, so take lines record the epoch they were typed in (`r.line ..., epoch: 1`), replays schedule them for that epoch (`Scheduler` entries take `epoch:`), and render until the end position in the last epoch (`ends_epoch:`).  The take spec seeks back from bar 12 to bar 3 and undoes it, bit for bit at 800 and 367/368.
- A started player whose start a backward seek moved ahead of the timeline waits, then plays again from the sample holding its start, as on its first start (its timeline nodes restart there with their origin; omnibus16: clipless graphs restarted at the start of the span holding it, up to a buffer early at 367 frames; session fuzz step "seeks back across a clipless part's start").  They restart there also when the start is a span's first sample (batch-fixes-1030): a waiting graph isn't read, so until then a loop starting on an 800-frame buffer's edge played from where the seek had put it, behind the timeline by the time it waited (a beat late in SessionFuzz seed 766010, on time at 367 frames, which put the start inside a span).
- Not handled: changes queued for times after a backward seek's landing (e.g. `go :x, on: 4` issued before it) land when the timeline reaches their time again; a skip line replayed ahead of time (lines run up to half a bar early) sees the form state of that moment, not of its issue time, if the form commits in between (seen when a skip was issued between a seek and its landing; avoided in the spec).

## Knobs (`lib/mb/sound/graph_node/knob.rb`, `session/knobs.rb`, console `KnobMethods`; phase 3, K6)

- Implicit knobs (omnibus9, 2026-10-18; the maintainer's ux-r4 note 5): in live mode (`MB::Sound.live?`) `Session#knob(name)` for an undefined name defines it (`Knobs#implicit_knob`: `IMPLICIT_DEFAULT` 0.5 of `IMPLICIT_RANGE` 0..1, `GraphNode::Knob#implicit`, `knob_info` says so, a one-line note); a later `knob :x, value, range:, curve:` respecs it as a new knob would (the placeholder range doesn't carry over) and moves it to the new default, keeping its readers.  Scripts and specs stay strict (the ArgumentError naming the knob and how to define it, which patch checks report).  The default doesn't come from the reader's context (a `knob(:x)` call can't see where its reader goes).

Maintainer, 2026-10-10: `turn` for knobs with `move` as an alias; tracks, groups, and knobs share one namespace (collisions through `live_error`).

```ruby
knob :cut, 800, range: 100..8000, curve: :exp, unit: 'Hz'   # define (again: new options, same value and readers)
bg :bass, bass.tone.saw.lp4(knob(:cut))                     # a GraphNode anywhere a node goes
turn :cut, 3000                          # now, with a 5 ms glide (smooth: 0 for an exact jump)
turn :cut, 400, over: 2.bars, curve: :smooth, on: :bar      # ramps: bars, Durations, Lengths; any Curve
turn :cut, 2600, from: 900, over: 8      # jump to 900, then ramp
turn :cut, tween([400, 8000], 8.bars)    # follow a node (or follow: :other_knob) until turned again
move :cut, 1200, in: 1.beat              # move is turn
scene :drop, bass: b, cut: 8000, space: [0.5, over: 2]      # knob values in scenes (a value, or [8000, over: 2] to ramp)
flow do; drop 8, cut: 8000; end          # and in sections (turned as each pass starts)
snap :dark; recall :dark, over: 4.bars   # snapshots of every knob
knob :morph, 0; xfade :dark, :bright, :morph; turn :morph, 1, over: 8   # a crossfader (xfade :a, :b, 0.3 for a fixed amount)
learn :cut                               # the next MIDI controller moved (knob ..., cc: 74 for a number)
```

- **The node** (`GraphNode::Knob`): a `Knob::Spec` shaped like `MIDI::ControlSpec` (name, default, range, curve `:linear`/`:exp`, unit, cc, takeover `:pickup`/`:jump`, smooth).  Its value is a function of the session frame: segments starting on exact frames (`Hold`; `Ramp` over N frames in the knob's scale, octaves for `:exp`, shaped by a Curve, the value on frame start + j being `from + (to - from) * curve((j + 1) / length)` and exactly `to` on the last frame; `Follow` a node, clamped to the range or mapped).  Ramps start from the value on the frame before they land (or `from:`).  Same values at any buffer size (spec'd at 1, 7, 128, 800, 367/368 standalone; 800, 367, 64, 1001/13 in a Session).
- **Readers**: `get_sampler` returns a new `Knob::Reader` per consumer (no Tee).  The Session advances every knob once per span, after `commit_due` and before players and master effects (`advance_knobs`, `Session#knob_frame`), and readers return that span's values (a frozen buffer; a cached view for a shorter read).  So knobs drive any number of graphs, including sleeping (muted) players, without falling behind.  A player starting or waking partway through a span reads from its own first frame: `render_player` sets `knob_frame` to it around the graph's read, and `Knob#read` serves any part of the span; further reads in the same span (a Synth lane read in pieces around idle stretches) continue from the reader's own count, and skipped Synth lanes read their knob readers as boundary nodes (fixes-7, 2026-10-13: readers used to start at the span's first frame, so a player launched or unmuted mid-buffer read the knob up to a buffer early, -18 dB in a persona take's harp at 367/368 vs 800).  Outside a Session readers count their own frames (a new reader starts at the block being read).  Oversampled reads (more frames than the span) aren't supported.
- **Plans**: readers describe themselves as `p.param` (`plan_param` gives a Float while the knob holds still over the block, else the block's buffer), so planned graphs keep fusing; plan check mode (`MB_SOUND_PLAN_CHECK`) reads the same cached block twice.
- **Changes**: `Session#turn` (and `snap`, `recall`, `xfade`, scene and section values) go through the change queue: kind `:turn`, subject the knob name, data `{value:, over:, curve:, from:}` or `{follow:}`; exact landing frames (`@landing_frame`), journaled (`turn :cut lands 2:1 (queued)`), one undo step per command.  Default alignment: none (right away or exactly at `in:`/`at:`, like mutes).  Undo snapshots the knob (`Knobs::KnobSubject`, `KnobState`: the held value, a ramp's target, or the followed node) and restores it with the knob's glide (or following the same node again).  `:snap` is a change without undo snapshots.
- **Follows**: a followed node's timeline nodes (a tween's clip, tempo LFOs) start at position 0 on the turn's frame, so automation started by a turn plays from its beginning (a looping tween launched as a player instead follows the timeline: since omnibus4 it resumes the step the timeline is in, or starts at its first keyframe with `tween(..., align: :launch)`; see curves.md).
- **Snapshots**: `snap :a` records every knob's held value or ramp target (a follow's current value) when it lands; `recall :a, over:` turns each knob; `xfade :a, :b, x` moves every knob x of the way in its own scale, or with a node or knob name follows it as a crossfader (the crossfader knob itself is left out).  Snapshot names are their own table (not the shared namespace).
- **MIDI**: `Knob#listen(stream)` reads controller events per span (exact frames from the event times), `#cc=`, `#learn` (the next controller moved); `:pickup` takeover waits until the controller passes the knob's position (or is within half a step), `:jump` moves right away; moves glide over `smooth:`, and a turn makes a pickup controller catch the knob again.  `Session#knob_midi` is the Session's default MIDI input (phase 4: `Session::MidiInput`, read on exact frames; the console attaches live input on `learn` or `cc:`) unless set to another stream.  Phase 4: controller gestures are `:cc` journal entries and takes replay the moves from their MIDI log; `learn` is a `:learn` change (Recording, below).  `Knob#control_specs` gives a ControlSpec, so `MIDI::ControlMap` and ACID XML list knobs used in graphs.
- **Names**: `knob`, `knobs`, `turn`/`move`, `snap`, `snaps`, `recall`, `xfade`/`crossfade`, `learn`: no collision with `MB::Sound`, Object/Kernel, GraphNode, or Pry commands (spec).  `knobs` and `snaps` are display commands in takes.
- **Cost** (2026-10-11, container, median per 800-frame buffer, 64 players each `lp4(knob)`): holding knobs +0.3 us each (1398 vs 1408 us with Constants); ramping 10.5 us each; following `2000 + 1000 * 0.3.hz.lfo` 16.9 us each, mostly the followed graph (followed nodes aren't planned).
- **graph-io**: `to_ruby` prints knobs as `GraphNode::Knob.new(...)`; graph documents (since omnibus4) write a `knob :cut, 800.0, range: 50.0..4000.0, curve: :exp, unit: "Hz", cc: 74` header line per knob (the console's `knob` syntax, with the knob's held value) and use the bare name in the graph; loading makes one standalone `GraphNode::Knob` per line (not registered with a Session), overridable like params (`params: { cut: 1200 }`) and turned by `Document#set`.  Documents' knobs join the Session (omnibus6, maintainer 2026-10-12: "join knobs and live_error"): `Session#adopt_knobs(graph)`, called by `Session#add` for every graph it plays and by the console's `preset` when it loads (into `Session.existing`, the session commands use if one exists; `session: false` opts out), brings standalone knobs in: a new name claims the namespace (a track or group of that name goes through `live_error`; live, the knob stays standalone) and the knob object itself joins, keeping its value and any move in progress (`Knob#attach` shifts its frames to the Session's); a name the Session already has, with the same range and curve, makes the graph read the Session's knob instead (`Reader#rebind`, `Knob#redirect`, the Document's `knob_nodes` retargeted, so `Document#set` turns the shared knob), keeping the Session's value: a document loaded twice, or two documents with a `:cut` knob, share one knob that `turn :cut` moves (decision; an explicit `preset :x, cut: 900` then turns the shared knob now, a journaled, undoable turn: maintainer 2026-10-12, "Agreed").  A different range or curve goes through `live_error`.  Outside a Session (plain `GraphIO.load`, foreground `play`) knobs stay standalone, one per load, until a Session plays the graph.  Knobs with `cc:` listen to `Session#knob_midi` when they join (`adopt_knobs`), and the console's `preset` and `bg` attach live input for them as `knob ..., cc:` does (maintainer 2026-10-12, "Yes").  Spec'd in `knob_spec.rb` (graph documents in a Session).  Moves are performance state (takes replay them), not graph structure: a moving knob saves the value on its last rendered frame, after a comment saying what it was doing (decision 2026-10-11, omnibus4; it raised DumpError for a few hours after the arrange-3/graph-io-2 merge).

### Keyframes and gestures (gesture-curves, time-automation 2026-10-18)

Agreed with the maintainer 2026-10-18 (brief `/app/workbench/briefs/gesture-curves.md`): readable Hash keyframes replace `turn :x, steps: [[frames, v], ...]` (removed); recorded gestures are simplified into curves for reading, while takes keep what was heard.

```ruby
turn :space, 0 => 0.30, 1.n8 => 0.50, 1.n4 => 0.62          # a monotone cubic through the keys
turn :cut, 0 => 400, 1.bar => 3000, 2.bars => 800, curve: :smooth   # each segment eased
turn :mode, 0 => 0.2, 800.samples => 0.5, curve: :step     # jumps (the knob's glide)
smooth_gesture :space                                       # the last recorded gesture becomes its fitted curve
```

- **Keys** (`MB::Sound::Gesture`, `lib/mb/sound/gesture.rb`): times after the launch point as 0, note lengths/Durations, Lengths, or plain numbers of bars; values in the knob's units.  Between keys: a monotone cubic (Fritsch-Carlson slopes, `Dynamics::Transfer.pchip_slopes`, compand's) in the knob's own scale (octaves for `:exp`), or `curve: :linear`, `:step`, or any Curve name per segment.  Each key lands on its frame exactly (frame t of a segment from key a to key b holds `a + (b - a) * s((t - ta) / (tb - ta))`, the Knob Ramp formula), so the same values at any buffer size (spec'd at 800, 367/368, 7).  Ruby splits the braceless Hash: Symbol keys stay keywords (`curve:`), others go to `**keys` (a Symbol that isn't a keyword raises Ruby's unknown-keyword error with a suggestion).
- **Fitting** (`Gesture.fit`): from the end points, add the raw step farthest from the curve until every step is within `TOLERANCE` (1e-3 of the knob's range, in its scale; maintainer 2026-10-18, raised from 1e-4, which stays available as `tolerance: 1e-4`), for both the monotone cubic and straight lines, keeping the one with fewer keys (a tie keeps the default cubic, which prints no `curve:`).  Budget: `MAX_KEYS` (64) keys, never wall-clock time, so a gesture fits the same on any machine.  Stepped knobs (read through `Knob#choose`: `Knob#stepped?`) and `tolerance: 0` keep their steps (`curve: :step`).  A held arrow (a straight ramp, 33 steps) fits to two keys at either tolerance; a 61-step sine wobble to 30 keys at 1e-3 (55 at 1e-4).
- **Printing**: ONE time unit per line (maintainer, 2026-10-18: never mixed): note lengths when every key is on the grid (`1.n8`, `13.n24`; whole notes at the gesture's tempo with a denominator dividing 64 or 24), else milliseconds when every key is a whole ms (`10.ms`), else exact seconds for all keys (`(1/60r).seconds`); every form reads back to the same frames (`Gesture.times_text`, spec'd); values to 6 figures (`Knob.number`); `curve:` only when not the default; a one-key gesture at 0 is `turn :x, 0.42`.
- **Rule: takes reproduce what was heard; exports read like music.**  A racks-pane gesture (`Session#preview_turn` steps) commits as ONE console line, `Session#gesture_line`'s fitted keyframes (printed in the REPL and saved in the take as typed), but its journal entry keeps the raw steps (`data[:raw]`, with `:epoch` and `:pos`); `Take#gestures` saves them (`r.gestures [[name, epoch, pos, steps], ...]`) and a replay plays them at the gesture's time (`Session::Gestures#replayed_gesture`, looked up with the time the take gives the action), bit for bit (knob_gesture_spec at 800 and 367/368). ## Names that stand for controls (ux-fix-1, 2026-10-18)

Maintainer on `turn :pump, 0` for a trigger track: "Context; look at conceptually neighboring architectural patterns in the code and make sure this is handled cleanly."  One rule, `Session::Knobs#control_name`: a Symbol where a knob is meant resolves through its owner's kind in the shared namespace (`Session::Names`):

| the name is | it stands for |
|---|---|
| a knob (`:cut`, a rack macro `:"dub/space"`, a send level's hidden knob) | that knob |
| a rack knob group (`:"dub/space"` once two instances play) | every instance's knob (`turn` turns them all; `Racks#group_members`) |
| an owner with a primary control (`#primary_control`): a track (trigger tracks included) | that control: its level `:"bass/level"` (made at unity on first use) |
| anything else | itself (errors list the knobs and suggest) |

Every command taking knob names resolves through it or `#knob!`: `turn`/`move`, `snap knobs:`, `recall only:/except:`, `xfade`, `learn`, `bind_cc` (`cc:`), and scene and section values (`Arrangement#control_value?`: on a name with a primary control, a number or `[number, over: ...]` turns the control and leaves the track playing, `pump: 0`; a clip still gives the track its line).  Sections accept `Session#control_names`.  Tracks have a primary control since omnibus17: their level (the strip's fader; Track levels, below), so `turn :bass, 0.5` and scene values `bass: -6.db` set it; a trigger track's level is how much it pumps (`pump: 0` turns it off).  A bus's level is its chain, and a send level is a (player, bus) pair, so neither gets a short name.  Track level names (`:"bass/level"`) are accepted by scenes, sections, and `turn` before the knob exists (`Session#track_level_name?`; the knob is made at unity when first used).

- **Full knob names** (knobs-1, 2026-10-30, the maintainer's D5 pick, option 3 of arch-session's A): track knobs for params are named in full by one rule, `Session::Name.param(track, param)` (preset params through TrackKnobs, bound literals, library entry params; a document's `param :reso` is `:"bass/resonance"`), and `control_name` (so every command above) and `Session#knob(name)` (graphs' `knob(:x)`) resolve a short form the Param names table aliases (`Param::NAME_ALIASES`: reso, freq, q; `Session::Name.full_name`) to the full knob when it exists, with a one-line note per name and Session (`Session::Knobs#full_knob_name`). Plain names (`:reso`) and rack knobs (`:"dub/space"`, declared by their racks) are the user's own and never change.

## Leading the beat and nudges (`Arrangement#track`, `MIDI::ClipSource#ahead`)

Maintainer, 2026-10-11 ("yes" for phase 3): "Slow pads sometimes need to lead the beat because of their slow attack."

- `track :pad, lead: :attack do |c| ... end` (or `lead: 1.beat`) plays the track early: bars, a Duration, a Length, or `:attack` (the longest attack of the patch's `amp_env` envelopes, `Envelope#preset_name`, else of any envelope; measured each time the patch is built), capped at `Arrangement::ATTACK_LEAD_MAX` (1 bar; maintainer-approved 2026-10-11, omnibus4: a 4 s pad attack would lead by 2 bars at 120 BPM) unless `lead_max:` (bars, Duration, Length) says otherwise; `tracks` shows "(attack capped)".  `lead: 0.5.attack` leads by that fraction of the attack (maintainer, 2026-10-11: "Might be good to have a fractional lead amount on the attack as well", then "What about lead: 0.5.attack so attack is like any other time unit?"; omnibus5): `Numeric#attack` (alias `attacks`) makes a `Length::Attack` (a fraction of attack times; not a Length, since it has no time of its own: `#of(attack)` resolves it, `to_ruby`/`inspect` print `0.5.attack`); `:attack` is stored as `1.attack`; the cap applies to the result; spec: half a 0.25 s attack leads 6000 frames, bit-identical at 800 and 367 buffers).  Fix found then (omnibus5): voice envelopes (`v.amp_env` in a Synth) scale their times by the GM2 controllers through nodes (`NoteEnvelope#gm`, on by default), so `Envelope#attack_time` was nil and `:attack` measured 0: night_bus_flow's pad never led (the arrange-3 "lead vs no lead" renders differed only by random state: renders in one process draw different seeds unless `MB::Sound.seed` is reset).  `Arrangement#envelope_attack` falls back to the attack as given (`base_times`, CC 73 at its center).  `nudge: 6.ms` moves its notes by a fixed time (negative early).  `ahead = lead - nudge` in whole notes at the tempo when set (`Arrangement#ahead(name)`; `tracks` shows "ahead 476 ms").
- `MIDI::ClipSource#ahead`: every timeline time the source is given (`start_at`, `swap_clip`, `ring_out`, `end_ring_out`) counts that much later, so notes sound early, and the track's launches, swaps, and stops land `ahead` earlier (so a lead's first notes play and the old clip's last ones still end on time).  Seeks, wakes, and ring-outs keep the offset.  A launch too close to make its lead lands now (the first notes chase in late).  Mutes aren't shifted.
- Spec: a 1-beat lead moves edges 24000 frames early at 800 and 367 buffers; a 0.25 s attack peaks within 2 frames of the downbeat; 10 ms nudge = 480 frames.

## Clocks (time-automation, 2026-10-18)

Agreed with the maintainer 2026-10-18 (brief `/app/workbench/briefs/time-automation.md`; persona asks: Kaede's bowl loops in seconds that survive scene drops, seeks, and takes, Nev's record at 138.75 inside a 165 set).

```ruby
clock :tide, 31.1.seconds                    # a loop period (one cycle of the clip, or of the audio loop)
clock :reese, 138.75.bpm                     # a tempo of its own
clock :lag, 5/4r                             # a ratio of the session tempo (follows tempo changes)
gear :reese, 165 => 138.75                   # the same as clock :reese, 37/44r
clock :tide, 31.1.seconds, speed: :tide_speed   # speed from a knob (or a number, cc(1, 0.5..2), or a tempo LFO: 4.bars.lfo.at(0.5..2), read per cell; omnibus15)
track :bowl, clock: :tide do |c| c.trigger.resonate(:bowl) end
bg :bass, bassline, clock: :reese            # play ..., clock: too (bg/play ..., clock:)
bowl.clocked(19.7.seconds)                   # canonical; aliases clock, clocked_at
bowl % 19.7.seconds; riff.at(138.75.bpm); riff.over(19.7.seconds)   # by type (ArgTypes), print as clocked
pad.clocked(19.7.seconds)                    # audio: stretched, pitch kept (fit: :stretch; fit: :resample is tape)
brk.follow(:resample, clock: :reese)         # Sample#follow on a clock: follow(clock:)
clocks                                       # name => "31.1 s period, cycle 4 + 0.42"
```

- **Values**: `Numeric#bpm` is a `MB::Sound::Tempo` (not a number; exact Rational BPM, Floats as the simplest fraction within a millionth; prints `138.75.bpm`).  `MB::Sound::Clock` (`lib/mb/sound/clock.rb`): `:tempo` and `:ratio` clocks count whole notes, `:period` clocks cycles; `Clock.coerce` takes a Tempo, a Rational, a seconds Length, a Clock, or a name.
- **Session time**: a clock's position counts the Session's **run frames** (frames rendered while the timeline moves; `Session::Clocks#run_frame`), not the bar grid: seeks don't reset them, scene drops don't touch them, and they pause with the timeline, so a live session and a take replay (which doesn't reproduce idle wall-clock gaps) agree.  This is the brief's "frames since session start", refined so takes are exact (design delta).  Ratio clocks follow the odometer (whole notes the timeline advanced, seeks not counted).  Takes starting after the timeline ran record the run frame and odometer (`run_frame:`, `odometer:` in the start state, only then) and replays restore them.
- **Exactness**: positions are exact Rationals; within each 800-frame cell (`Clock::CELL`, on run frames) a clock is linear (cells and tempo changes are its only breakpoints), and a speed is read once per cell at the cell's first frame (knobs by `value_at(frame:)`, params by `value_at(pos)`), integrated in Rationals by the render thread (`Clock#advance` per span; a poll thread reading ahead extrapolates and never fixes a cell).  Clocked clips read their events piece by piece with the clip position set from the clock (`ClipSource#clock_edges`), and audio loops compute each sample's phase from its cell's exact base plus whole-sample offsets (`LoopPlayer#sample_clocked`), so both are the same at any buffer size (spec'd: strikes at 800, 367/368, 7 with a knob turning the speed; loops bit-identical at 800 and 367/368).
- **Clips**: `Sequence::Clocked` (in Clip; carried through every transform like PlayedBy: `riff.clocked(:x).transpose(2)` stays on `:x`).  Looping clips follow the clock from session time (clip position = clock position × the clip's length per cycle on period clocks); launch-aligned loops (`.loop(align: :launch)`) and one-shot clips count from their launch on the clock.  Launches still land on the session's bars (launch points unchanged).  Swaps between clocked and plain clips switch timebase on the swap's exact time.  A graph that started, then waits for its start again after a backward seek, resyncs clocked nodes where it plays again (`Player#waited`, `clock_resync`).
- **Demos** (bench-fixes-1, the maintainer's time-automation Bench picks): the pad loop on a 19.7 s period leads with `fit: :stretch` ("stretch to 19.7 s" over resample), and Nev's riff stays at the set tempo ("before": the 138.75 clock against the 165 break drifted; no shipped demo plays it, the clock example in `help :clocks` is a 98 BPM riff).
- **Audio** (`LoopPlayer` with `clock:`): one loop per period on period clocks (no tempo needed), the loop's beats at the clock's tempo otherwise; `fit: :resample` bends pitch with a speed knob (tape), `fit: :stretch` restretches when the loop's length on the clock moves by more than `CLOCK_STEP` (1/2000; `stretch: :auto` as `follow`).
- **Names and listings**: clock names share `Session::Names` (`:clock` kind; collisions through `live_error`); `clocks` (console), `Session#clock_info`; the UI shows clocks (`Slow#clocks` ClockInfo from the poll thread): a row per clock on the launch lane's free rows, a clock line at the bottom of the clip matrix, a line in `ui.list`.  `help :clocks`, `help :at`, `help :over` (tables from ArgTypes; arg_types.md).
- **Documents**: graph documents write `clock :tide, 31.1.seconds[, speed: :knob]` header lines for the named clocks their clips use (the RubyWriter collects `clocked(:name)`); the Session that plays the graph (or `preset`) defines missing ones (`Session::Clocks#adopt_clocks`; a different clock of the same name through `live_error`).  Set documents write every session clock in the header (after the knobs) and `track ..., clock:`; the loader defines them first.  No format bump (old documents load unchanged).  Periods print in seconds (`clocked(19.7.seconds)`, not `19700.ms`).
- Generators are clips, so `motifs(...).clocked(:tide)` cycles on a clock (checked: the same events at a clock of the session's own tempo).
- Not built (proposed): `clock:` keywords on generators (`.clocked` covers it), LFOs/TempoNode values on a clock (`1.cycle.on(:tide)`), MIDI capture on a clocked track converting to the clock's time, Kits (grids) on clocks, orbits/conjunctions (a future UI mode), tempo ramps inside a clip, stretch-to-fit.

## capture per armed track (ux-1 round 2, 2026-10-17)

`capture` (no names: every armed track) captures into each track on its own: a track whose patch fails to build (or that has nothing to capture) doesn't stop the others.  The failures come after, as one `Arrangement::Recording::CaptureFailed` through `live_error` (raised in scripts and specs, a warning live, so the messages pane shows it while a UI is up), naming each track and the line in the user's code (`Internal.error_origin`: the first backtrace frame outside mb-sound's lib/ and gems), with the tracks that were captured: "capture into :l_bass failed: NoMethodError: ... (at (pry):3) (:lead captured)".  `#failed` and `#entries` carry the details.  KEYS mode's Enter runs `capture :name` per armed track (take lines) and shows the same.


## ux-r3 session round (2026-10-17)

- **Arm state** (`arrangement/arm_state.rb`, item 21): each armed track has an `Arrangement::Arm` (input, monitor wanted, state) in a declared state machine: `:disarmed`, `:monitoring` (the monitor `:"x/live"` plays or is queued), `:silent` (armed for `rec`/`capture`, no monitor: `monitor: false`, a patch that can't play live MIDI, or a monitor stopped by name); events `arm`, `arm_silent`, `disarm`, `panic`, `monitor_lost`, `monitor_found`, `redefine` (`Arm::TABLE` answers every pair; `Arm.table_text` prints it).  Invariant: `:monitoring` exactly when the monitor plays or is queued, and no monitor plays for a disarmed track (`Recording#arm_problems`).  `Recording#sync_arms` restores it after every `Session#command`, undo, and redo (the player set is the truth for "plays"; the arm state owns the monitors: a monitor brought back for a disarmed track, e.g. by undoing `stop :"x/live"` after `disarm`, is stopped with a declick), and `Session#resume` refuses a disarmed track's monitor.  **`panic` disarms every track** (maintainer, 2026-10-17: an armed track may be the broken one making noise), journaling a `:disarm` per track (`data: { by: :panic }`) and saying which (`panic: stopped 1 player; disarmed :y, :z`).  `tracks` shows `armed (no monitor)` for silent arms.  A spec random-walks arm/disarm/panic/stop/forget/undo/redo/seek/scene/bg/resume/track redefinition with buffers between and checks the invariant after every step; it found the next point.
- **`playing_after_queue?` reads undo restores**: a `:restore` change with nil `starts` (no player in its snapshot) counts as stopping; before, undoing `arm` left the monitor counted as playing until the restore landed.
- **Replacements crossfade** (item 5): `bg :x, g` replacing a playing `:x` switched on one exact sample with no fade, by design; between unrelated graphs (re-running `bg :c2, C2.unison(4, spread: 0.5).triangle` with spread 0.9) that is a 0.11 step against 0.003 per sample.  Replacements now crossfade over `Fades::DECLICK_SECONDS` (5 ms, frame-counted Ramps from the exact start sample) unless given a fade (`fade: 0` still cuts); undo's restores already did.  Track launches pass `fade: 0` explicitly, so songs' scene changes are unchanged: all 66 bin/songs and bin/synths renders are sample-identical before and after (decoded md5; no demo replaces a playing player with a default fade).  `Session#replace_declick` (default true) turns it off; takes record it in their start state and `Take::Replay` defaults it to false, so takes saved before it replay with their hard cuts, exactly.
- **Patches are checked when stored** (`Arrangement::PatchCheck`, `arrangement/patch_check.rb`, item 6; pattern F): `track`, `scene` (each track's patch with the scene's clip, once per patch and clip), and `arm` (the monitor) build the patch once in the Session's context with the random state kept, from the clip it will play or a probe (`PatchCheck.probe`, a one-note C2 loop: MIDI 36 so drum kits find a voice).  A failure is a `PatchError` naming what stored it, the error, the line inside the patch (the first backtrace line in the patch's file), and what it was built from; scripts raise it, live mode prints it in red at the prompt (the REPL pane in tiles) and adds it to the UI's messages; nothing changes (a redefinition keeps the old patch).  Patches written for another source pass the probe: a NoMethodError on the probe itself, or `MB::Sound::SourceMismatch` (tr808 and Drums::Machine raise it for "Nothing in ... plays a voice") anywhere in the cause chain.  A track reading a knob needs the knob first (`loop_church.rb` moved its `knob :dub` up).  Guard spec: Prism walks `arrangement.rb` and `arrangement/*.rb`, and every method that stores a Track or Scene must call `check_patch`.
- **`demo`** (`demo_methods.rb`, item 26): loads `presets/night_bus.mbg.rb` (a set document saved by `bin/save_presets.rb` from `night_bus_flow.rb`'s `last_stop` and `last_stop_form`) into the current Session paused at bar 1 and prints what to try; `demo` again returns the document (`Arrangement#demo_document`), with players playing it asks (`replace: true` stops them), `demos` lists sets.  The loaded set plays the script's music (bar RMS within 8%; drawn seeds differ).  tunnel_vision isn't shipped: set documents don't hold buses and sends yet.

## The clip matrix (ux-r4-feed, 2026-10-18)

`Arrangement::ClipMatrix` (`arrangement/clip_matrix.rb`) keeps each track's **slots**: the clips it can play, append-only (a slot's index never changes in a session, so take lines like `launch :bass, 3` replay the same), filled with the clips scenes give it (in scene order, as scenes are defined), then clips played on it (`bg`, `launch`), its captures, and tweaked copies.  Every change `set_track` makes remembers the clip it launched (`launch_clip(seq)`, the last 512), so the terminal UI's Poll can tell which slot is playing from the journal alone (the newest landed `:bg`/`:swap`/`:resume`/`:restore`/`:capture`/`:stop` per track; restores and captures read the track's clip; contract in terminal_ui.md "UI round 4").  Capture placeholders aren't slots.

- Marks (gesture-curves, 2026-10-18; `UI::Panes::Clips::PLAY_MARKS`): ▶ the playing slot in one column (the current scene's, else the first giving it), a dim ▷ in the other scene columns that would keep it playing if launched, ◆ queued with its countdown (`play_marks` :will_play, the default; :current and :all kept).
- `launch :bass, :bass_b` / `launch :bass, 3, on: :beat`: plays a slot by clip name (the track's slots, then captures, then any track's) or index through `Arrangement#play` (the `bg :bass, clip` path: journaled, one undo step, launch points).  `launch` was free (no MB::Sound method or Pry command; `Form::Playback#launch` is another object's).
- `tweak :bass, transpose: 2` (`legato:`, `swing:`, `quantize:` a grid or true, `:reverse`, `:halftime` twice as long, `:doubletime` half as long, `:double` twice through, `:half` its first half; an octave is `transpose: 12`): one transform of the track's clip (the one queued last, else playing), named after it (`:"riff_a/t+2"`, unnamed clips `"bass#1/t+2"`), played at the track's launch point as one change and one undo step, and kept as a new slot.  Kits take what Kit has (`halftime`, `doubletime`, `legato`, `:double`, `:half`); the rest is a live_error naming the kit.  `edit` is a Pry command, so the verb is `tweak`.
- Wrong slots, names, and transforms go through `live_error` with the range, did_you_mean, or the list.  Specs: `spec/lib/mb/sound/ui/feed_round4_spec.rb`, `take_spec.rb` (launches and tweaks replay bit for bit).

## Params (param-1, 2026-10-24)

Knob specs build an `MB::Sound::Param` (`design/notes/params.md`): typed declarations (`knob :cut, 2400.hz, range: 150.hz..8000.hz`, or `(150.hz..8000.hz).at(2400.hz)`), names-table ranges (`knob :pan, 0` is -1..1); a default outside its range goes through `live_error` (raise in scripts, limited with a warning live; it used to be limited silently), and `clamp: false` lets a knob leave its range.  A turn past a knob's range goes through `live_error`: it raises in scripts and specs, and live it warns once per knob and limits the value as before.  `turn :cut, 3000.hz` on a frequency knob is a value (it used to be a sine to follow).
