# Terminal UI

<!-- summary -->
`ui` (`lib/mb/sound/ui.rb` + `ui/`) is the live terminal UI: a read-only dashboard band under the console (`ui :deck`, `ui :mini`), or `ui :tiles`/`:studio`, which own the alternate screen and tile panes around the real Pry on an in-process pty (the generic layers are the mb-term gem, `gems/mb-term/`, `MB::Term`).  The render thread publishes one frozen `UI::Snapshot` per buffer the painter takes; `UI::Poll` reads slow data 4/s; a painter thread draws panes (Ruby: `pane`, `layout`) into a C cell grid and writes changed cells in one synchronized frame.  Never poll `Session#players`/`#clock`/`#strip_info` from the painter (render lock), and panes never write their own bytes.  `ui.note 'text'` (or NAV #) keeps a UI note with a screen capture (`UI::NoteLog`).  `bin/play.rb` has player screens by file type (`MB::Sound::Player`); `vis`, `--plot`, and `bin/record.rb` use a `:vis` band.
<!-- /summary -->

## Quick reference

- Feed: `Session#ui_feed` (a `UI::Feed`) gets one frozen `UI::Snapshot` per buffer after the painter took the last one (load, CPU per part, master meters with true peak and short-term LUFS, scope samples, knobs); `UI::Poll` reads tracks, scenes, form, queued changes (`Journal#subscribe`), the clip matrix, and rack infos 4/s without the render lock; bus/send meters (`UI::BusMeter`) and held MIDI notes (`MidiInput#held_notes`) ride the snapshot (the round-4 feed contract below).
- Panes and layouts are Ruby: `pane :name, rate:, height:, needs: do |c, s| ... end` (`UI::Canvas`) and `layout :name do cols { ... }; rows { ... } end`, saved with `ui.save` (a Prism-walked loader, no eval).  Layouts, themes (`MB::Term::Themes`), and pane files are data read by `MB::Term::DataFile` and reloaded by mtime.
- bin/sound.rb installs the prompt (`UI::Prompt`, `UI::NudgeKeys`) and Tab completion of session names (`UI::Completion`, also in the screen's REPL thread; both below).  `design :bass[, instrument, clip]` opens `ui :sound` on a track (sound_design_ui.md; the RENDER pane's worker renders only in `PatchRender.slack` windows after the live render thread finishes a buffer).
- mb-term: a path gem with its own bundle; specs run without mb-sound (`rake spec:gems`); mb-sound registers its native grid (`MB::Term::Grid.native = NativeCells`, `plot/text.rb`).  `MB::Term::VT.new` is the C `NativeVT` (`RubyVT`, its mirror, with `MB_TERM_NATIVE=0`); scrollback: `#scrollback_length`, `#line_at`.
- `bin/play.rb`: `MB::Sound::Player`; `vis`/`--plot`: the `:vis` band.
- Tools: `bin/ui_check.rb`; `bin/ui_demo.rb [--compare] [-L low]` (wake delays) the band, `bin/ui_demo.rb --tiles [--flood N]` (`--perf`), `--design LINE`; `ui.perf [:capture]`, `bin/ui_bench.rb` (`--alloc N`); `ui.smooth/pace`.

The live terminal UI for the console (`bin/sound.rb`).  Step 1 (ui-2, 2026-10-15) made plots fast enough for live panes (`fast_ui`, `Plot::Live`; see plotting.md).  Step 2 (ui-3) is the read-only **dashboard band**: a few rows above (or below) Pry, kept out of scrolling with a scroll region, drawn by an in-process painter from per-buffer snapshots.  Step 3 (ui-5, the section "The tiled screen" below) is **`ui :tiles`**: the whole screen owned cell by cell, panes tiled in a split tree around the real Pry/Reline, which runs on an in-process pty and draws into its pane through a terminal model.  CUE and the Deck's other parts wait for later steps.

Background: research-ui-2 d3e30356 (never merged): `research/terminal-ui-2/README.md` (painter measurements on the Linux desktop) and `ARCHITECTURE.md` (layers, three options).  Decisions accepted by the maintainer (2026-10-15): option 1 (in-process painter, native cell grid, "snapshots in, cells out", per-pane rates, `Thread.pass` between panes, never poll `Session#players` per frame); a DECSTBM band first, Pry unchanged; live panes default to quadrants in 256 colors (iTerm2 is throughput-bound at ~2.5 MB/s, so bytes per frame matter; Braille stays available per pane); names `ui` / `ui :deck` / `ui off`, `pane :name do |c, s| ... end`, `layout :name do ... end`, `ui.save`.

## Using it

```ruby
ui                      # the default band: transport, form, tracks, queued, master meters, scope (7 rows)
ui :deck                # 13 rows: adds knobs and CPU per part
ui :mini                # one line: transport and form
ui :band, at: :top      # above the scrolling text (default :bottom since ux-1; also color: :truecolor, look: :scope for Braille)
ui :wall                # every pane (200x60 and up); ui :tiles, :studio, :keys
keys                    # the keyboard (F2 in the tiles); fg after Ctrl-Z; jobs
ui.fps; ui.target_fps = 30; ui.frame_rate   # measured vs the painter's rate (NAV f shows it)
UI.messages.recent      # warnings while a screen was up (NAV m: the messages pane)
ui off                  # (`off` is :off; also ui :off, ui false)
ui.stats                # painter CPU per refresh, bytes per frame, the slowest refreshes

pane :where, height: 1 do |c, s|          # s: a Snapshot, c: the pane's Canvas
  c.puts ['bar ', :dim], [s.stamp, :key], '  ', [s.form&.section.to_s, :name]
end
layout :mine do
  cols { pane :transport; pane :where }
  cols { pane :meters; pane :scope, width: 50 }
end
ui :mine
ui.save                 # ~/.local/share/mb-sound/ui/mine.rb (Mac: Application Support), loaded by `ui :mine` later
```

The prompt shows Pry's line counter and only state that commands change (ux-1, maintainer 2026-10-17: a prompt is drawn once, so a playback position read as a line number): recording and armed tracks and the form's section or scene, `sound.rb [12] ●rec:lead arm:pad drop MB::Sound(0) >` (`UI::Prompt.main`, `UI.prompt_status`; `UI.prompt_status_enabled = false` turns the state off).  Lines inside unclosed constructs get a dim prompt as wide as the main one naming what is open (`do ( … >`; `UI::Prompt.continuation`, from Ripper tokens, set as Reline's `prompt_proc`).  Enter runs a complete buffer wherever the cursor is (`UI::EnterSubmits`, prepended to `Reline::LineEditor`); an incomplete buffer gets a new line, and Alt-Enter always does (not Ctrl-J: type-ahead reaches Reline as "\n" through the tty's ICRNL).  Tab completes track, scene, knob, bus, layout, and pane names after the commands that take them (`go :<Tab>`, `turn :c<Tab>`, `ui :<Tab>`), and lists session names first for any other Symbol.  `now` suggests `ui`; `help :ui` is the topic.

## How it works

```
 render thread (Session#process_buffer)
   inside the render lock, when the painter took the last snapshot:  feed.capture(session) -> Session#ui_parts
   after the output write:                                           feed.publish(mix, load) -> meters, scope ring, Snapshot
                                                                        (one frozen object, one reference swap)
 painter thread ('MB::Sound::UI', priority -1, up to 60/s)
   take the newest Snapshot; Poll (4/s) for Slow data; size check
   each due pane: draw into its Canvas (Plot::Live panes blit their cells in); Thread.pass
   overlays (NAV badges, the ? box), the status line into the same grid
   Grid#frame (changed cells, C) -> one write:
     CSI ?2026h  ESC 7  [CSI top;bottom r]  cells  ESC 8  CSI ?2026l
```

- **Snapshots in** (`UI::Feed`, `lib/mb/sound/ui/snapshot.rb`): the render thread publishes a frozen `UI::Snapshot` only after the painter took the previous one (so at most once per buffer and at most at the painter's rate), with what accumulated since: render load mean/max, each part's CPU share (`PartLoad`: players by state with their own `muted`/`soloed` flags (knobs-pane-keys-1, read in `Session#ui_parts` under the render lock it already holds), buses, the master chain; graph times counted in `Player#cpu`/`Chain#cpu` only while a feed is attached), master meters (`MasterMeter`: sample peak and RMS per channel, Annex 2 true peak through `FastLoudness.true_peak`, short-term LUFS from K-weighted 100 ms blocks over 3 s), the latest 1024 samples per channel (`ScopeRing`), output underruns, and knob values.  Meters and the scope run only when a visible pane `needs` them.  Peaks between frames are never missed.
- **Slow data** (`UI::Poll`, painter thread, 4/s): tracks, scenes, armed tracks, the form (`Form::Playback#upcoming`), knob specs, and queued changes and running recordings, which it keeps from the journal's new entries (`Journal#subscribe`) instead of rereading `Journal#changes` (it grows with the session).  Nothing it calls takes the render lock (`Session#players`, `#clock`, `#strip_info` do; a spec checks).
- **Cells out** (`UI::Canvas`, `UI::Pane`, `UI::Panes`): panes draw text segments with color roles (`UI::Theme`), eighth-block meters with zones and a peak hold, and sparklines into their rectangle of a `Plot::Text::NativeCells` grid (`FastUI::Grid`; the Ruby mirror `MB::Term::Cells`, the `cell_grid` kernel's Ruby side or a screen's `cells:` class, gives the same text and bytes, checked by specs).  The scope and spectrum panes are `Plot::Live`s whose cells are blitted into the grid (`Live#draw(chart, grid, x:, y:)`, `FastUI::Grid#blit`; `Pane#plot?` marks them for `ui.look`); until ui-fix-3 they wrote their own changed-cell bytes after the grid's frame, which painted over the `?` overlay.  No pane writes terminal bytes: the grid is the only path, so whatever the screen paints after the panes stays on top.  A pane that raises shows its error in its rectangle (warned once) and the others keep drawing.
- **Layouts** (`UI::Layout`): rows of `cols`/`rows`/`pane` with fixed `height:`/`width:` or `weight:` (default: the pane's natural width), one blank column between panes; `to_ruby` prints them back; `UI::LayoutLoader` reads saved layouts by walking the Prism tree (only `layout`, `pane`, `rows`, `cols`, literal arguments; never eval).
- **The band** (`UI::Band`): on start it scrolls the screen up by the band's height (so nothing is overwritten), sets the region, and puts the cursor back on its line.  SIGWINCH (chained with Reline's handler) and a size check every 0.5 s relayout and redraw; every 2 s the region is reissued with a full redraw (after `reset`, a pager, `clear`).  `UI::RelineGuard` (prepended to `Reline::ANSI` while a band is on) makes Reline see the region as the screen: cursor rows shifted below a top band, the height minus the band, and Ctrl-L clearing and redrawing the band.  Stopping resets the region and clears the band's rows.
- **Warm-up** (`UI.warm_up`, once per process with YJIT, ~0.4 s): the first frames otherwise hold the GVL for 10-30 ms while YJIT compiles the painter; `bin/sound.rb` runs it at startup, `ScriptRunner` before playback with `--ui` (scene-jit-1: in `#live_ui` it ran after the form started, ~0.4 s holding the GVL during the first bars), `UI.show` before the first band otherwise.
- `MB::Term::Screen` is a small VT replayer (CUP, DECSC/DECRC, DECSTBM, erases, SGR) for specs (diffed frames must rebuild a full redraw) and captures.

## Measurements (Mac container, i9-9880H, 2026-10-15)

`bin/ui_demo.rb` plays "Last Stop" with the band drawn to /dev/null at 30x120 (no terminal in the container), 800-frame NullOutput buffers, YJIT, after `UI.warm_up`; GVL waits from `FastUI::GVLProbe` (Ruby's internal thread event hook).

| | render-thread wake delay p50 / p99 / p99.9 / max (ms) | waits > 2 ms per minute |
|---|---|---|
| band off | 0.000 / 0.001 / 0.03 / 0.03-0.8 | 0 |
| band on (`:band`, 60 fps) | 0.000 / 0.21-0.28 / 2.2-4.5 / ~10 | 6-10 |

Painter per refresh (band layout, 120 columns, ansi256): CPU p50 0.2 ms, p99 0.9 ms; refreshes that drew a pane p50 0.3 ms, p99 1.1-1.5 ms; 1.8 panes per refresh; ~400 bytes per written frame (max ~2.5 KB on the 2 s full redraws); ~200 Ruby objects per refresh (scope ~220 per draw, meters ~105).  The waits over 1 ms are attributed by `GVLProbe.blockers` to the painter (a few: its first full frame, ~30 ms including the scope's first Plot layout, and the poll's occasional 2-3 ms) and to "none of the watched threads" (GC pauses and GVL handoffs); a GC run takes ~10 ms here.  Render load is unchanged (p50 7-9%).

The timing spec (`spec/lib/mb/sound/ui/painter_timing_spec.rb`, no YJIT, 256-frame paced buffers, the deck at 60/s, 40x160): render wait p99 0.18-0.29 ms (max 0.3-0.4 ms), painter busy p99 ~1 ms; budgets 2 ms and 4 ms times the machine's slowdown (a full deck redraw timed in the same process over 1.1 ms).  Since omnibus12 (2026-10-23) the slowdown is the larger of calibrations before and after the measurement, the painter budget reads `Band#stats[:busy_no_gc_ms]` (refreshes during which the GC ran left out: GC pauses made the slowest refreshes, 13-22 ms in a fresh process, 30 ms p99 in a suite process, and the longest render waits, 12 ms; with GC off 1.3-1.7 ms and 0.4-0.6 ms), and `:gc_frames` is bounded at a tenth of the refreshes (1-2 of ~168 measured).

Not measured here: a real terminal's own parse and draw time (iTerm2, Konsole), native macOS, JACK at 128 frames, underruns on a sound card (the container's NullOutput has no underrun count).  `bin/ui_demo.rb [-L low] [--compare]` measures them in a real terminal.

## Frame instruments (ui-perf-1, 2026-11-16)

The maintainer saw lag in the tiles on the Linux desktop while the listed and target rates were high; the listed rate (`ui.fps`) counts frames the painter wrote.  `ui.perf` (`UI::Perf`, `lib/mb/sound/ui/perf.rb`) measures what that number can't see, only while it records (off: one nil test per hook; the rings are preallocated and recording allocates nothing per frame, `perf_spec`):

- per frame: lateness against the Pacer's deadline, paint, write (time blocked handing bytes to the terminal), bytes, panes drawn, cleared frames, GC; the worst gap between written frames ("stall") and between frame starts;
- per pane: update age (time between its redraws, `PaneRates#drew`);
- key to frame: a key's arrival to the write of the first frame drawn after its handler ran (REPL keys: the first frame that redrew the REPL, since the echo comes back through the pty).  A frame written is not a change shown: a key whose effect arrives later (a knob value from the next snapshot) or not at all still matches the next written frame;
- a terminal query (DA1) after sampled frames, 4/s: the terminal answers only after parsing what came before, so the answer time bounds its parse, not its paint (Konsole and iTerm2 paint on their own timers).  Answers are taken out in the input thread (`Decoder#expect_cpr`/`#expect_dcs`) and never reach the Router, Pry, or NAV; queries stop after the first lost ones (a terminal that doesn't answer);
- the terminal's identity: the probe's features, `TERM_PROGRAM`/`KONSOLE_VERSION`-style environment, XTVERSION and DA2;
- the render thread's wake delay and the painter's GVL waits (`FastUI::GVLProbe`, when no other tool runs it).

`ui.perf` starts, `:report` (a `Help::Doc` page), `:stop`, `:save` (report.txt, summary.json, frames.json under the checkout's `tmp/ui-perf/captures/`, `MB_SOUND_CHECKOUT_TMP` respected), `:capture` (below).  NAV f's readout adds "late p99 X / stall Y ms" only when frames hitch (`Pacer#hitches`: p99 lateness over half a period or a gap over two periods).

**The capture** (`ui.perf :capture`, about a minute, in the background): phase 1 records the current tiles with the set playing (it listens to the mix for 0.5 s, `Capture.listen`, a tap on the render thread; when it is silent it goes to a scene of the loaded set, else loads `demo` and goes to a scene, then settles 2 s; deciding by tracks recorded a stopped set on 2026-11-16); phase 2 opens `design` on the last designed track if it still exists (else a temporary `:ui_perf` track owned by the run: a leftover from an earlier run is removed first, never adopted, and the run removes its own in an ensure and puts `Design.last` back; untrack leaves the track's knobs in the Session), waits until the inspector draws that track (`Capture.wait_drawn`: a designed track lands on its launch point, and until then the inspector shows the first playing track, where a Down would move it), steps the inspector Down to a knob row (`Capture.pick_knob`, only on that track) and turns it with scripted Right/Left keys (`Tiles#type_scripted`: decoded, routed, and timed as typed), each only while the screen, focused pane, input mode, and picked knob are what the script expects (`Capture.key_target`).  When they change it tells his keys (`Perf#typed_keys`, keys from the terminal while recording) from the screen changing by itself: with keys typed the phase stops with one line (his keys once sent the arrows to the track levels); with none (the maintainer's 2026-11-21 tunnel_vision captures: the flow's next scene stopped the temporary track, since a scene stops the tracks it doesn't name, and the inspector fell back to the first playing one) the keys wait while the set and its form play on, the run starts its temporary track again (`bg :ui_perf`, at most `RESTARTS` a wait; `Capture.come_back`), re-picks the knob, and goes on, saying so in a note.  It sets the knob back at the end.  The settings line names whether audio was playing (peak dBFS), the song, tempo, buffer size and rate, and snapshots per second; `frames.json` keeps the per-frame `panes` count with `panes_drawn` (from `pane_mask`) and `pane_gaps`; the screen's focus and mode come back at the end.  It prints three lines per phase (worst stall, stalest pane, key-to-frame p95) and saves both phases once at the end (never while recording) with load averages and scheduler run delays; `ui.perf :cancel` stops it early and saves what it has (Ctrl-C reaches Pry, not the capture's thread); a failure prints one line, stops recording and a demo it started, and a design screen open at the start stays open.  Run end to end on a pty with a model terminal, with and without answers (2026-11-16), and two captures in one process with keys typed in phase 2 (2026-11-17), and tunnel_vision with its form on `ui :wall` at 63x236 and 512-frame buffers (2026-11-21); in Konsole by the maintainer 2026-11-16.

**The harness** (`bin/ui_bench.rb`): scenarios band, tiles (Last Stop playing), flood (40 000 console lines), design (the sound screen with a knob swept by arrows), typing (the REPL), plot (a standalone `Plot::Live` scope, the ui-2 path); each in its own process, the pty read by a forked SINK that models a terminal (unlimited; `--sink throttle --bps N`; `parse`/`konsole`: costs per escape, cell, and frame), answers queries only after consuming the bytes before them, types the scenario's keys, and keeps a VT, so each pane's VISIBLE update rate and the key-to-visible time (a key's send to the first frame changing a cell of the panes it acts on, `KEY_PANES`) are measured at the terminal's end.  Every run prints the 1-minute load, the scheduler run delay of the process, painter, and render thread ("clean" under 1 % of wall time), CPU beside wall time, and JSON (`-j`); `--screen FILE` writes the sink's last frame.  `--every-buffer`, `--snapshot-timed`, and `--echo-wake` turn on the pacing options below (`--smooth` all three; `--live-waves`; `--holders` adds per-buffer render times and GC steps); `--buffer N` renders N-frame buffers and `--out-latency B` makes the null output report B buffers of latency (meters and scopes then show what is heard).

## The combined branches (ui-perf-2, 2026-11-16; harness numbers)

`ui-perf-1` and `ui-wave-perf-1` merged, then:
- **The painter and the input thread yield.**  `FrameRate#yield_to_render` (each frame, on the painter: two ivar reads when nothing changed) joins `UI::Yielding` when the followed Session's render thread appears or changes, and the input thread with it; `#stop_yielding` when the painter's loop ends.  On the Mac i9 (main session's runs, tip a379ef62f, 8 s each): render waits over 2 ms a minute with yielding on/off: tiles 90/142, design 60/150, typing 142/202; the input thread fell from 10 waits a run to 1-3.
- **What still holds the lock is YJIT warming up** (second agent, tip a9270fcc2 on).  Compiling holds the GVL with no interrupt check, so no handover reaches it.  The YJIT log (`ruby --yjit --yjit-call-threshold=5 --yjit-log=FILE bin/ui_bench.rb ... --holders`; the bench prints the screen's start as epoch seconds, the log's stamps) puts a cold screen's compiles in its first 2 s (emulated i9, tiles: ~126-142 ms of UI code then, almost nothing after), plus one burst when the song first swaps clips (bar 9 of Last Stop, Session code, below).  The biggest UI pieces were the first `Poll#call` of a set (each clip's Ruby for ClipInfo#ruby: 111 ms natively, 94 ms of it compiling 3422 blocks) and the feed's snapshot and meter code on the render thread.  `UI.warm_up` now runs the render side in six short sessions (`UI::RENDER_SESSIONS`) and polls a small set (`UI.warm_up_poll`): the song's first buffer 18.7-23.7 -> 6.4-8.6 ms on the emulated i9 (no more overrun there), the first poll 111 -> 18 ms natively, cold render waits over 2 ms in a screen's first 18 s: tiles 17-20 -> 8-14, typing 16 -> 8-10; `UI.warm_up` 0.33 -> 0.45 s natively (0.44 -> ~0.7 s emulated i9).  Running the tiles and the sound screen offscreen on a private pty for 1.5 s each (3.1 s at start) halved the first 2 s's UI compiles (4500 -> 2400 blocks) but not the waits (tried, not kept).

## When the terminal shows a frame (konsole-pacing, 2026-11-21)

The maintainer, natively in Konsole 23.08.5 on a 120 Hz screen (PipeWire quantum 400 frames, `ui.smooth :on`): "at target fps 120 I see the same smoothness as target fps 30", "at target fps 60 I see more variations in the filter cutoff waveform change".  Konsole doesn't repaint per write.  Its source (`src/Emulation.cpp`, v23.08.5 and master): `Emulation::receiveData` calls `bufferedUpdate()` for every chunk read from the pty, which restarts `_bulkTimer1` (`BULK_TIMEOUT1 = 10` ms) and starts `_bulkTimer2` (`BULK_TIMEOUT2 = 40` ms) only when it isn't running; either timeout calls `showBulk()`, which stops both and emits `outputChanged` (the view's `update()`; no other throttle: Qt treats a coarse timer under 20 ms as precise, and the widget's own timers are blink and resize ones).  So frames written more than 10 ms apart each show about 10 ms after they arrive, and frames written closer (above about 100/s) keep restarting the short timer and show only when the long one fires: about 25/s.  Any write within 10 ms of a frame holds that frame back too.  Synchronized output (DEC 2026) came in commit fae264b5 (2026-01-26), first released in 26.04.0: the start and end of a synchronized update call `showBulk()` (the end shows the frame at once) and timers don't run inside one.  23.08 ignores DEC 2026, and no Konsole version answers DECRQM (the probe's `:sync` stays false; the tiles bracket every frame anyway).  **Confirmed on his screen by the maintainer (2026-11-21)**: "the 95 vs 105 fps tests matched Konsole's timer description; since my display is at 120fps I'll keep the 60fps target for now".

- `UI::TerminalProfile` models it (`:bulk` short/long timers; `:sync`; `:cadence` (iTerm2's 60/s update cadence, WezTerm's `max_fps` 60); `:interval` (kitty's `repaint_delay` 10 ms)); `.detect` reads Konsole's XTVERSION answer or `KONSOLE_VERSION` (nil behind tmux/screen and for other terminals).  `#presents(arrivals)` gives the view's update times; `#min_gap` is the short timer plus 2 ms.
- `bin/ui_bench.rb --present konsole+konsole26 [--vsync 120]`: the sink records each chunk's read time, and the report says the modelled view updates per second, write-to-view delay, each pane's shown rate and gaps, and frames arriving within the short timer of the one before (`present_report`).  Harness, 63x236, 400-frame device pulls, `ui.smooth :on`: target 60 -> 58.5 scope updates shown/s (gaps p95 17.1 ms), 120 -> 24.3/s (41.7 ms), 240 -> 24.4/s; with smooth off the feed's 60 snapshots/s cap the written rate near 63 whatever the target.
- At target 60 (his choice) frames are 16.7 ms apart and each shows about 10 ms after it is written (harness: 58.7-59.6 scope updates shown/s, gaps p95 17 ms, an even 2:1 cadence on a 120 Hz display).  What still lands within 10 ms of a frame: 0.1-0.7 writes/s with the set playing, 2.2/s while typing (key-woken frames), 5.9/s typing with `ui.smooth :on` (echo wakes); each holds the frame before it back by up to 10 ms more (40 ms at worst), the hitch he first reported.  Frames are single writes (the DA1 and identity queries ride in the frame's write; the REPL's replies go to its own pty), so nothing to coalesce there.
- `ui.pace :terminal` (`FrameRate.pace`; `MB_SOUND_UI_PACE=exact` turns it off at start): `Pacer#min_gap` (the profile's short timer plus 2 ms; nil for every terminal but Konsole before 26.04, so elsewhere the painter runs the `:exact` code path, `min_gap` being the only way the mode reaches it) keeps deadlines at least the gap apart, and `Pacer#hold_before_write` (in `timed_write`) waits out the gap since the last write (`Frame#hold`, `breakdown[:hold_ms]`, not in paint; it waits again when a key's wakeup ends the wait early).  The first version (konsole-pacing) started a woken frame at once and held its write, which held the next deadline's frame off the grid (typing with smooth at 60: scope shown gaps p95 20.9 -> 37.5 ms), and spaced frames by the bare 12 ms gap, which beat against the feed's 60 snapshots a second with smooth off (47 caught at target 120 against 57 with :exact).
- **Pacing by default (pace-default-1, 2026-11-21)**.  The maintainer, asked how Konsole 23.08 should pace by default: "Pace by default: On older Konsole keep writes at least 12 ms apart automatically (at most about 83 a second), whatever target is typed."  So `:terminal` is the default; `ui.pace :exact` turns it off.  Two Pacer changes came first: a woken frame (a key, the REPL's echo) without room (its write closer than the gap after the last, or the deadline's frame closer than the gap after it) waits for the deadline it slept toward (`Pacer#defer_wake?`; at 60 no woken frame has room, at 30 one can), and the spacing is the smallest whole number of target periods at least the gap when that is within 1.5 gaps, else the gap (`Pacer#gap_step`, `GRID_SLACK`: 120 and 180 run at 60, 240 at 80, 144 at 72; 90-110 at the gap).  `Pacer#write_gaps` records the gaps on the painter's own clock (`ui_bench` JSON `pacer_writes`).  Harness (7950X container under other agents' load, 63x236, 400-frame pulls, 8 s, typing 14 s with keys at every phase of the frame grid; Konsole 23.08 model; `bin/ui_bench.rb --present konsole --vsync 120 --holders`, `--pace exact|terminal`): scope shown/s and gap p95, :exact -> paced: target 60 equal within run noise (58.7-59.4/s, 17.0-17.4 ms; typing with smooth 56.1/s, 33.3 ms -> 59.4/s, 17.0 ms); target 120 smooth off 53.0/s, 33.4 ms -> 58.8/s, 17.0 ms; smooth on 24.4/s, 45.7 ms -> 59.2/s, 17.1 ms (the plain 12 ms gap gave 70/s at p95 24 ms).  Writes within 10 ms of the last: 0.3-1.1/s paced against up to 5.6/s (60, typing, smooth) and 115-122/s (120, smooth).  The cost: key to shown with smooth at 60 is p50 12.8 -> 20.0 ms (p95 28.1 -> 26.8): the key now shows with the next grid frame instead of a woken one, and with smooth off and at 120 key to shown is unchanged or better.  Render waits over 2 ms stay at 0-1 per run either way.
- A typed target the terminal doesn't show prints one line, once a process (`FrameRate#pace_notice`): paced, above `max_shown_fps` (83 on Konsole before 26.04) "Konsole before 26.04 shows at most about 83 frames a second: pacing writes; target 60 is the smoothest on a 120 Hz display; ui.pace :exact turns pacing off"; with `:exact`, where the target collapses (above 100), the konsole-pacing line naming target 60 (a divisor of common 120 Hz displays: 90 would judder 3:4) and `ui.pace :terminal`.
- `ui.perf`'s report has a "Rates (a second)" block: target, refreshes, written, new data (snapshots), and the frames the terminal showed, estimated from the write times by its profile, with a sentence where two differ by more than 15 %.  `ui.perf` and its actions return a one-line `Facade::PerfStatus` (`ui.perf :stop` returned the `UI::Perf`, whose rings Pry printed as 209 000 lines, holding the GVL about 0.8 s; `Perf#inspect` is one line too), `ui.perf.report` and `.stop` work, and `ui.perf` with no argument while recording prints a status line instead of the report.  Mistyped `ui.smooth`/`ui.pace`/`ui.perf` arguments raise with a did-you-mean (`Facade.did_you_mean`: DidYouMean, else one or two edits away).

## The tiled screen (ui-5, 2026-10-15)

Design spike: research-ui-4 0ff717a7 (`research/terminal-ui-4/`: README, ARCHITECTURE.md, COMPARISON.md, the prototype).  Maintainer's decisions (2026-10-15): REPL option (a2), real Pry/Reline on an in-process pty, rendered by our VT model ("(b) only if probe wins": DECSLRM margins not built); the REPL pane has its own scrollback (10k lines, `/` search, OSC 52 copy) while the band keeps the terminal's; Ctrl-] (0x1D) is the NAV key, immediate, and a lone Esc enters NAV only when `ui.nav_esc = 0.3` (seconds; 0.25-0.4 sensible) is set, an Esc followed by a key within that time going to Reline; pane files, layouts, and themes are all data loaded by a Prism walker; interactive resizes save weights as cells/gcd; one Action stream for keys, the `:` palette (Ruby one-liners in the console binding), and MIDI (`ui.on C1, :zoom`); glyphs picked by measuring ambiguous width; a gem-boundary guard spec.

```ruby
ui :tiles                 # transport/form row; the REPL beside tracks, queue, meters, scope
ui :studio                # tracks | REPL over a scope | tabs of meters, knobs, cpu
layout :mine, focus: :repl do
  cols height: 1 do pane :transport; pane :form end
  cols do
    repl weight: 2
    rows(width: 40) { pane :meters, height: 6; pane :scope, look: :scope, rate: 30 }
    tabs :knobs, :cpu
  end
end
ui :mine
ui.split :v; ui.show :knobs; ui.resize :right, 4; ui.undo; ui.zoom; ui.save :mine
ui.on C1, :zoom; ui.on_cc 21, :tab; ui.on(C2) { go :drop }
ui.theme :mono; ui.nav_esc 0.3; ui.mouse
```

**Keys.**  REPL mode: everything goes to Reline (Ctrl-C is SIGINT, as a terminal's line discipline would send; Ctrl-Z hides the tiles, see below).  Ctrl-] toggles NAV: 1-9 (the badges), Tab/Shift-Tab, arrows focus (h j k l until ux-r4b), p the pane before; z zoom; s/v split below/beside (the new slot shows how to `show` a pane); x close; = equalize; Shift-arrows resize by 1, Ctrl-Shift-arrows by 5 (arrows and Shift-arrows until ux-r4b); u / Ctrl-R undo/redo (100 steps; focus isn't a step); [ ] tabs; PgUp/PgDn/Ctrl-B/Ctrl-F/g/G scroll the REPL's scrollback; / search (smart case, backward; n/N again); y copy (the match's line, else the visible text) with OSC 52; : palette; Ctrl-L redraw; i, Esc, Enter, Ctrl-] back.  The status line shows the mode, the focused pane, hints or the last message, and bar:beat.

**Input as a state machine (ux-1 round 3, 2026-10-17).**  `MB::Term::Input::Router` declares its states (`STATES`: :repl, :play (a screen without a console), :nav, :line, :grab, :overlay, :pending), the event classes it tells apart (`EVENTS`: nav_key, keys_key, interrupt, suspend, prefix, global, key, release, paste, tick, other), and a `TABLE` row (handler, what it does) for every pair; `Router.table` prints it; `router_spec.rb` checks every pair has a row and a handler, Ctrl-] from every state lands in NAV and a second press returns, overlay + key == NAV + key for every NAV binding, and random walks keep the invariants.  Ctrl-C, Ctrl-Z, F2, releases, and the overlay go through the table (one owner for input; Tiles#handle only relays while hidden).  Prefix chords (`Router::Prefix`): the held lone Esc (`nav_esc`).  (Ctrl-W was a prefix of vim window keys with a word-delete pass-through until ux-r4b; it is the one-shot NAV state :once now, below.)  Ctrl-] always enters NAV, from KEYS and prompt lines too (a line is kept), and Ctrl-] in NAV goes back; i/Enter/Esc in NAV: the REPL.  Keys a state can't take are refused with the reason on the status line.  Focus follows the mode (REPL mode: the REPL; KEYS: the keyboard), pinned in one place (`Tiles#tile`).  Input handling and Ruby mode changes share one lock.

**The key table** (`UI::Keys`, pattern C): keymaps carry their help (`Keymap#on(..., help:, label:)`, `group`, `doc`, `help_groups`): Router::NAV, Keys::NAV_EXTRA, Keys::ONCE_DOCS (Ctrl-W), the REPL's direct keys (`REPL_DEFAULTS`: Alt-PgUp/PgDn scroll the REPL pane without NAV, typing back to live; skipped when the user's inputrc binds them, read by `Input::RelineKeys.user_bound?` in every byte form), `Keyboard::KEYMAP` (KEYS mode acts through it), step entry docs, script screens' `SONG_SCREEN`/`SYNTH_SCREEN` (Tiles `play_keys:` + `on_action:`; repeats act like presses; Esc quits a song screen, panics a synth screen), and `ELSEWHERE` (each REPL-side UI key in the band and without a UI).  The `?` overlay, `help :ui` (`Tiles::KEY_HELP`, `Tiles.key_table`), and `keys_spec.rb` read it.  `ui.bind ['k', :ctrl], :keys` / `ui.unbind` add users' keys (REPL or NAV; Ctrl-K as the keyboard toggle is such an option, maintainer 2026-10-17).  Panes declare keys of their own (`UI::PaneKeys`: `keys do on 'L', :cycle_look, help: ... end` + `key_<action>(state, *args)`), consulted first in NAV while focused and shown in the overlay.

**Outside the tiles** (`UI::ConsoleKeys`, Reline *default* bindings, so an inputrc wins): Ctrl-] opens the tiled screen in NAV (the band's counterpart: band/mini :tiles, deck :studio; hidden tiles come back) and F2 KEYS, the line being typed carrying on in the REPL pane; IDE editing keys Ctrl-Backspace (^H unless it is the tty's erase), Ctrl-Delete, Ctrl-Shift-Delete (`Input::RelineKeys.install_editing_keys`).  Never call Reline's own `Config#read`: Reline sets up its default bindings (bracketed paste, cursor keys) only when it reads the inputrc itself.  `ui` returns `UI::Facade`: the same surface in every mode (`ui.keys` from the band opens the tiles; the other screen's commands say what to do; `ui.mode`, `ui.screen`).

**Output owner.**  `Tiles#write` is the one writer of frames; a frame with a raw newline is dropped of it and warned about (specs fail).  Status flashes are one line (`Tiles.one_line`).  Palette lines of console Ruby print their output and value into the REPL pane (`ReplHost#print_above`).  Warnings: a new one opens the messages pane (NAV m: away); the REPL's own command's warnings print in the REPL (`UI.repl_thread?`).  Flashes order by when things happened, not when the painter looks (fixes-ui-specs, 2026-10-17): each flash keeps `UI.messages.seq` at its time, and the painter's message flash replaces only flashes older than the message (an action's summary naming its own failures stays; the pane still opens).  Specs of screen state that the painter also writes fix the order by holding the screen's lock or calling `Tiles#refresh` themselves, instead of relying on whether the painter ticked (messages_spec's ordering example).

**Key repeats** (`Keyboard::HoldTracker`, item 9): per-key states :idle/:pressed/:repeating with `TRANSITIONS`; gaps up to 90 ms are always repeats, a first repeat within 80 ms (40 ms once learned) of the delay is a repeat, and a strike followed by short-gap repeats teaches the delay retroactively (at most the first hold of a session retriggers once); `ui.keyboard.repeat_delay =` sets it.

**Ctrl-Z hides, the set plays on** (maintainer, 2026-10-15: "Hide screen, keep playing"; no process suspend in `:tiles`).  Ctrl-Z leaves the alternate screen for the plain console: the REPL's pty is relayed to the terminal's normal screen (its bytes written through unchanged, input bytes passed to the pty, Ctrl-C still SIGINT), so the same Pry and Reline keep going, the line being edited included (Reline redraws it after a forced SIGWINCH), and audio, the Session, and the UI's layout, edits, and REPL scrollback all stay.  Ctrl-Z again, `ui`, or `ui :<that layout>` brings the tiles back as they were; `ui off` or `exit` ends them.  No fd is reopened while hidden (reopening fd 0 while Reline waits on it blocks), and signal traps stay (Reline's WINCH handler for the line it reads wraps ours).

**How it works** (the generic layers are the mb-term gem since term-extract-1, 2026-10-29: `gems/mb-term/`, `MB::Term`, a path gem; see "The mb-term gem" below; the `UI::VT`, `UI::Input`, `UI::Viewports`, ... names in this section were aliases of its constants until omnibus16 (2026-10-29) migrated every caller and removed them: read them as `MB::Term::VT`, `MB::Term::Input`, `MB::Term::Viewports`, ...):

- `MB::Term::Terminal`: alternate screen, raw input, bracketed paste, optional mouse/focus/kitty; `#leave` undoes all of it (twice-safe, at_exit, exceptions); a probe fenced by DA1 (DECRQM 2026, ambiguous width by a cursor report after one ambiguous glyph, kitty flags).  Tiles works on dups of the terminal's descriptors.
- `MB::Term::Input::ReplHost`: in `:adopt` mode (the console) fds 0/1/2 are reopened onto the pty's slave, so the running Pry and Reline need no configuration, and `puts`, warnings, `live_error` text, and subprocess output (ffmpeg) land in the pane; `ui off` reopens them onto the terminal.  `:thread` mode runs its own Pry (specs, `bin/ui_demo.rb --tiles`).  A reader thread (priority -1) feeds Pry's output to the VT in 4 KB pieces with `Thread.pass` between and answers its queries (Reline's cursor reports).  Pane resizes set the pty's size and send SIGWINCH (Reline's own handler).
- `MB::Term::VT` (`VT.new` makes the C `NativeVT` since term-2, 2026-10-31; `RubyVT` is its reference, see "The C VT" below): rows as Strings in RubyVT (one character per cell, "\0" the right half of a wide character, widths from Reline's table with the probed ambiguous width), styles allocated only for styled rows, palette colors kept as indexes (fast_ui's `INDEXED` bit: SGR 31 stays 31, so the user's palette shows), scroll regions, the alternate screen, insert/delete, pending wraps; scrollback with stable absolute line numbers; draws only changed rows.
- `MB::Term::Input::Decoder` and `Router`: bytes to Key (with its bytes, forwarded unchanged), Paste (one event), Mouse, Focus, Reply; modes :repl, :nav, :line (palette and search prompts with history).
- `MB::Term::Viewports`: the prototype's immutable split tree (Pane/Split/Tabs Data, placement by fixed sizes then weights by largest remainder then mins), Tiler operations with undo, pane options per placement (`pane :scope, look: :scope, rate: 30`), `to_ruby`, and the loader.
- `MB::Term::DataFile`: the one Prism walker for layouts, themes, and pane files: calls from a closed table per block level, literal values, constants from a closed table, LoadError with file:line and did_you_mean; replayed through the builders people use.
- `UI::Tiles` (mb-sound side): input thread, painter (ui-3's panes at their rates, the REPL from its VT only when it changed, gap rules with the focused pane's in the key color, NAV badges, status line; one diffed frame per refresh in DEC 2026 with the cursor placed in the REPL), the palette (a UI command like `show :knobs` runs on the screen with its arguments evaluated in the console binding; any other line is evaluated in the console binding, recorded before each line by `UI.install_pry!`), MIDI bindings read from `Session#midi_log` (no render lock), data-file reloads once a second.
- Data files (in `UI.layouts_dir`): layouts (`ui.save`; a file with a `repl` pane is tiled, else a band), `themes/*.rb` (`theme :mine, based_on: :default do role :title, '#9ef01a', bold: true; role :dim, 245; role :warn, :yellow; glyphs :ascii do play '>' end end`; built in :default, :paper, :phosphor, :mono; the sound inspector's section heading colors are roles too, `:band_source` ... `:band_fx`, `:band_knobs`, foreground colors since inspector-headers-1), `panes/*.rb` (`pane :mix, kind: :meters, title: 'mix'`; kinds are Ruby: the built-in panes, :text, :knob, and `UI.pane_kind`).

## The keyboard (ui-6, 2026-10-16)

Maintainer's request (2026-10-16): "a virtual keyboard panel for realtime note entry and clip creation that uses roughly the same key bindings as jack-keyboard or zynaddsubfx virtual keyboard when focused", then "Step editing also requested, maybe with one octave for notes and the number keys for duration?  Explore a couple of ideas and build one that makes sense".

```ruby
ui :keys                  # tiles with the keyboard below the REPL, starting in KEYS mode
ui.keys                   # (or NAV K, F2) KEYS mode, the pane put in below the REPL if missing
ui.keys off: :tap         # note-off mode: :auto, :release, :hold, :tap, :legato
ui.keys step: true        # step entry
ui.keys patch: ->(v) { v.hz.square * v.amp_env }   # the default patch (nil: none)
ui.keyboard.clip          # the last clip made in step entry (.clips: all)
ui.keyboard.base = 60     # z is C4 (octaves; also - and +)
```

**Research** (sources in the ui-6 report): jack-keyboard binds X hardware keycodes in one QWERTY table: lower row z s x d c v g b h n j m , l . ; / (C to E), upper row q 2 w 3 e r 5 t 6 y 7 u i 9 o 0 p [ = ] an octave up and \ the A above ] (the G# key would be Backspace); z = 60 at its default octave 4; keypad +/- (and main -) octave, Shift high velocity (100) and Ctrl low (32) over normal 64, keypad * / program, PgUp/PgDn bank, Home/End channel, Space sustain, Esc panic.  ZynAddSubFX's VirKeyboard has the same QWERTY rows (\ and Enter continue its upper row chromatically), Dvorak/QWERTZ/AZERTY tables, separate octave counters per row (z = 48, q = 60 by default), velocity and randomness knobs, and no octave hotkeys; it works only while the widget has focus.  Terminals: the legacy encoding sends presses and OS autorepeats only, no releases; the kitty keyboard protocol's flag 2 reports press/repeat/release (`CSI code;mods:event u`), and text keys need flag 8 too (all keys as escape codes).  Flag 2 support: kitty, Ghostty, foot 1.11+, Alacritty 0.13+, WezTerm with `enable_kitty_keyboard = true`, Windows Terminal 1.25+, iTerm2 (its "Allow application to change how keys are reported" setting; version unverified), Konsole (merged 2026-05, release unverified); not VTE/GNOME Terminal, tmux (PR open), xterm.  Autorepeat defaults: X11 660 ms / 25 Hz, GNOME 500 ms / 30 ms; macOS is often cited as 375 ms / 90 ms (unverified).

**Keys** (play mode): the two rows (z = C3, q = C4, as ZynAddSubFX), - and + or Left/Right octave (the z key stays a C, C-1 to C6), Up/Down velocity (normal 96), Shift accent (127; shifted punctuation of a US layout counts), Ctrl soft (40; legacy terminals send it for letter keys only, and Ctrl-C, Ctrl-Z, and Ctrl-M (Enter) keep their meanings), Home/End channel, Space sustain (held while down with releases, else a toggle), Esc all notes off (CC 64 0, CC 123), Enter `capture` into the armed tracks, \` the note-off mode, Tab step entry, Ctrl-] back (also Ctrl-C: all off and back, never an interrupt).  Program and bank keys are left out (mb-sound synths don't read them).

**Note-off modes** (`UI::Keyboard`, shown in the pane): `:release` with kitty event types (chosen by :auto when the probe answered the kitty query, or once a release or repeat event arrives), else `:tap` (the default without key-up, maintainer 2026-10-16: fixed-length notes, `ui.keyboard.tap` seconds, 0.25 by default; repeats never retrigger); `:hold` (by backtick or `ui.keys off: :hold`) guesses held keys from autorepeats, `Keyboard::HoldTracker`: a key's second event sooner than 0.6 of the repeat delay is a new strike, later ones are repeats, the delay and interval are learned from what arrives (from 0.5 s and 35 ms), a note ends 2.5 intervals + 30 ms after its last repeat or, for a tap, the delay + 0.12 s after the press; keys pressed within 60 ms hold together as long as any of them repeats (the OS repeats only the last key), so chords sustain; `:legato` each note until the next (the new note-on first, so mono voices glide).  Every way out sends note-offs: Ctrl-], Ctrl-C, Ctrl-Z, terminal focus loss (?1004 is on in KEYS mode), `ui off`, exit; the spec checks each.

**The path into the Session** (`Keyboard::Link`): a `MIDI::VirtualInput` (a MIDI::Input stand-in: `#send_bytes`/`#note_on` from any thread, `#read_raw` as RtMidi deltas) read by a `LiveSource` (its :exact timing, or MIDI_TIMING=asap) and added to the current Session's default MIDI input with `MidiInput#add_source` (new: extra streams merged into each span in frame order, the input's own first; drained and dropped while a take replays).  So typed notes are stamped on frames beside a hardware keyboard's and reach armed monitors, `rec`, `capture`, the console's `midi`, the MIDI log, and takes.  With nothing armed, entering KEYS mode starts a default patch on the input (player `:"keyboard/live"`, a soft filtered saw, 8 voices); it rings out on the first note after a track is armed.

**KEYS on the sound-design screen** (`Keyboard::Takeover`, ux-notes-2, 2026-11-02; the maintainer's note "Opening the keyboard in sound design mode should give me control over the sound and stop whatever else was feeding it", his choice "Arm + hold the clip"): with an inspector on screen and a patch track inspected, entering KEYS runs `arm :bass` (unless its monitor already plays; a silent arm is re-armed with its input) and `hold :bass` (arrangement.md, Mute and solo: Holds) as console lines through `UI.run_line` (journaled, undoable, in the take, but not printed: the maintainer, 2026-11-02, "No printout when activating the keyboard in sound design"; an error still prints); every way out of KEYS runs `unhold :bass` and puts the arm back (`disarm :bass`, or `arm :bass, monitor: false, input: ...`), each only if the takeover did it and it is still so.  The keyboard plays into the input the monitor reads (`Link#input=`: the default input, a named one, or a wired track's wire input, whose stream the hold silences).  A state table (:off/:on × enter/leave, `Takeover::TABLE`); graph tracks and unknown names are left alone.  Specs: `keys_takeover_spec.rb` (a clip, no clip, an arm already, a silent arm with an input, a wire, a graph; the pty screen's lines in and out).

**Latency** (Mac container, i9-9880H, 2026-10-16; `bin` not needed: a pty, `ui :tiles`, a realtime Session on paced NullOutput, keys typed 130-180 ms apart, 42 per run; "frames" = the note-on's stamped frame minus the Session's render frame when the byte was written; "wall" = byte written to the note-on stamped in a span):

| buffer | timing | frames p50 / p90 / max (ms) | wall p50 / max (ms) |
|---|---|---|---|
| 128 | exact | 3.7 / 5.0 / 5.9 | 6.7 / 8.1 |
| 512 | exact | 10.7 / 15.1 / 19.1 | 21.4 / 44.2 |
| 800 | exact | 22.8 / 29.4 / 31.9 | 40.9 / 49.1 |
| 128 | asap | 0.0 / 2.7 / 2.7 | 4.5 / 5.7 |
| 512 | asap | 0.0 / 0.0 / 0.0 | 16.1 / 21.3 |

:exact keeps the spacing of the keys (one constant latency of about a read, plus the output queue on a sound card: LiveSource's L, ~18 ms with :low), :asap snaps each note to the next buffer.  The terminal, the decoder, and the router add well under a millisecond; the rest is the buffer.  Not measured: a sound card's queue, a real terminal's keyboard handling, ssh.

**Step entry** (`Keyboard::StepEntry`, Tab).  Designs considered: (a) one row of notes plus the number keys for lengths, with dotted/triplet toggles, rest and tie keys, and marks: the maintainer's suggestion and the closest fit to `seq` (each key is one step, lengths are Note length methods, marks are `.acc`/`.slide`); (b) a tracker grid (a cursor over rows of steps at a fixed step length, editing in place): good for drums and editing, but a second editor (cursor movement, insert/delete) and grid-shaped where `seq` is list-shaped (`grid` strings already cover drum rows); (c) jack-keyboard has no step mode, and Elektron-style step buttons (a fixed 16-step bar, notes per step, trigs with parameter locks) suit a pad grid more than a QWERTY row.  Built: (a).  Lower row notes (z..m , . / from the keyboard's C), 1-7 whole..64th, 8 dotted, 9 triplet (toggles), r rest, t tie, a accent and \` slide on the last step, Shift accents a note, notes within 80 ms (or, with releases, while a note key is down) join the last step as a chord (`C3.n4 & E3.n4`), Backspace undo, Delete clear, p plays the clip through the keyboard's output (tick-scheduled), w swaps the clip so far (`.loop`) into each armed track at its next launch point through `Arrangement#play` (the `bg :lead, clip` path: a swap if the track plays, else a launch; journaled and undoable) and keeps the steps for more edits (Shift-Enter does the same where the terminal sends it apart from Enter, i.e. with the kitty protocol; legacy terminals send CR for both, so w is the reliable key), Enter finishes.  The clip is built by calling the DSL (`MB::Sound.seq(...)` with Note constants, `Rest`, `Tie`, length methods, `.d`/`.t`, `.acc`, `.slide`, `&` for chords), the commonest plain length factored out (`seq(C3, D3, E3.n4).n8`), so its recipe prints it back (`to_ruby`; the spec evaluates the text and compares events).  Each entered note sounds for its length (0.08 to 1 s) through the same Link.  Enter keeps the clip in `ui.keyboard.clips` and puts its Ruby on the REPL's line (a bracketed paste, not run), back in REPL mode, so naming it is typing `riff = ` in front.

**Specs**: `keyboard_spec.rb` (rows and keys; each mode with a fake clock: release/repeat events, autorepeat hold, quick re-strikes, learned timing, chords, tap, legato, sustain, panic, all_off in every mode; step entry with the to_ruby round trip, chords by time and by held keys, preview, Enter; the pane's text), `tiles_keys_spec.rb` (a pty: `:keys` with kitty sequences, NAV p with legacy keys and every exit, step entry onto the REPL line, an armed track captured from typed keys through a realtime Session), `decoder_spec.rb` (event types), `midi_input_spec.rb` (merged sources, a VirtualInput's timing).

**Open**: the band (ui-3) can show the pane but has no input of its own (Reline owns stdin), so KEYS mode is tiles-only; a plain-console `keys` prompt is possible later.  Non-US layouts: legacy Shift detection maps a US layout's shifted punctuation; kitty's base keys are layout-independent for the letter rows only.  Program/bank keys, per-row octaves (ZynAddSubFX), and showing a hardware keyboard's notes on the strip are not built.

## UI round 4: the feed contract (ux-r4-feed, 2026-10-18)

Data the round-4 panes (ux-r4-panes) draw from, published before it was built so the panes could start against it.  Built in the same branch (specs `spec/lib/mb/sound/ui/feed_round4_spec.rb`, `spec/ext/mb/sound/fast_loudness_spec.rb`, `take_spec.rb`).  Panes ask for the bus meters with `needs: [:buses]`.  Fast data rides the per-buffer `Snapshot` (render thread, no render lock from the painter); slow data rides `Slow` (Poll, 4/s, painter thread, frozen, cached per immutable clip).  Every field defaults to empty/nil, so panes draw on older sessions and in `Snapshot.fake`.

**Snapshot (per buffer)**

- `bus_levels` - `{ bus name => BusLevels }` while a visible pane `needs :buses` (else `nil`).  `BusLevels = Data(:input, :output)`, each a `Levels = Data(:peak, :rms, :short)`: `peak`/`rms` Arrays of dBFS per channel over the snapshot's buffers (peaks never missed), `short` dBFS of the mean power of the channels over the last 300 ms (a VU-like short-term level, 300 ms exponential).  Input is what reached the bus (main outs routed `to:` it plus sends); output is after its chain and its mute (what goes on toward its `to:`).  A sleeping bus reads `-Float::INFINITY`.
  Cost (Linux desktop, Ryzen 7950X, no YJIT, 4 buses, 8 stereo players with 2 sends each, snapshots at 60/s): 0.096 ms per 800-frame buffer (0.57% of realtime), 0.038 ms per 128-frame buffer (1.43%); about 2.5 ns per sample metered plus ~0.8 µs per bus or send per span.  The first version (Numo `abs.max` and `(x * x).sum`) cost 1.7% / 6.6%; the peak and sum of squares are one C pass now (`FastLoudness.peak_sumsq`, exact Ruby mirror `BusMeter.peak_sumsq_ruby`, the `peak_sumsq` kernel).
- `send_levels` - `{ [player, bus] => SendLevel }` (same `needs :buses`).  `SendLevel = Data(:player, :bus, :gain, :level)`: `gain` the send's gain in dB this buffer (the send knob; `-Float::INFINITY` at 0), `level` a `Levels` of the signal sent (post-fader, after the send gain).  A track routed `to:` a bus shows as that bus's input, not as a send: one concept (a bus is a named chain; `to:` sends everything, `send:` sends a level).
- `notes` - frozen Array of `HeldNote = Data(:note, :velocity, :channel, :source, :input, :frame, :pos)`: notes held now on the Session's MIDI inputs (updated in `MidiInput#pump` from the events of each span, so they match what graphs play): `note` 0..127, `velocity` 0..127, `channel` 0-based, `source` `:input` (the input's own stream: an external keyboard) or the label of an added source (`:keyboard` for the UI's virtual keyboard; `MidiInput#add_source(stream, label:)`), `input` the MidiInput's name (nil = default), `frame`/`pos` where its note-on landed.  Always present (a reference read).  `sounding` (reserved, nil): notes after a scale transform, for "pressed vs sounding"; midi-consol-2's stream transforms fill it later.  Until then the keyboard pane shows pressed = `UI::Keyboard#held` (its own keys, already scale-mapped) and input = `notes`.

**Slow (Poll, 4/s)**

- `matrix` - `MatrixInfo = Data(:tracks, :scenes)` or nil without tracks.
  - `tracks`: Array of `LaneInfo = Data(:name, :q, :state, :playing, :queued, :slots)`; `q` the launch quantization as text, `state` `:playing`/`:stopped` (as of landed changes; `Snapshot#lane_state(name)` merges the per-buffer player state from `parts`: :starting, :stopping, :ringing, :fading, :muted, :asleep), `playing` the slot index playing (or nil), `queued` Array of `LaunchInfo = Data(:seq, :kind, :slot, :lands, :pos)` (`kind` `:launch`, `:stop`; `slot` index or nil; `lands` bar:beat text, `pos` whole notes), `slots` Array of `ClipInfo` (below), append-only per track (a slot's index never changes in a session, so `launch :bass, 3` replays the same in takes): clips the track's scenes give it (scene order), then clips launched on it, its captures (`bass_1`...), and tweaked versions as they appear (a scene defined later appends its clips).
  - `scenes`: Array of `SceneInfo = Data(:name, :cells, :current, :queued)`: `cells` `{ track => slot index | :stop | :keep }`, `current` true for `Arrangement#current_scene`, `queued` a `LaunchInfo` or nil.
- `ClipInfo` keeps its fields (`name`, `kind`, `bars`, `pattern`, `used`) and adds `key` (a stable display key: the clip's name, else `"bass#3"`, track and slot) and the detail pane's data, frozen and computed off the render thread once per clip (clips are immutable): `loop` (true/false), `length` (whole notes, Rational), `events` (frozen Array of `NoteInfo = Data(:start, :length, :note, :velocity, :row, :marks)`; whole notes; `note` a MIDI number or nil for kit rows, `row` the kit row name or nil, `velocity` 0..1, `marks` frozen Array of Symbols like `:accent`, `:slide`, `:flam`), `ruby` (its recipe's text, `to_ruby`, or nil), `range` (lowest..highest note, or nil).  The detail pane never needs the clip object.
- `racks` - frozen Array of `Rack::RackInfo` (one per instance with rack knobs, as `Session::Racks#rack_info`: name, path, kind, signature, ports, latency, knobs (Session knob names), knob_specs; ux-r4b renamed macros/macro_specs).  Rack knob values are knob values: `Snapshot#knobs` includes every Session knob, rack knobs included, per buffer.
- `buses` (BusInfo) gains `sends` (`[player, ...]` sending to it) and `sources` (`[player, ...]` routed `to:` it); `routes` as before.

**Console commands** (journaled, undoable, launch points `on:`/`in:`/`at:` like `bg`; each one console line, so panes emit them through `UI.run_line` and takes print them back as written):

- `launch :bass, :bass_b` / `launch :bass, 3` / `launch :bass, :bass_b, on: :beat` - plays a track's slot by clip name or slot index (the `bg :bass, clip` path: `Arrangement#play`); returns the journal entry.  Scenes keep `go :drop`, stops `stop :bass` (ring out).  (`launch` is free: no MB::Sound method or Pry command.)
- `tweak :bass, transpose: 2` (also `legato: 0.8`, `swing: 0.6`, `quantize: 1/16r` or `true`, `:reverse`, `:halftime` (length x2), `:doubletime` (/2), `:double` (repeat to twice the length), `:half` (keep the first half); an octave is `transpose: 12`) - one transform of the track's current (or queued) clip, played at the track's launch point as one change and one undo step; the new clip is named after the old one with the transform (`:"bass_a/t+2"`) and becomes a new slot.  (`edit` is a Pry command; `tweak` is free.)

## ux-r4 navigation and pane rates (ux-r4-nav, 2026-10-18)

The maintainer's answers to round 3 (workbench briefs ux-r4-notes.md items 1, 2, 4).

**Going into panes** (item 1: "Enter focuses/enters the SELECTED pane").  NAV picks a pane (numbers, Tab, arrows since ux-r4b) without going into it; Enter goes in: the REPL pane into REPL mode, the keyboard into KEYS, a pane whose kind declares `mode_keys` into its own mode (the Router's new `:pane` state), any other pane just stays focused (a flash says so).  `ui.enter :clips` does the same from Ruby.  In `:pane` every key goes to the pane: its `mode_keys`, then its NAV-time `keys`; unbound keys are refused on the status line (never NAV's, so a matrix can bind arrows, h j k l, and Enter); Esc and Ctrl-] go to NAV (Ctrl-] in NAV comes back in), `?` lists the pane's keys first, F2 / Ctrl-C / Ctrl-Z act as in NAV, pastes and Ctrl-W are refused.  The status badge names the pane (` CLIPS `) and the hints come from its mode keymap; the pane's per-placement state has `state[:mode] == true` while in (draw the cursor then).  The mode follows the focus: anything that moves the focus (Ruby `ui.focus`, a jump, a layout change) drops to NAV (`Tiles#tile`), and `Tiles#mode_problems` checks the pane mode invariants (the focused pane has mode keys, the marked pane is the focused one, not hidden).  Esc in NAV still goes to the REPL, so the levels read pane -> NAV -> REPL.

**Jump letters**: a letter beside a pane's number in NAV (" 3 t ") focuses it and goes in, as Enter: i the REPL, k the keyboard (K until ux-r4b; KEYS; put in below the REPL when missing), t tracks, e meters (`Keys::JUMPS`, bound in NAV_EXTRA), and `jump 'a'` in a pane class (`UI::PaneKeys`; bound per screen in a `:jumps` keymap from the panes on screen; `ui.jump :tracks`).  A jump to a pane not on screen flashes how to show it.  `k` stayed NAV's focus-up (h j k l mirror Ctrl-W h j k l), so the keyboard is K; NAV p now means what Ctrl-W p means (the pane focused before) instead of KEYS.  `Keys.check_jumps` (keys_spec over every Pane subclass) keeps jump letters off NAV's keys, the Ctrl-W window keys, and each other.

**Pane rates** (item 2: "run panes at 60/s or at target_fps, and have them slow down and take turns when the CPU is loaded").  `UI::PaneRates` (`lib/mb/sound/ui/pane_rates.rb`; used by Tiles and the band through `FrameRate#panes_to_draw`): meters, scopes, and spectra (`:meter`) and the transport, knobs, lane, and keyboard (`:live`) run at the painter's target (`ui.target_fps`, 60 by default; never below their own rate); list panes (`:list`: tracks, queue, buses, clips, log, cpu, form, messages, and new kinds unless they define `priority`) keep their own rates, since the data they show changes a few times a second (UI::Poll reads 4/s).  A layout's explicit `rate:` wins.  Load per frame: the painter's paint + write time as a share of the frame period (smoothed, ALPHA 0.2) and the render thread's load (`Snapshot#load`).  Busy (share > 0.5 or render > 0.8) for STRAIN (0.25 s) steps down one level; calm (share < 0.2 and render < 0.6) for EASE (2 s) steps back up, EASE_QUIET (0.5 s) while quiet (share < 0.1, render < 0.3; inspector-nav-1: after `design` the warm-up frames, 200-490 ms of YJIT compiling, first walks, and voice copies, took the sound screen to level 4, and the quiet painter, 0.03-0.08 of a frame, climbed back in 11-17 s with the inspector and preview at 8-15 redraws/s; now about 5 s); between them the level holds.  `LEVELS`: 1 halves live and list panes, 2 quarters lists and lets two non-meter panes draw per frame (the most overdue first), 3 halves meters and gives one turn, 4 quarters meters (never under 0.5/s).  A state table (`TRANSITIONS`, :steady/:strained/:easing x :busy/:fine/:calm) drives it; `pane_rates_spec.rb` simulates a fake clock with synthetic painter and render loads (full rates when idle, steps one at a time, meters keeping the most, turns, recovery, every pair, a random walk).  NAV f puts each pane's measured rate beside its number (refreshed in the chrome once a second; only the changed cells are written) and the readout adds the level when it isn't 0, and names the slowest live pane when it draws under 90% of the target (`60/60 Hz (preview 9.5/s) · ...`: the painter's 60 refreshes said nothing of the panes it skipped; inspector-nav-1); `ui.frame_rate[:rates]`, `[:live_panes]`.

Cost: the painter now draws meters and scopes 60 times a second instead of 30 (`band_spec`'s deck: 51 draws a second at 10 ms ticks).  Measured on the Linux desktop's container (Ryzen 7950X, `bin/ui_demo.rb --tiles -s 20`, 40x120 and 60x200, master-ai and the branch alternating, two runs each): painter CPU per refresh p50 0.15-0.20 -> 0.22-0.29 ms (3.3 instead of 1.8 panes per refresh; about +0.5% of a core at 60 refreshes/s), p99 unchanged (1.2-1.6 ms), render-thread wake delay p99 unchanged (0.00-0.54 ms both), bytes per written frame unchanged (370-420).  That is about 2% of a 60 Hz period, so the level stays 0 unless the render thread is loaded or the terminal is slow to take writes.

**WINCH cycles** (fixes the Mac's intermittent tiles_spec SystemStackError, 2026-10-18): Reline 0.7's WINCH handler calls whatever handler Reline replaced most recently (it reads `@old_winch_handler` when it runs), so a screen wrapper W around Reline's R1, saved by the next prompt's `set_winch_handler`, made R1 call W and W call R1 forever on the next SIGWINCH.  `UI::Signals.handler` builds wrappers that ignore calls made while they run (any cycle ends after one round); screens install idempotently.  Lesson -> mechanism: a chained handler can't trust the handler it wraps to be acyclic, so every wrapper is re-entrancy-guarded by construction (`signals_spec` reproduces Reline's semantics; a plain proc there raises SystemStackError).


**Transport guard** (item 4): `spec/support/transport_guard.rb` fails an example that leaves the default transport moved (position, tempo, meter), naming what moved.  Measured first in report mode (2026-10-18, the full suite): 2 of 9089 examples left it moved (rack_documents_spec, channels_spec's `play`), both fixed with a rewind, so failing costs almost nothing and names a new offender where it is written.  spec_helper's reset before every example (ux-r3-session) keeps results independent of the order regardless; the guard keeps the CLAUDE.md convention, which matters in the console and scripts, where nothing resets the transport.  Rewind in an `after` block (an `around` hook's ensure runs after the check).  `MB_SOUND_TRANSPORT_CHECK=report` lists offenders after the run instead (`rake spec:parallel` gathers them per process), `off` skips it.

**Spec rule: wait for transitions, not states** (2026-10-18): the Router changes its state before `Tiles#mode_changed` pins the focus and puts panes in or out, so a spec that sees the new mode can read the focus mid-transition (tiles_keys_spec's F2 example failed under load).  `wait_mode(tiles, :repl)` / `wait_settled(tiles) { ... }` (spec/support/ui_helpers.rb) evaluate under the screen's input lock, which the input thread holds for a whole event; a 0.3 s stall injected into `mode_changed` fails the old waits and passes these.  Likewise, wait for every line of a command's output you read, not only the first.

**Stopping and spec waits** (test-speed-3, 2026-10-18): `Tiles#stop` wakes the input thread through a pipe (`#wait_input` selects on the terminal and the pipe): `Thread#wakeup` doesn't end an IO wait, so every stop used to wait out the reader's 0.5 s timeout and kill it (6 stops were 2.8 s of tiles_property_spec; tiles_spec checks the reader ends unkilled).  Specs: for "after these edits, every pane as drawn", call `tiles.refresh` (a frame on the calling thread, full after a relayout, as the painter's next would be) instead of waiting for quiet output; for what Reline shows, poll the REPL's VT (`host.vt.lines`) rather than the painted screen (a frame later, ~55 ms per wait), and match the prompt line, never the whole screen (a line typed earlier still shows there: tiles_keys_spec's history check passed before Up acted). ## Starting processes: the process starter (spawner-1, 2026-11-03)

The maintainer's choice after hand-tune-2 (2026-11-03, "Merge, starter process"): "a tiny starter process launched at startup that starts other processes (this worker, ffmpeg, git) without holding the GVL, removing spawn-while-playing risk everywhere".  Starting a process from the console forks its big heap with the GVL held (Ruby uses vfork on Linux, not on macOS), so a playing render thread waits for it: hand-tune-2 measured 20 render-thread GVL waits of 1 ms or more in 30 s (longest 16.9 ms) with a process started every 2 s, against 7 at idle.

- **The starter** (`MB::Sound::Starter`, `lib/mb/sound/starter.rb`; its process `lib/mb/sound/starter/server.rb`): bin/sound.rb launches it once before anything plays (`Starter.start`; `MB_SOUND_STARTER=0` skips it), as does spec_helper for the suite.  Plain Ruby with `--disable-gems`, loading only socket and json: about 13 MB RSS (16 MB after 260 children), 24 ms to start, in its own process group (Ctrl-C at the terminal doesn't reach it or its children, as `pgroup: 0` kept ffmpeg out of it before).
- **IPC**: one UNIX stream socket pair, the starter's end given as fd 3 (close-on-exec in the starter, so children don't inherit it).  Requests are frames (4-byte length, JSON: argv as `Process.spawn` takes it, the console's whole current environment with changes applied, its directory, `pgroup`), with the child's stdin/stdout/stderr riding on the frame as SCM_RIGHTS: pipe ends or files the console opened itself (`IO.pipe` doesn't fork), so the console keeps its ends and the starter only forks.  The starter reads with `recvmsg` for exactly the frame's remaining bytes (a read never takes the next frame's first byte, which carries its descriptors), spawns, closes its copies, and answers with JSON lines: the pid, or the Errno and detail (raised again in the console as `Process.spawn` would), and later `{exit:, status:, signal:}` from a waiter thread per child.  Kills go through the starter, only to children it hasn't reaped (no signal to a reused pid).  Named pipes were the alternative: they'd need paths, cleanup, and opening order; descriptor passing works the same on Linux and macOS.
- **API**: `Starter.spawn([env,] *cmd, in:, out:, err:, chdir:, pgroup:)` (redirections: an IO, a path, `:null`, `err: :out`) returns a `Child` (`#wait(timeout)`, `#kill`, `#alive?`, `#pid`); `.popen(cmd, 'r'|'w'[b])` returns `[IO, Child]`; `.capture(*cmd, stdin_data:, err: :capture|:out|:null|nil)` returns `[out, err, Status]` (Open3's capture3/2e/2 and backticks).  `Starter::Status` reads like `Process::Status` plus `#unknown?`.  `Starter#children` counts every child still running, `#child_list` lists them (`{ id:, pid:, argv: }`) for diagnostics (fix-flaky-1104: three suite failures of starter_spec's "40 children at once" were children other examples left running, ffmpeg readers of FFMPEGInputs never closed until the GC closed their pipes, so the spec counts its own).  A child's pid is set by the reader thread from the spawn's reply, before the exit line that can follow it at once (set by the spawning thread after it woke, a quick child's Status had no pid: 51 of 1200 statuses in 30 bursts of 40).
- **Fallbacks, never a hang**: where no starter runs (scripts, which start processes while nothing plays; a fork of the process, which inherits the object but not the starter; `MB_SOUND_STARTER=0`), the same calls start the process directly (`DirectChild`).  If the starter dies (EOF on its socket) or doesn't answer a spawn within `Starter::TIMEOUT` (10 s; it's then killed, since descriptors in its unread frames stay open while it lives and a pipe sent to it would never end), callers start directly with a warning once per call site (`Internal.warn_once_per_site`), and its running children end with an unknown status (`FFMPEGInput`/`FFMPEGOutput#close` accept it).  The starter exits at the end of its socket (the console closed, exited, or crashed), leaving its children running; `ExitClose` closes it after everything registered later (outputs waiting for their ffmpeg).
- **What goes through it**: every process start in lib/: ffmpeg pipes and ffprobe (audio_io.md), Library saving's git, Bench's git, child renders, and FLAC writes, codec peak checks, `open_graphviz`'s dot and open, and refine's worker (hand_tune.md: started on demand at the first `tune` or `refine` instead of at every launch).  Left direct, with reasons in `spawn_sites_spec.rb`: the starter itself, the golden-set rake tasks (`sound_guard/`), the plot font script, mb-term's one `stty -a` at prompt setup (before anything plays; mb-term has no mb-sound) and its network REPL host.  bin/ scripts start processes directly (nothing plays when they do, or they don't start any), except `bin/dropout_probe.rb --inject spawn`, which launches a starter before playing.

## The mb-term gem (term-extract-1, 2026-10-29)

The maintainer (2026-10-29): "Can the terminal emulator simulation that was built for various tests and research projects be extracted as a library?" ... "Ruby first then the C, and compare performance.  My first theoretical application is running it over a network socket to share a repl session across machines, without using screen or tmux."  Chosen layout: a gem inside this repository with a path dependency.

- **Layout**: `gems/mb-term/` (gemspec, its own Gemfile and Gemfile.lock (term-2, 2026-10-31, the maintainer's decision of 2026-10-30), `lib/mb/term/`, `spec/`, README with the VT's supported and unsupported sequences); mb-sound's Gemfile has `gem 'mb-term', path: 'gems/mb-term'`, its gemspec depends on it, `lib/mb/sound.rb` requires `mb/term`.  Name provisional (`mb-term` is free on rubygems).
- **What moved**: `UI::VT` -> `MB::Term::VT`, `UI::Term` -> `MB::Term::Terminal`, `UI::Screen` -> `MB::Term::Screen`, `UI::Input` (Decoder, events, Keymap, Router, ReplHost, RelineKeys), `UI::Viewports`, `UI::Themes`, `UI::DataFile`, and from `Plot::Text` the Ruby grid `Cells` and the SGR color codes `ANSI`.  The old names were aliases until omnibus16 (2026-10-29) migrated every caller in lib/, spec/, and bin/ to `MB::Term::*` and removed them (`lib/mb/sound/ui/term_aliases.rb`, `Plot::Text::Cells`/`ANSI`); `term_integration_spec.rb` fails if they come back (constants or references in lib/, bin/, spec/). - **Specs**: the gem's (`gems/mb-term/spec/`, its own spec_helper: warnings fail examples, a temp dir per example) run in their own process from the gem's directory under the gem's own bundle, without mb-sound (`rake spec:gems`; `spec:parallel`, `spec:full`, `spec:quick`, and `merge:gate` run them after the suite through `spec/gem_specs.rb`, which sets `BUNDLE_GEMFILE` to the gem's Gemfile outside the calling bundle; CI too). - **The C VT** (term-2, 2026-10-31; the maintainer, 2026-10-30: "mb-term: its own Gemfile/lockfile, and the VT parser in C"): the whole model moved to C, not only the parser, since the feed's cost was spread over the parse, the row Strings and style Arrays, and the CSI splits, and VT#draw was ~80% of a refresh.  `MB::Term::VT` is a module (constants, `VT::Row`, `VT.sgr_for`, `#text`/`#total_lines`/`#search`/`#text_between`/`#inspect`, and `VT.new`, which makes `NativeVT` when fast_term is compiled, else `RubyVT`; `MB_TERM_NATIVE=0` or `native: false` for Ruby, as with `Grid`; mb-sound's `term_vt` kernel sets `VT.native`, so `MB::Sound.kernels = :ruby` switches it too); `RubyVT` is the old VT and the reference; `NativeVT` is `FastTerm::VT` (fast_term's `vt.c`) with RubyVT's keywords.  vt.c mirrors each step (String#scrub's rule for invalid UTF-8, the ASCII-run and per-character text paths, Reline's width table handed to the C once, pending wraps, tabs, resizes, dirty rows, replies); scrollback rows are trimmed to their last non-blank cell; `#draw` writes cells straight into native grids and makes RubyVT's `#put_run` calls on others, never holding a row pointer across a Ruby call; `#line_at`/`#screen` give `VT::Row` copies, `#line_text` a line's text.  `VT#scrollback` (an Array of Rows) became `#scrollback_length` (callers migrated); `#debug_state` gives everything for comparisons.  Fuzzing found edges of the Ruby that both now share: CSI parameters are their leading digits saturating at 65535 (`VT::PARAM_MAX`; `to_i` read signs, spaces, underscores, bignums), DECSTBM reads 0 as the default (`CSI 0;0 r` set the top to -1), a wide character in a one-column VT is dropped (it grew the row), `ambiguous_width=` clears the width cache, held-back bytes of a split UTF-8 character survive an incomplete sequence before them (lost before, so the screen depended on how reads split), and drawing a plain row with marks no longer allocates its styles.  Specs: `gems/mb-term/spec/vt_native_spec.rb` compares the whole state over captured streams (Pry fixture, colored listing, truecolor repaints, a full-screen program) in random pieces and 300 seeded random-byte cases (resizes, ambiguous-width changes, replies, draws both ways; `VT_FUZZ=N`, `VT_FUZZ_SEED=n`), and checks that bytes read at once or in any pieces give the same state, in both; vt_spec runs for both classes; the spec is in mb-sound's memcheck list (clean, 0.4 min under Valgrind).  Bench (`bench/term_bench.rb 5`, Mac container, CPU time, alternating): feed 76-142 MB/s in C vs 0.6-5.6 MB/s in Ruby (14-225x); VT#draw of every row 7-60 µs vs 73-1196 µs with the Ruby VT on the C grid; a REPL refresh 18-154 µs vs 112-1432 µs (4-14x).  `bin/ui_demo.rb --tiles --flood 20000`: reader CPU 36-59 ms vs 163-193 ms; Pry sets the pace (25-32k lines/s).  A source added to or removed from an extension now reruns extconf (the Rakefile's `refresh_makefiles`: the new vt.c was first left out of the .so).
- **Network REPL spike** (`gems/mb-term/examples/share_repl.rb`, the maintainer's first application): `ReplHost` gained `:command` mode (any program, PTY.spawn, the slave kept O_NOCTTY) and `#mirror` (raw output while the VT keeps answering queries); per-viewer changed-cell frames at up to 30/s or raw bytes, late joiners get the screen, localhost by default, tokens (read-write and read-only). ## The number nudge (repl-scrub-1, 2026-11-21)

The maintainer's takes of 2026-11-21 designed sounds by recalling one 150-250 character `fx`/`track` line fifty to sixty times and changing one number per try (the analysis of those takes recommended "an inline number scrubber in the REPL").  `UI::NudgeKeys` (prepended to `Reline::LineEditor` by bin/sound.rb, Reline *default* bindings) makes that one key: Alt-Up/Alt-Down step the number at the cursor and run the line as Enter would (`finish`, so Pry's eval, the take, the journal, and undo all see a typed line; it lands where the line lands, the session's quant unchanged); the line comes back on the next prompt (`Reline.pre_input_hook`, chained) with the cursor on the same digit.

- **Finding numbers**: `UI::NumberNudge` reads Prism tokens (byte offsets, as Reline's): number tokens, with an adjacent `UMINUS_NUM` as the sign, so strings, symbols, labels, identifiers, comments are never touched; `1.n8`'s 1, both ends of `150..1500`, `h3: -3`'s -3 are numbers; note names have none.  Off a number, the first press moves to the nearest one without changing it.
- **The step rule**: one unit of the last written digit, computed in integer units (no float noise: 0.19 -> 0.20, decimals kept); coarse (Ctrl-Alt) 10 units; fine (Alt-Shift) one unit of one more decimal (writes it: 0.125 -> 0.1251), refused on an Integer (the type never changes); signs come and go through zero (`5 - 1` -> `5 - -1` is valid Ruby); underscores regroup by thousands; exponents and r/i suffixes stay; hex/binary/octal refused.  A Reline numeric argument multiplies (Alt-5 Alt-Up).
- **Keys** (`NudgeKeys::BINDINGS`): the xterm forms (`\e[1;3A` Alt, `;4` Alt-Shift, `;7` Ctrl-Alt; Konsole, VTE, xterm; iTerm2 with Option as Esc+), the Esc-prefixed forms (Esc typed by hand, terminals sending Alt as an Esc prefix), and the 1;9/1;10/1;13 "meta" forms; jumps on Alt-Shift-Left/Right, since Alt-Left/Right are Reline's word moves (kept: nothing changes for someone who never presses the new keys).  The tiles pass these bytes through unchanged in REPL mode (the Router binds only Alt-PgUp/PgDn there; the Decoder splits Esc-then-Up into two keys, which Reline joins within its keyseq timeout).  Not measured on real terminals: Konsole scrolls one line on Shift-Up on the normal screen (Alt-Shift may scroll there too), GNOME/KDE may take Ctrl-Alt-arrows for workspaces; an inputrc can bind other bytes to `mb-sound-nudge-up` etc.
- **Coalescing**: a nudge waits `NudgeKeys.settle` (0.15 s) for another key (`in_pasting?`); keys arriving within it (a held key's repeats, presses typed while the line ran) edit on and the last one runs the line once.  A key other than a nudge in that time leaves the edit for Enter.  So a tap is one landing, a hold two (the first press, then the release).  Incomplete Ruby is only edited.
- **Errors**: the line's error prints as Enter's would and the stepped line stays on the prompt (no rollback).  Refusals flash on the tiles' status line (`:refused` action), else ring the bell.
- **History** (`UI::NudgeHistory`, prepended to `Pry::History`, `<<` included since Pry aliases it): the recalled line stays, plus one entry for the run's latest version, replaced each step; the history file gets that version when the next line comes or at exit (`ExitClose`).  The tiles' own Pry thread reads with `Reline.readline(prompt, true)`, which adds the line itself: handled.
- Specs: `number_nudge_spec.rb` (finder and rule tables), `nudge_keys_spec.rb` (Reline in a pty: runs, prefill and cursor, coalescing, jumps, fallback forms, incomplete buffers, refusals; history), `tiles_nudge_spec.rb` (the REPL pane with a non-realtime Session: three nudges of a wrapped line redefine a playing track each bar, history, undo), `spec/bin/sound_nudge_spec.rb` (bin/sound.rb in a pty with a track playing: each step lands, the take keeps every step, history one, undo, a failing line kept).
