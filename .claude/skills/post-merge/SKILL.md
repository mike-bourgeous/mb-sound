# After a merge

A merge isn't finished until these are done, in this order, without being asked (the maintainer asked for the note on 2026-09-28 and had to prompt for it once):

1. **Tests:** run them outside `/app` (maintainer, 2026-10-18), so `/app` is held only for the merge's git writes: either the Linux runner on the merge commit (`/claude/test-runner/run_test.sh <id> <sha> suite smoke [memcheck:changed]`; skip this step when the merged tree is identical to the tree the runner already tested), or `.claude/skills/post-merge/postmerge_tests.sh <worktree>` in the background in a detached worktree at the merge commit (`git -C /app worktree add --detach --lock /claude/worktrees/postmerge-<sha> <sha>`; clean compile, suite, smoke, `memcheck:status`; `FULLMC=1` adds the full memcheck, only when the maintainer asks for one (a pre-release step or a leak hunt; full runs are never due by merge count, 2026-10-18); the Mac's slower loaded runs are worth keeping, they found races the runner missed).  Remove the worktree afterwards.  A clean compile matters after ext/ merges: a stale `.so` passes while the merged C doesn't build.  Every failure is investigated right away, with no rerun first (maintainer, 2026-10-15), including the load-sensitive examples CLAUDE.md lists.  Script-only merges run only that script's specs.
2. **Merge report:** what merged (hash), before/after measurements, test results, anything left for the maintainer (cleanup, branches, decisions), and briefly the questions still open from earlier work (they get lost in scrollback).
3. **"Did you know" note:** two paragraphs on something from audio, Ruby, or a nearby field the project apparently doesn't use yet (grep the codebase first), tangential to the project just merged and ideally useful for the next one; something to play with, not a lecture.  For a batch of merges, one note covers the batch.  Publish it to the Did You Know page (https://claude.ai/artifact/1a5voMUcBSrtTmCUG4JyUM, maintainer's request 2026-10-14: merges are frequent, notes got missed in scrollback): append an entry to `/app/workbench/pages/did_you_know/notes.json` (tmp/did_you_know is a symlink to it) and republish as its README says (publish from the real `/app/workbench/...` paths, never the `tmp/` symlinks: a symlinked source needs a consent dialog the remote UI doesn't show; before every publish, read the live `notes.json` (`Artifact` read with `path: "notes.json"`) and add your note to that copy, since both machines' sessions publish this page); the merge report then carries one line with the title and a link instead of the full text.  Before planning a project, read the page's `marks` collection (ArtifactData) for notes the maintainer marked "Try this" / "Note for later", with their comments.
4. **Record the topic** in the list below (commit it with the next repo change) and in local notes; the page's notes.json holds the full text.
5. Remove the merged worktree (after preserving any research, see CLAUDE.md), and update local status notes.
